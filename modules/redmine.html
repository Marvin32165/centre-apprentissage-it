Redmine
Un outil de tickets pour le support, branché sur le domaine

Ce que tu sauras faire à la fin

  • Expliquer le modèle de Redmine : projet, tracker, statut, rôle, workflow — et ce qui lui manque face à un outil de helpdesk dédié.
  • Installer Redmine et MariaDB en Docker Compose, et ouvrir son API REST.
  • Brancher l'authentification sur l'Active Directory en LDAP, et diagnostiquer le refus d'un DC Windows Server 2025.
  • Sortir les mots de passe du Compose dans un .env sans casser une base existante.
  • Sauvegarder base, pièces jointes et configuration par un script planifié avec cron.
  • Publier Redmine en HTTPS derrière un reverse proxy nginx, avec redirection et en-têtes transmis.

Prérequis : Docker (Compose, volumes, réseaux). Linux et Windows Server aident pour la ligne de commande et l'annuaire. Ce module prolonge le module Agile & Scrum côté support : un flux de demandes imprévisibles, plutôt que des sprints.

Le labo : un serveur Ubuntu Server qui porte Redmine, publié sous helpdesk.orion.local (un alias DNS vers le serveur), dans le domaine orion.local déjà supervisé par Zabbix.

01

Ce qu'est Redmine

Redmine est une application web libre et gratuite (licence GPL v2) de gestion de projets et de suivi de demandes (issue tracking), écrite en Ruby on Rails, avec une base PostgreSQL, MySQL/MariaDB, SQL Server ou SQLite. Dans le TP, elle remplace SCSM (System Center Service Manager) comme outil de tickets — comme Zabbix remplace SCOM.

L'objet central : la demande

NotionSens
ProjetConteneur des demandes, avec ses membres et ses modules ; sous-projets possibles
TrackerLe type de demande (anomalie, évolution, assistance…), chacun avec ses champs
StatutOù en est la demande : nouveau, en cours, résolu, fermé…
PrioritéDe bas à immédiat
Assigné àLa personne ou le groupe qui traite la demande
WorkflowLes passages de statut permis, par rôle et par tracker (ex. seul le support passe en Résolu)

Un utilisateur devient membre d'un projet avec un rôle (Manager, Developer, Reporter…) qui porte les permissions ; il peut avoir des rôles différents d'un projet à l'autre. Les autres modules s'activent projet par projet : suivi du temps, Gantt et calendrier, wiki, forums, documents, dépôt Git. S'y ajoutent les champs personnalisés, les notifications et la création de demandes par e-mail, une API REST et des plugins.

Redmine n'est pas né helpdesk

Il vient de la gestion de projets de développement. Configuré (un projet « Support », un tracker d'assistance, un workflow adapté, la connexion à l'AD), il fait un honnête outil de support — mais il lui manque nativement ce qu'ont les outils dédiés comme GLPI : un portail simplifié pour l'utilisateur, des SLA, l'inventaire du parc. Des plugins, souvent payants, comblent ces manques.

À retenir

Tout tourne autour de la demande, rangée dans un projet, typée par un tracker, et qui avance de statut en statut selon un workflow qui dépend du rôle. Les droits ne sont pas portés par l'utilisateur mais par son rôle dans le projet.

02

Installer Redmine en Docker Compose

Deux conteneurs : Redmine et sa base MariaDB, dans un dossier ~/redmine sur le serveur.

ServiceImageConteneurRôle
dbmariadb:11redmine-dbLa base redmine ; port 3306 non publié
redmineredmine:7.0.2redmine-appL'application, publiée sur le port 80 de la VM (→ 3000)
  • REDMINE_DB_MYSQL: db : Redmine joint la base par le nom du service, sur un réseau privé.
  • Deux volumes nommés : la base et les pièces jointes — les données survivent aux conteneurs.
  • restart: unless-stopped pour redémarrer avec la VM ; SECRET_KEY_BASE signe les cookies de session.
bash — serveur Redmine
cd ~/redmine
sudo docker compose up -d
sudo docker ps                # redmine-app et redmine-db : Up

Au premier démarrage, Redmine crée lui-même ses tables.

Premier accès

  1. 01
    Sign inAvec le compte par défaut de Redmine, admin / admin : Redmine oblige à changer le mot de passe tout de suite.
  2. 02
    Load the default configurationUn bandeau d'Administration signale que rôles, trackers, statuts et workflow ne sont pas configurés. Le bouton charge les trackers Bug, Feature, Support, les rôles Manager, Developer, Reporter et 6 statuts.
  3. 03
    Ouvrir l'APIAdministration > Settings, onglet Integration : Enable REST web service (un script ou un autre outil peut lire et créer des tickets), Enable JSONP support, Enable webhooks (Redmine prévient une autre application quand un ticket change).

La clé API d'un compte se lit dans My account > API access key ; elle voyage dans l'en-tête X-Redmine-API-Key d'une requête.

À retenir

Une base non exposée, jointe par son nom de service ; des volumes pour la base et les pièces jointes ; puis trois gestes au premier accès — changer le mot de passe admin, charger la configuration par défaut, ouvrir l'API si un autre outil doit créer des tickets.

03

Brancher l'Active Directory

But : que chacun se connecte avec son compte du domaine, sans recréer les utilisateurs ni leurs mots de passe. Redmine vérifie le mot de passe auprès du contrôleur de domaine par LDAP (port 389 ; LDAPS, chiffré, sur le port 636).

Administration > LDAP authentication > New authentication mode :

ChampValeurExplication
Host / PortSRV-AD01.orion.local · 389Le DC à interroger, en LDAP non chiffré
Accountun compte de service du domaineSert à chercher l'utilisateur dans l'annuaire
Base DNDC=orion,DC=localPoint de départ de la recherche ; une OU (OU=Support,DC=orion,DC=local) limiterait aux comptes qu'elle contient
On-the-fly user creationcochéLe compte Redmine est créé à la première connexion
Login attributesAMAccountNameLe login Windows, sans le domaine
Firstname / Lastname / EmailgivenName · sN · mailLes attributs AD recopiés dans le profil

Test, sur la ligne du mode, vérifie seulement la connexion au DC avec le compte de service : il ne crée aucun utilisateur.

Le refus du DC

Premier test : « Unable to connect (Invalid LDAP Account/Password) ». Le compte et le mot de passe étaient pourtant bons : Redmine affiche ce message pour tout refus. La vraie réponse du DC était Stronger Auth Needed.

  • Redmine fait du LDAP simple : compte et mot de passe en clair, sans signature (qui garantit que l'échange n'a pas été modifié en route).
  • Un DC Windows Server 2025 exige cette signature par défaut. Le paramètre Domain controller: LDAP server signing requirements était à None, mais le nouveau …requirements Enforcement, Not Defined, l'impose quand même : c'est lui qui passe par-dessus.
  • LDAPS n'était pas une issue : le DC n'avait pas de certificat pour chiffrer.

Correction de lab, dans la Default Domain Controllers Policy (gpmc.msc) : Computer Configuration > Policies > Windows Settings > Security Settings > Local Policies > Security Options, Domain controller: LDAP server signing requirements Enforcement → Disabled, puis gpupdate /force sur le DC. Le Test passe, et un login du domaine crée son compte Redmine à la première connexion.

Lab seulement

En LDAP simple, les mots de passe du domaine passent en clair sur le réseau. En production : LDAPS (certificat sur le DC, port 636). Et jamais le compte Administrateur comme compte de service : un compte dédié, simple utilisateur du domaine — lire l'annuaire suffit.

À retenir

Un mode LDAP vers le DC + la création à la volée = les comptes AD se connectent avec leur login Windows. Face à « Invalid LDAP Account/Password », ne pas s'acharner sur le mot de passe : sur un DC 2025, la cause est d'abord la signature LDAP exigée.

04

Comptes, projet et premier ticket

Les comptes viennent de deux sources : créés à la main (Administration > Users > New user), ou à la première connexion depuis l'AD. Si la fiche AD d'un compte n'a ni prénom, ni nom, ni e-mail, on les saisit côté Redmine.

Le projet ITSM

Administration > Projects > New project → ITSM (IT Service Management, la gestion des services informatiques : le rôle que tenait SCSM). Identifiant itsm, projet public, trackers et modules par défaut. Puis, dans le projet : Issues > New issue → tracker, sujet, description, priorité, Assignee → Create.

Le premier ticket du TP a été créé par un utilisateur qui n'était membre d'aucun projet : il a pu le faire parce que le projet est public, ce qui lui donne le rôle Non member.

Exercice 1 — faire de ITSM un vrai helpdesk

C'est la suite prévue du TP. Les utilisateurs du domaine doivent pouvoir déclarer des incidents et suivre les leurs ; seule l'équipe support doit pouvoir les résoudre. Que configures-tu, et où ?

Afficher une proposition

Une configuration possible, à partir des notions du chapitre 01. Membres et rôles du projet : l'équipe support avec un rôle qui peut modifier et assigner les demandes, les utilisateurs avec un rôle de type Reporter (créer, commenter). Tracker : Support pour les incidents. Workflow (Administration > Workflow, par rôle et par tracker) : le passage en Resolved réservé au rôle support. Enfin, se demander si le projet doit rester public : en l'état, n'importe quel compte connecté voit les tickets des autres.

À retenir

Un projet public ouvre ses demandes au rôle Non member : pratique pour un premier test, à décider consciemment pour un vrai helpdesk. La configuration du support se fait par membres et rôles, trackers et workflow.

05

Les secrets dans un .env

Comme pour Zabbix : les mots de passe quittent docker-compose.yml pour un fichier .env posé à côté. Compose le lit tout seul et remplace chaque ${VARIABLE} par sa valeur.

~/redmine/.env (valeurs d'exemple)
# MariaDB
MYSQL_DATABASE=redmine
MYSQL_USER=redmine
MYSQL_PASSWORD=changez-moi
MYSQL_ROOT_PASSWORD=changez-moi-aussi
# Redmine
REDMINE_SECRET_KEY_BASE=une-longue-chaine-aleatoire
docker-compose.yml (extrait)
  db:
    environment:
      MARIADB_DATABASE: ${MYSQL_DATABASE}
      MARIADB_PASSWORD: ${MYSQL_PASSWORD}
  redmine:
    environment:
      REDMINE_DB_MYSQL: db
      REDMINE_DB_PASSWORD: ${MYSQL_PASSWORD}
      SECRET_KEY_BASE: ${REDMINE_SECRET_KEY_BASE}
bash — serveur Redmine
sudo chmod 600 .env                              # -rw------- : propriétaire seul
sudo docker compose config | grep -i password   # les valeurs du .env doivent apparaître
sudo docker compose up -d                       # recrée les conteneurs ; volumes conservés
  • Syntaxe d'un .env : NOM=valeur, sans espace autour du = — pas NOM: valeur comme dans le Compose. Et il ne va jamais dans un dépôt Git (.gitignore).
  • Au démarrage, un Can't connect to server on 'db' dans les logs est normal : depends_on attend que MariaDB démarre, pas qu'elle soit prête. Redmine réessaie et se connecte.

Deux pièges silencieux

Un nom de variable mal tapé (${MSQL_USER}) ne provoque aucune erreur : Compose le remplace par une chaîne vide, avec un simple avertissement — docker compose config le montre. Et sur une base existante, on garde les mêmes valeurs : MariaDB ne lit MARIADB_* qu'à la création de la base ; un mot de passe changé dans le .env ne changerait pas celui de la base, et Redmine ne pourrait plus s'y connecter.

À retenir

Secrets dans un .env en 600, hors de Git ; ${VARIABLE} dans le Compose ; docker compose config pour vérifier le remplacement avant de relancer.

06

Sauvegarder Redmine

Les données de Redmine sont à deux endroits : la base MariaDB (projets, tickets, comptes) et le volume des pièces jointes. Une sauvegarde complète prend les deux, plus la configuration (docker-compose.yml et .env) pour pouvoir tout reconstruire.

Le script du TP, backup-redmine.sh, range chaque sauvegarde dans un dossier daté :

ÉtapeCommande utiliséeRésultat
Lire le .envset -a; source .env; set +aLes mots de passe de la base en variables
Vérifierdocker inspect redmine-db / redmine-appArrêt si un conteneur manque
Basedocker exec redmine-db mariadb-dump --single-transaction … | gzipredmine-db.sql.gz
Pièces jointesdocker run --rm --volumes-from redmine-app alpine tar czf …redmine-files.tar.gz
Configurationcp docker-compose.yml .envCopie du Compose et du .env (600)
Rotationfind … -mindepth 1 -maxdepth 1 -type d -mtime +7 -exec rm -rf {} \;Supprime les sauvegardes de plus de 7 jours
  • --single-transaction : le dump se fait sans bloquer Redmine, sur une photo cohérente de la base.
  • --volumes-from redmine-app : un conteneur alpine jetable monte les mêmes volumes que Redmine et archive les pièces jointes.
  • Un fichier vide arrête le script et supprime le dossier incomplet.

Tous les jours à 16 h

cron est le planificateur de tâches de Linux. sudo crontab -e ouvre la table de root (le script a besoin de ses droits) :

crontab de root
# min heure jour mois jour-semaine  commande
0 16 * * * /home/admin/redmine/backup/backup-redmine.sh >> /home/admin/redmine/backups/backup.log 2>&1

>> backup.log 2>&1 ajoute la sortie et les erreurs du script au journal. Vérifier avec sudo crontab -l, puis lire le journal après le premier passage.

Ce que cette sauvegarde ne couvre pas

Elle reste sur la VM elle-même : elle protège d'une erreur de manipulation, pas de la perte de la VM — en production, on la copie ailleurs. Elle n'emporte pas la configuration nginx du chapitre suivant. Le .env copié contient les mots de passe en clair. Et tant qu'aucune restauration n'a été testée, elle reste une hypothèse.

À retenir

Une sauvegarde applicative complète = base (dump cohérent) + fichiers (le volume) + configuration, avec une rotation et une planification. Puis la question de la règle 3-2-1 : où est la copie qui survit à la perte du serveur ?

07

Publier Redmine en HTTPS derrière nginx

En HTTP, les mots de passe — y compris ceux du domaine, via LDAP — passent en clair. On place devant Redmine un reverse proxy nginx : nginx reçoit les connexions en HTTPS, les déchiffre et les transmet à Redmine sur le réseau Docker interne.

Le chemin d'une requête
navigateur ──HTTPS 443──▶ redmine-nginx ──HTTP 3000──▶ redmine-app ──▶ redmine-db
           ──HTTP 80 ───▶ (redirection 301 vers https://)

Le Compose

redmine ne publie plus aucun port : il n'est joignable que par nginx. Nouveau service nginx (nginx:alpine) qui publie 80 et 443, avec ses dossiers ./nginx/conf.d et ./nginx/certs montés en lecture seule (:ro).

Le certificat auto-signé

bash — ~/redmine
openssl genrsa -out nginx/certs/redmine.key 4096
openssl req -x509 -new -nodes -key nginx/certs/redmine.key -sha256 -days 365 \
  -out nginx/certs/redmine.crt \
  -subj "/C=BE/O=LAB/OU=IT/CN=helpdesk.orion.local" \
  -addext "subjectAltName=DNS:helpdesk.orion.local"

-x509 produit directement un certificat ; -nodes laisse la clé non chiffrée, pour que nginx la lise sans phrase secrète ; le subjectAltName est indispensable — le CN seul ne suffit plus aux navigateurs. Auto-signé : le chiffrement fonctionne, mais le navigateur avertit, faute d'autorité qu'il connaisse.

La configuration de nginx

nginx/conf.d/redmine.conf
server {
    listen 80;
    server_name helpdesk.orion.local;
    return 301 https://$host$request_uri;          # HTTP → HTTPS
}
server {
    listen 443 ssl;
    server_name helpdesk.orion.local;
    ssl_certificate     /etc/nginx/certs/redmine.crt;
    ssl_certificate_key /etc/nginx/certs/redmine.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    client_max_body_size 100M;                      # pièces jointes jusqu'à 100 Mo
    location / {
        proxy_pass http://redmine:3000;             # le service redmine du Compose
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;   # le client est en HTTPS
    }
}
bash — vérifier
sudo docker compose up -d
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://helpdesk.orion.local/
# 301 https://helpdesk.orion.local/
curl -sk -o /dev/null -w '%{http_code}\n' https://helpdesk.orion.local/   # -k : certificat auto-signé
# 200

Dire à Redmine son adresse

Redmine ne voit que nginx : il ne connaît pas l'adresse publique du site. Or il en a besoin pour les liens absolus qu'il envoie hors du navigateur — notifications par e-mail, webhooks, API — sinon ils pointent vers http://localhost:3000/…. Administration > Settings > General : Host name and path = helpdesk.orion.local, Protocol = HTTPS.

À retenir

Un reverse proxy : seul nginx publie des ports, il redirige 80 vers 443, termine le TLS et joint l'application par son nom de service. Les en-têtes X-Forwarded-* et le réglage Host name / Protocol rendent à l'application ce que le proxy lui cache : l'IP du client, le protocole et l'adresse publique.
