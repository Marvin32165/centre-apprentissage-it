Ce que tu sauras faire à la fin

  • Déployer Zabbix en Docker Compose avec une base injoignable du réseau et des mots de passe hors du fichier Compose.
  • Raccorder un serveur Windows par Zabbix Agent 2 en vérifications actives, chiffrées par PSK, et diagnostiquer un refus d'identité PSK.
  • Superviser le serveur Zabbix lui-même par un agent en conteneur, en visant le bon nom sur le réseau Docker.

Prérequis : Supervision — Zabbix (items, déclencheurs, modèles, agent) et Docker (Compose, réseaux, volumes). Windows Server aide pour la partie domaine.

Le labo : un serveur Ubuntu qui porte Zabbix en conteneurs, et trois serveurs Windows Server 2025 du domaine orion.local — un contrôleur de domaine, un serveur IIS, un serveur de fichiers. Les sauvegardes du même domaine sont dans System Center DPM, le support dans Redmine.

01

Zabbix à la place de SCOM

Dans la suite System Center, la supervision revient à SCOM (System Center Operations Manager). Le TP la confie à Zabbix, libre et gratuit : même rôle — collecter, évaluer, alerter — sur les mêmes serveurs Windows.

SRV-ZBX01172.16.50.40Ubuntu + Docker : base PostgreSQL, serveur et interface Zabbix 7.4, agent du serveur
SRV-AD01172.16.50.10Contrôleur de domaine + DNS — agent 2
SRV-WEB01172.16.50.25IIS et certificats de test — agent 2
SRV-FILE01172.16.50.20Serveur de fichiers — agent 2

Actif ou passif

Vérifications passives

  • Le serveur interroge l'agent, sur le port 10050 de l'agent.
  • Il faut que ce port soit joignable depuis le serveur.

Vérifications actives

  • C'est l'agent qui contacte le serveur, sur le port 10051, et lui envoie ses données.
  • Le choix du TP : modèle Windows by Zabbix agent active.

À retenir

Changer d'outil ne change pas la chaîne : mesurer, évaluer, alerter. Ce qui change, c'est le sens de la connexion : en actif, l'agent appelle le serveur sur 10051 — et ce choix a des conséquences tout au long du module.

02

La pile en Docker Compose

Plutôt qu'une installation paquet par paquet comme dans le module Supervision — Zabbix, le TP déploie Zabbix en conteneurs, dans un dossier projet /opt/zabbix-lab qui contient deux fichiers : docker-compose.yml et .env.

ConteneurImageRôle
zabbix-postgrespostgres:16-alpineLa base : configuration et historique, dans un volume nommé
zabbix-serverzabbix-server-pgsql:alpine-7.4-latestLe moteur — port 10051 publié pour les agents actifs
zabbix-webzabbix-web-nginx-pgsql:alpine-7.4-latestL'interface — port 80 de la VM vers 8080 du conteneur

Deux réseaux, un seul exposé

docker-compose.yml (extrait)
  postgres:
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}   # valeur lue dans .env
    volumes:
      - pgdata:/var/lib/postgresql/data       # les données survivent au conteneur
    networks:
      - zabbix-backend                        # réseau interne seulement

networks:
  zabbix-backend:
    internal: true                            # aucun accès vers l'extérieur
  zabbix-frontend:                            # réseau normal : permet de publier des ports

La base n'est que sur zabbix-backend : elle est injoignable depuis le réseau. Le serveur et l'interface sont sur les deux réseaux — le backend pour joindre la base, le frontend pour publier leur port. Ils trouvent la base par son nom de service (DB_SERVER_HOST: postgres), grâce au DNS interne de Docker. L'interface reçoit aussi PHP_TZ : le serveur Ubuntu est en UTC, l'affichage en heure de Bruxelles.

Les mots de passe dans un .env

Compose lit tout seul le fichier .env posé à côté et remplace chaque ${POSTGRES_...} par sa valeur. Le Compose peut être copié ou montré sans livrer les mots de passe, et le .env est réservé à son propriétaire :

bash — SRV-ZBX01
sudo mkdir -p /opt/zabbix-lab
cd /opt/zabbix-lab
sudo chmod 600 .env            # lisible par root seul
sudo docker compose up -d
docker ps                       # 3 conteneurs "Up"
docker logs zabbix-server

L'interface répond ensuite par son nom, grâce à un enregistrement A dans la zone DNS du domaine.

À retenir

Trois conteneurs, deux réseaux : la base sur un réseau interne, le serveur et l'interface à cheval sur les deux. Les secrets dans un .env en 600, les données dans un volume nommé. Et chaque service joint l'autre par son nom, jamais par une IP de conteneur.

Question éclair

Depuis SRV-AD01, un collègue tente de se connecter à PostgreSQL sur 172.16.50.40:5432 pour « jeter un œil à la base ». Que se passe-t-il ?

Le conteneur zabbix-postgres ne publie aucun port, et le réseau zabbix-backend est internal: true. Seuls les conteneurs reliés à ce réseau (serveur et interface) l'atteignent, par le nom postgres. Pour l'administrer : docker exec -it zabbix-postgres psql -U … depuis la VM.

03

Les agents Windows, chiffrés par PSK

Sur chaque serveur Windows : Zabbix Agent 2 en MSI, de la même version que le serveur (7.4). Puis une clé partagée pour chiffrer les échanges, et l'hôte à déclarer dans Zabbix.

L'installation

Écran / champValeur
Host nameSRV-AD01 — exactement le nom de l'hôte qu'on créera dans Zabbix
Zabbix server IP/DNSsrv-zbx01.orion.local
Agent listen port10050
Server or proxy for active checkssrv-zbx01.orion.local
Add agent location to the PATHcoché

Le PSK

Un PSK (Pre-Shared Key) est une clé partagée par l'agent et le serveur pour chiffrer leurs échanges. Le TP la pose avec un script fourni, qui génère une clé aléatoire de 64 caractères hexadécimaux dans psk\agent.psk, règle Hostname, ServerActive et les lignes TLS… de zabbix_agent2.conf, puis redémarre le service. Il demande PowerShell 7 :

PowerShell 7 — SRV-AD01
winget install --id Microsoft.PowerShell --source winget
& ".\Configure-ZabbixAgent2-PSK.ps1" -ZabbixServer srv-zbx01.orion.local -HostName SRV-AD01 -PskIdentity LAB-AD01-PSK
# PSK identity : LAB-AD01-PSK
# PSK value    : (64 caractères hexadécimaux, à reporter dans Zabbix)

L'hôte dans Zabbix

Data collection > Hosts > Create host. Onglet Host : le nom SRV-AD01, le modèle Windows by Zabbix agent active, les groupes Windows servers et Virtual machines. Onglet Encryption : PSK dans les deux sens, l'identité et la valeur affichées par le script.

Même chose pour le serveur IIS et le serveur de fichiers, chacun avec sa propre identité PSK. Résultat : Monitoring > Latest data se remplit. Dans l'infobulle de disponibilité, Active checks : Available, et l'interface …:10050 en Unknown — normal : un modèle agent active ne fait aucune vérification passive, le serveur n'appelle jamais le port 10050.

Exercice 1 — l'agent refusé

Un quatrième serveur ne remonte rien. Dans docker logs zabbix-server : cannot find requested PSK identity "LAB-APP01-PSK". Où chercher ?

Afficher la correction

Le serveur reçoit bien l'agent, mais ne connaît pas cette identité : l'onglet Encryption de l'hôte n'est pas rempli, ou pas avec la même identité. L'identité et la valeur doivent être identiques des deux côtés. Deuxième vérification : le nom de l'hôte dans Zabbix doit être exactement le Hostname= de l'agent — en vérifications actives, c'est ce nom que l'agent annonce.

À retenir

Trois choses doivent correspondre exactement entre l'agent et Zabbix : le nom d'hôte, l'identité PSK et la valeur PSK. Et en mode actif, une interface 10050 « Unknown » n'est pas une panne.

Question éclair

SRV-WEB01 : Latest data se remplit, l'infobulle indique Active checks : Available, mais l'interface 172.16.50.25:10050 reste « Unknown ». Que fais-tu ?

« Unknown » veut dire « jamais testé », pas « en erreur ». Avec Windows by Zabbix agent active, toutes les données passent par la connexion sortante de l'agent vers le 10051 : c'est l'indicateur Active checks qui compte.

04

Superviser le serveur Zabbix lui-même

L'hôte Zabbix server, créé par défaut, visait un agent sur 127.0.0.1:10050. Aucun agent n'était installé : l'hôte restait indisponible. Le TP ajoute un quatrième service au Compose.

docker-compose.yml — le 4ᵉ service
  zabbix-agent:
    image: zabbix/zabbix-agent2:alpine-7.4-latest  # même version que le serveur
    container_name: zabbix-agent
    hostname: zabbix-agent
    restart: unless-stopped
    init: true                                     # signaux d'arrêt, pas de zombies
    privileged: true                               # accès étendu au système de la VM
    pid: host                                      # voit les processus de la VM
    environment:
      ZBX_HOSTNAME: Zabbix server                  # = nom exact de l'hôte dans Zabbix
      ZBX_SERVER_HOST: zabbix-server
    networks:
      - zabbix-backend
bash — SRV-ZBX01
sudo docker compose up -d zabbix-agent   # seul le nouveau conteneur démarre
docker exec zabbix-server zabbix_get -s zabbix-agent -k agent.version
# 7.4.15

Puis, sur l'hôte Zabbix server, l'interface Agent : IP vide, DNS name zabbix-agent, Connect to : DNS, port 10050.

Pourquoi un nom, et pas une adresse ?

C'est le conteneur serveur qui interroge l'agent. Dans un conteneur, 127.0.0.1 désigne le conteneur lui-même : l'ancienne interface visait donc zabbix-server, où il n'y a pas d'agent. L'IP d'un conteneur change quand il est recréé, son nom de service non. Et l'IP de la VM ne marcherait pas : le port 10050 de l'agent n'est pas publié, il n'existe que sur le réseau Docker. Enfin, Connect to : DNS, sinon Zabbix utilise le champ IP et ignore le nom.

Limite : l'agent voit le CPU, la mémoire et les processus de la VM (pid: host), mais les disques de son conteneur. Pour superviser les disques du serveur, il faudrait un agent installé directement sur la VM.

À retenir

Entre conteneurs, 127.0.0.1 ne désigne jamais « la machine » : on vise le nom du service sur un réseau commun, et on choisit Connect to : DNS. Un agent en conteneur voit les processus de l'hôte, pas ses disques.

Question éclair

L'hôte Zabbix server garde son interface 127.0.0.1:10050 alors que le conteneur zabbix-agent tourne. Pourquoi reste-t-il indisponible ?

Chaque conteneur a sa propre pile réseau et son propre localhost. La correction : interface en DNS zabbix-agent, Connect to : DNS, sur le réseau Docker que les deux conteneurs partagent.

05

Un modèle maison : script + UserParameter

Le modèle Windows générique ne sait pas tout. Le TP lui ajoute deux modèles fournis — l'heure et les certificats — qui reposent sur le même mécanisme : une nouvelle clé apprise à l'agent.

Chaque modèle apporte un script PowerShell et un fichier .conf qui déclare la clé : UserParameter=clé,commande. Sur chaque serveur concerné :

  1. 01
    Le scriptDans C:\Program Files\Zabbix Agent 2\scripts\ (à créer s'il n'existe pas).
  2. 02
    Le .confDans zabbix_agent2.d\, déjà inclus par la ligne Include= de zabbix_agent2.conf.
  3. 03
    Redémarrer l'agentRestart-Service "Zabbix Agent 2"
  4. 04
    Tester la clé en localAvec l'option -t de l'agent (ci-dessous).
  5. 05
    Côté ZabbixData collection > Templates > Import du .yaml, puis lier le modèle aux hôtes.
PowerShell — serveur Windows
& "C:\Program Files\Zabbix Agent 2\zabbix_agent2.exe" -c "C:\Program Files\Zabbix Agent 2\zabbix_agent2.conf" -t windows.time.source

« Unknown metric » alors que le test réussit

-t relit la configuration à neuf et réussit ; mais le service déjà lancé ne connaît pas encore la nouvelle clé. Sans redémarrage de l'agent, l'item reste en Unknown metric — vu sur le serveur de fichiers du TP.

Deux réglages communs aux deux modèles : leurs items sont en Zabbix agent (active), comme le reste du labo, avec un timeout de 10 s — un script PowerShell dépasse souvent les 3 s par défaut. Et un item actif, c'est l'agent qui l'envoie : le bouton Execute now ne s'applique pas aux items actifs (il ne vaut que pour les vérifications que le serveur lance lui-même). Pour forcer une collecte, on redémarre l'agent.

À retenir

Un modèle maison = un script dans scripts\, un UserParameter dans zabbix_agent2.d\, un redémarrage de l'agent, puis l'import et la liaison du .yaml. Items actifs : timeout relevé, et pas d'Execute now.

Question éclair

Tu ajoutes UserParameter=windows.time.source,… dans zabbix_agent2.d\. Le test zabbix_agent2.exe -t windows.time.source renvoie bien une valeur, mais l'item affiche « Unknown metric ». Que manque-t-il ?

-t lance un processus neuf qui lit la configuration actuelle ; le service, lui, tourne avec celle qu'il a lue au démarrage. Restart-Service "Zabbix Agent 2", puis la clé est connue.

06

L'heure du domaine

Le modèle Windows Time Monitoring surveille le décalage d'horloge par rapport à un serveur NTP, la source de temps et la dernière synchronisation. Lié aux trois serveurs, il a tout de suite trouvé un vrai problème.

Le réglage

La macro du modèle {$TIME.NTP.SERVER} vaut le contrôleur de domaine : les membres se comparent à lui. Le DC ne pouvant se comparer à lui-même, une macro d'hôte sur le DC (Hosts > hôte > Macros) la remplace par un serveur public, be.pool.ntp.org.

Le problème découvert

Sur les trois serveurs, un avertissement : « VM IC Time Synchronization Provider is being used ». Les VM prenaient l'heure de l'hôte Hyper-V (fournisseur VMICTimeProvider), contrôleur de domaine compris, au lieu de suivre la hiérarchie du domaine. Or dans un domaine, la référence est le DC (émulateur PDC), lui-même synchronisé sur une source externe ; les membres se synchronisent sur lui.

PowerShell — sur le DC d'abord
# ne plus prendre l'heure de Hyper-V
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\W32Time\TimeProviders\VMICTimeProvider' -Name Enabled -Value 0
# source externe, et DC annoncé comme serveur de temps fiable
w32tm /config /manualpeerlist:"be.pool.ntp.org,0x8" /syncfromflags:manual /reliable:yes /update
Restart-Service w32time
w32tm /resync /rediscover
w32tm /query /source            # be.pool.ntp.org,0x8
PowerShell — puis sur chaque membre
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\W32Time\TimeProviders\VMICTimeProvider' -Name Enabled -Value 0
w32tm /config /syncfromflags:domhier /update     # hiérarchie du domaine → le DC
Restart-Service w32time
w32tm /resync /rediscover
w32tm /query /source            # SRV-AD01.orion.local

Un redémarrage de l'agent sur chacun, pour que Zabbix voie le changement tout de suite. Résultat : le DC en stratum 2, les membres en stratum 3, les trois problèmes se ferment. (Autre choix possible, si on tient à l'heure Hyper-V : la macro {$TIME.ALLOW.VMIC}=1.)

À retenir

Dans un domaine virtualisé : le DC sur une source externe (/reliable:yes), les membres en domhier, et le fournisseur Hyper-V désactivé. L'heure compte plus qu'il n'y paraît : Kerberos refuse l'authentification au-delà de quelques minutes d'écart. C'est un bon exemple de ce qu'une supervision apporte — un défaut silencieux rendu visible.

Question éclair

Sur SRV-FILE01, membre du domaine, w32tm /query /source répond be.pool.ntp.org,0x8. Est-ce la bonne configuration ?

Seul le DC émulateur PDC de la racine de la forêt va chercher une source externe. Les membres : w32tm /config /syncfromflags:domhier /update, puis w32tm /resync /rediscover ; la source doit devenir SRV-AD01.orion.local.

07

Surveiller les certificats

Le modèle Windows Certificates, lié au serveur IIS, prévient avant qu'un certificat n'expire. Il repose sur une découverte : Zabbix crée lui-même les items de chaque certificat trouvé.

Le script liste les certificats des magasins Cert:\LocalMachine\My et Cert:\LocalMachine\WebHosting dont le nom convivial (FriendlyName) contient @, et renvoie un JSON. Zabbix en fait une LLD (Low-Level Discovery) : pour chaque certificat, 9 items (jours restants, expiration, sujet, émetteur, noms DNS, clé privée…) et des déclencheurs d'expiration.

Deux adaptations du modèle d'origine

  • L'item maître passé en Zabbix agent (active), avec un timeout de 10 s.
  • Une sortie JSON toujours en tableau : en PowerShell 5.1, @($x) | ConvertTo-Json ne renvoie rien pour une liste vide et un objet seul pour un seul certificat, ce qui casse la découverte. D'où ConvertTo-Json -InputObject @($result).

Le test

Quatre certificats auto-signés de test sur le serveur IIS : deux dans My, deux dans WebHosting ; dans chaque magasin, l'un valable deux ans, l'autre quinze jours. Résultat : les quatre sont découverts, et les deux certificats à quinze jours lèvent un problème Average « expires in less than 15 days ».

  • New-SelfSignedCertificate ne crée que dans My : pour WebHosting, créer dans My puis déplacer avec Move-Item.
  • Le @ doit être dans le FriendlyName, pas seulement dans le sujet.
  • Pour les voir : certlm.msc (ordinateur local) — certmgr.msc montre les magasins de l'utilisateur.
  • Relancer la création sans supprimer les anciens crée des doublons (nouvelle empreinte). Côté Zabbix, les items d'un certificat disparu passent en Certificate not found in master JSON ; la découverte les désactive après 1 jour et les supprime après 7.

Exercice 2 — le certificat invisible

Un certificat de site web, bien présent dans certmgr.msc avec le sujet CN=intranet@orion, n'est pas découvert par Zabbix. Donne deux raisons possibles.

Afficher la correction

1) certmgr.msc montre les magasins de l'utilisateur : le script ne lit que ceux de l'ordinateur local (My et WebHosting), visibles dans certlm.msc. 2) Le @ est dans le sujet, alors que le script filtre sur le FriendlyName. Troisième piste si les deux sont bonnes : la découverte n'a pas encore tourné — c'est un item actif, on redémarre l'agent plutôt que de cliquer sur Execute now.

À retenir

Une découverte (LLD) transforme une liste JSON en items et déclencheurs, un jeu par objet trouvé. Pour ce modèle : @ dans le FriendlyName, magasins My et WebHosting de la machine, alerte Average à moins de 15 jours — et un JSON qui doit rester un tableau, même vide.

Question éclair

Sur un serveur qui n'a qu'un seul certificat marqué @, la découverte échoue alors qu'elle marche ailleurs. Le script se termine par $result | ConvertTo-Json (PowerShell 5.1). Pourquoi ?

Dans le pipeline, PowerShell 5.1 « déroule » la collection : un seul objet sort en {…}, aucun objet ne sort rien du tout. ConvertTo-Json -InputObject @($result) garde toujours un tableau […].

08

S'entraîner : PSK, métriques maison, heure

Les trois pièges du TP en exercices : l'identité PSK, la métrique maison qui reste « Unknown metric », et le contrôleur de domaine qui prend l'heure de Hyper-V.

Vérifier

Interroger un agent chiffré par PSK depuis le serveur. Ce test passe par une vérification passive : il suppose que le pare-feu de SRV-AD01 laisse entrer 10050 depuis SRV-ZBX01 (inutile en mode actif seul), et que la valeur PSK a été copiée dans un fichier lisible par le conteneur (ici /var/lib/zabbix/enc/ad01.psk, chemin à adapter).

bash — conteneur zabbix-server
docker exec zabbix-server zabbix_get -s 172.16.50.10 -k system.uptime \
--tls-connect psk --tls-psk-identity LAB-AD01-PSK --tls-psk-file /var/lib/zabbix/enc/ad01.psk

Sortie attendue

864213

Un échec de la négociation TLS (handshake) : l'identité ou la clé diffèrent d'un côté à l'autre — elles doivent être identiques au caractère près dans zabbix_agent2.conf et dans l'onglet Encryption de l'hôte.

À toi de taper

Teste localement, sur l'hôte Windows, la clé windows.certificates.expiring d'un UserParameter, avec la configuration de l'agent.

Voir la solution

& "C:\Program Files\Zabbix Agent 2\zabbix_agent2.exe" -c "C:\Program Files\Zabbix Agent 2\zabbix_agent2.conf" -t windows.certificates.expiring. Si le test répond mais que Zabbix affiche « Unknown metric », c'est que le service tourne encore avec l'ancienne configuration : Restart-Service "Zabbix Agent 2".

Vérifier

Le contrôleur de domaine a-t-il la bonne source de temps ?

PowerShell — SRV-AD01
w32tm /query /source

Sortie attendue

be.pool.ntp.org,0x8

VM IC Time Synchronization Provider : le DC prend toujours l'heure de l'hôte Hyper-V (désactiver ce fournisseur, chapitre 06). Local CMOS Clock : aucune source n'est joignable — vérifier UDP 123 en sortie.

À retenir

PSK : identité et clé identiques des deux côtés. Métrique maison : -t pour la tester, redémarrer l'agent pour qu'elle existe. Heure : le DC source du domaine ne doit jamais suivre l'hôte Hyper-V.
