01

Ce qu'est IIS

IIS (Internet Information Services) est le serveur web de Microsoft, livré comme un rôle de Windows Server. Il héberge sites et applications web, et c'est la plateforme d'exécution habituelle des technologies ASP.NET. Sa version suit celle de Windows : IIS 10 sur Windows Server 2016, 2019, 2022 et 2025.

ProtocoleUsage
HTTP / HTTPSPublication de sites web — le cœur du rôle
FTPDépôt et récupération de fichiers (chapitre 08)
SMTPRelais de messagerie, sans boîte aux lettres. Attention : c'est une fonctionnalité Windows à part (SMTP Server), gérée par l'ancienne console IIS 6, dépréciée depuis longtemps et retirée de Windows Server 2025. Pour du courrier, on passe par Exchange ou un relais tiers.

Les quatre méthodes d'installation

Toutes donnent le même résultat ; seul le contexte change.

MéthodeQuand l'utiliser
Server ManagerInstallation manuelle, une machine — c'est celle du labo
Depuis un autre serveurLe Server Manager d'un serveur d'administration installe le rôle sur une machine distante
PowerShellInstall-WindowsFeature Web-Server -IncludeManagementTools
Module WebAdministrationPas l'installation du rôle, mais la configuration ensuite : sites, pools, bindings, en script (lecteur IIS:\, New-Website…). Son successeur, IISAdministration (Get-IISSite, New-IISSite), fait la même chose plus vite ; la ligne de commande historique %windir%\system32\inetsrv\appcmd.exe existe toujours.

Côté client FTP

Deux outils suffisent : FileZilla (graphique) ou WinSCP (graphique et ligne de commande). Ils servent au chapitre 08.

À retenir

IIS est un rôle Windows Server, pas un produit séparé : HTTP/HTTPS d'abord, FTP en option (le SMTP est une fonctionnalité voisine, en voie de disparition). Le rôle s'installe nu, et les modules supplémentaires (FTP, authentifications avancées, ASP.NET) s'ajoutent après coup sans réinstaller quoi que ce soit.

Topologie du labo

Le serveur web rejoint la forêt orion.local déjà montée pour le module SQL Server : même contrôleur de domaine, même DNS, même plan d'adressage 172.16.50.0/24.

SRV-AD01172.16.50.10Contrôleur de domaine + DNS — orion.local (NetBIOS ORION)
SRV-SQL01172.16.50.30Serveur SQL Server, membre du domaine
SRV-WEB01172.16.50.25Serveur web, membre du domaine — srv-web01.orion.local

Machines et adresses du lab de référence Orion : le TP du cours utilisait ses propres noms, transposés ici.

Trois noms circulent dans tout le module : srv-web01.orion.local (le serveur lui-même), cafe.orion.local (le second site publié) et ftp.orion.local (le service FTP).

Préparer la VM

PowerShell — sur la VM IIS
# Adressage fixe, DNS pointé sur le contrôleur de domaine
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 172.16.50.25 -PrefixLength 24 -DefaultGateway 172.16.50.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 172.16.50.10
Disable-NetAdapterBinding -Name "Ethernet" -ComponentID ms_tcpip6

# Nom de machine puis jonction au domaine (un redémarrage à chaque fois)
Rename-Computer -NewName "SRV-WEB01" -Restart
Add-Computer -DomainName "orion.local" -Restart

À retenir

Le point qui conditionne tout le reste est le DNS pointé sur le contrôleur de domaine. Sans lui, ni la jonction au domaine ni la résolution de srv-web01.orion.local ne fonctionnent — et comme la publication de sites repose entièrement sur des noms, un serveur web mal résolu est un serveur web injoignable.

04

La console IIS Manager

La console est découpée en trois colonnes, et cette disposition se retrouve à chaque écran. Comprendre ce découpage, c'est savoir où chercher n'importe quel réglage.

À gauche — Connections

  • L'arborescence : le serveur, puis Application Pools et Sites.
  • Le niveau sélectionné détermine ce qu'affiche le centre.
  • Les réglages d'un site héritent de ceux du serveur tant qu'on ne les surcharge pas.

À droite — Actions

  • Edit Site → Bindings… : protocole + IP + port + nom d'hôte.
  • Basic Settings… : nom, pool et chemin physique.
  • Manage Website : Start / Stop / Restart, site par site.
  • Browse Website : ouvrir le site pour vérifier tout de suite.

05

Les pools d'applications

Un pool d'applications est le processus de travail (w3wp.exe) dans lequel tourne un site. C'est l'unité d'isolation d'IIS : deux sites dans deux pools distincts ne peuvent pas se planter l'un l'autre, et tournent sous des identités différentes.

Quand on crée un site dans IIS Manager (Add Website…), la console crée automatiquement un pool portant son nom. En PowerShell, New-Website ne le fait pas : sans -ApplicationPool, le site atterrit dans DefaultAppPool — d'où le New-WebAppPool du chapitre 09.

On en crée un séparé quand un site a besoin d'une identité propre — typiquement pour l'authentification : le pool s'exécute alors sous un compte de domaine qui, seul, a les droits sur les données visées.

ColonneSens
NameNom du pool ; DefaultAppPool est celui du site par défaut
StatusStarted / Stopped — un pool arrêté rend son site injoignable
.NET CLR Versionv4.0, ou No Managed Code pour un site statique ou PHP
Managed Pipeline ModeIntegrated (moderne) ou Classic (compatibilité ascendante)
IdentityCompte sous lequel tourne le processus — ApplicationPoolIdentity par défaut : un compte virtuel propre au pool, IIS AppPool\<nom du pool>, qui sort sur le réseau sous le compte ordinateur (ORION\SRV-WEB01$). Autres choix : LocalService, NetworkService, LocalSystem (à éviter : tous les droits sur la machine) ou un compte de domaine personnalisé (idéalement un gMSA, dont le mot de passe tourne tout seul)
ApplicationsNombre d'applications hébergées par le pool

À retenir

Un site = son pool. C'est ce qui permet d'arrêter, de redémarrer ou de compromettre un site sans toucher aux autres. L'identité du pool est aussi le compte que les droits NTFS doivent autoriser : un site qui renvoie 401.3 (accès refusé par une ACL) alors que les fichiers sont bien là, c'est presque toujours le compte qui lit le contenu qui n'a pas la lecture.

Piège : quel compte lit vraiment les fichiers ?

Deux comptes interviennent. Le processus w3wp.exe, sous l'identité du pool, lit toujours la configuration (web.config) : s'il ne peut pas, c'est un 500.19. Le contenu, lui, est lu sous l'identité de la requête : en authentification anonyme, c'est par défaut le compte IUSR (Authentication → Anonymous Authentication → Edit) ; en authentification Windows, c'est l'utilisateur connecté. S'il manque la lecture NTFS, IIS répond 401.3. Le réglage courant pour un site isolé : passer l'anonyme sur Application pool identity, pour qu'un seul compte, IIS AppPool\<pool>, lise tout.

Pas à pas

Le trajet d'une requête HTTP dans IIS : HTTP.sys → WAS → w3wp

  1. Étape 1 · client → HTTP.sys (noyau)

    La requête arrive sur le port 80

    Le navigateur envoie GET / HTTP/1.1 avec Host: cafe.orion.local. Ce n'est pas un processus IIS qui écoute le port, mais HTTP.sys, un pilote du noyau Windows. Si la réponse est dans son cache noyau, il la renvoie tout de suite, sans rien réveiller.

    L'écoute du port est faite par HTTP.sys, en mode noyau.

  2. Étape 2 · HTTP.sys

    Aiguillage vers la file du bon pool

    HTTP.sys compare IP, port et en-tête Host aux bindings qu'on lui a déclarés, trouve le site cafe, donc son pool, et dépose la requête dans la file d'attente de ce pool.

    Chaque pool a sa propre file dans HTTP.sys.

  3. Étape 3 · W3SVC / WAS → applicationHost.config

    Qui a configuré HTTP.sys ?

    Au démarrage, WAS (Windows Process Activation Service) lit %windir%\system32\inetsrv\config\applicationHost.config ; le service W3SVC s'en sert pour déclarer à HTTP.sys les URL à écouter. Modifier un binding dans la console met à jour ce fichier, puis HTTP.sys.

    W3SVC configure HTTP.sys ; la configuration vit dans applicationHost.config.

  4. Étape 4 · HTTP.sys → WAS

    Aucun processus pour ce pool ? WAS en démarre un

    Si aucun w3wp.exe ne sert encore le pool (premier accès, ou processus arrêté après 20 minutes sans requête, le Idle Time-out par défaut), la requête attend dans la file et WAS lance un processus de travail w3wp.exe sous l'identité du pool. D'où la première page plus lente après un moment d'inactivité.

    WAS crée, surveille et recycle les w3wp.exe.

  5. Étape 5 · w3wp.exe

    Le processus de travail traite la requête

    Le w3wp.exe prend la requête dans la file et la fait passer par ses modules : authentification, filtrage, document par défaut, puis le gestionnaire du fichier (fichier statique, ASP.NET…). Il lit le contenu sous l'identité de la requête : IUSR en anonyme par défaut, ou l'identité du pool si l'anonyme est réglé ainsi, ou l'utilisateur en authentification Windows. C'est ici que tombe un 401.3 si les droits NTFS manquent.

    Le contenu est lu sous l'identité de la requête (IUSR ou pool), jamais sous ton compte d'admin.

  6. Étape 6 · w3wp → HTTP.sys → client

    La réponse repart par le même chemin

    La réponse (200, 404…) est rendue à HTTP.sys, qui l'envoie au client et peut la mettre en cache. Si WAS ne peut pas démarrer le processus (mot de passe de l'identité expiré, plantages répétés qui déclenchent la protection rapide contre les échecs), c'est HTTP.sys qui répond lui-même 503.

    Un 503 vient de HTTP.sys : le pool n'a pas de processus pour répondre.

Question éclair

Tu copies les fichiers du site cafe dans D:\web\cafe en tant qu'administrateur. L'authentification anonyme est réglée sur Application pool identity. Le site répond 401.3, alors que toi, tu ouvres les fichiers sans problème. Que corriges-tu ?

401.3 = accès refusé par une ACL. Avec l'anonyme sur Application pool identity, le contenu est lu par w3wp.exe sous l'identité du pool, pas sous le compte qui a copié les fichiers (avec le réglage par défaut, ce serait IUSR). icacls "D:\web\cafe" /grant "IIS AppPool\cafe:(OI)(CI)RX" /T donne la lecture au seul compte virtuel du pool : moindre privilège respecté.

06

Publier un site avec son propre nom

Default Web Site publie C:\inetpub\wwwroot sur le port 80 : http://localhost depuis le serveur, http://srv-web01.orion.local depuis le réseau. C'est un site de test, pas un emplacement de production.

Mauvaise pratique

Déposer son site directement dans Default Web Site / C:\inetpub\wwwroot mélange son contenu avec le site par défaut, lui fait hériter de ses réglages et de son pool, et interdit d'arrêter ou de sécuriser l'un sans l'autre. Un site = son propre dossier, son propre binding, son propre pool.

Ajouter le site

Clic droit sur Sites → Add Website… :

  • Site name : le nom dans la console — crée aussi le pool du même nom.
  • Physical path : le dossier du site, en dehors de wwwroot.
  • Host name : cafe.orion.local.

Le host name est ce qui permet d'héberger plusieurs sites sur la même IP et le même port 80 : IIS lit l'en-tête Host de la requête HTTP et aiguille vers le bon site. Sans lui, deux sites en *:80 entrent en conflit : le second refuse de démarrer.

Et en HTTPS ? Le rôle de SNI

En HTTPS, le serveur doit présenter son certificat pendant la poignée de main TLS, donc avant d'avoir lu l'en-tête Host, qui voyage chiffré. Sans aide, IIS ne sait pas quel certificat envoyer : historiquement, il fallait une IP par site HTTPS. SNI (Server Name Indication, extension TLS gérée depuis IIS 8) règle le problème : le client annonce le nom voulu dès son premier message.

CritèreBinding HTTPBinding HTTPS
Port par défaut80443
Ce qui distingue les sitesL'en-tête HostLe nom annoncé par SNI, puis l'en-tête Host
Dans la fenêtre Add Site BindingHost nameHost name + case Require Server Name Indication + SSL certificate
Plusieurs sites sur une IPOui, un nom chacunOui, avec SNI : un certificat par nom (ou un certificat multi-noms)

Puis déclarer le nom dans le DNS

C'est l'étape qu'on oublie : sans elle, le navigateur ne sait pas où envoyer la requête, et le binding ne sert à rien. Sur SRV-AD01, dans la zone orion.local, on crée un alias (CNAME) — pas un enregistrement A :

EnregistrementTypeValeur
srv-web01A172.16.50.25 (le serveur lui-même)
cafeCNAMEsrv-web01.orion.local

Le seul enregistrement A est donc celui du serveur ; chaque site publié n'est qu'un alias vers lui. L'intérêt : si l'IP du serveur change, une seule ligne est à corriger, et tous les sites suivent. Avec des enregistrements A multiples, il faudrait reprendre chacun d'eux — avec le risque d'en oublier un.

Le mécanisme reste transparent pour IIS : le client résout cafe.orion.local → srv-web01.orion.local → 172.16.50.25, mais il envoie toujours l'en-tête Host: cafe.orion.local, qui est ce sur quoi le binding fait l'aiguillage.

Exercice 1 — le site qui ne répond pas

Tu as créé le site cafe avec le binding http/*:80:cafe.orion.local, le dossier contient bien un index.html, et le pool est démarré. Depuis un poste du domaine, http://cafe.orion.local ne donne rien du tout — pas même une erreur d'IIS. Où chercher, et dans quel ordre ?

Afficher la correction

« Pas même une erreur d'IIS » est l'indice : si IIS avait répondu quoi que ce soit (401, 403, 404, 500), c'est que la requête serait arrivée jusqu'à lui. Ici elle n'arrive pas.

  1. La résolution du nom : nslookup cafe.orion.local depuis le client. Pas de réponse → l'alias CNAME n'a pas été créé dans la zone orion.local. C'est l'oubli classique : le binding seul ne suffit pas.
  2. Le nom résout mais rien ne répond → vérifier que le client interroge bien le DNS du domaine (172.16.50.10) et non un DNS public.
  3. Enfin seulement : pare-feu du serveur sur le port 80, puis état du site et du pool dans la console.

Le raisonnement général : le nom résout-il ? la requête arrive-t-elle ? IIS répond-il ? — dans cet ordre, jamais l'inverse.

À retenir

Publier un site, c'est deux gestes, sur deux machines : le binding côté IIS, et l'alias CNAME côté DNS. Un seul enregistrement A, celui du serveur ; tout le reste en alias, pour n'avoir qu'une ligne à corriger le jour où l'IP change.

Question éclair

Le site cafe a son binding http/*:80:cafe.orion.local et son CNAME. Un collègue ouvre http://172.16.50.25 et tombe sur la page par défaut d'IIS, pas sur le café. Est-ce une panne ?

En tapant l'IP, le navigateur envoie Host: 172.16.50.25. Aucun binding ne porte ce nom : IIS sert le site lié à *:80 sans nom d'hôte, c'est-à-dire Default Web Site. C'est le comportement attendu : on teste un site par son nom, jamais par l'IP.

07

Déployer deux sites de bout en bout

Le labo publie deux sites statiques indépendants — guitare.orion.local et poissons.orion.local — sans aucune dépendance externe, pour qu'ils fonctionnent sur une VM coupée d'Internet. Chacun porte son web.config.

  1. 01
    Copier les fichiers hors de wwwrootPar exemple C:\sites\guitare\ et C:\sites\poissons\, via le partage admin ou une session RDP.
  2. 02
    Donner la lecture à l'identité du poolC'est IIS AppPool\<nom du pool> qui lit les fichiers (authentification anonyme réglée sur Application pool identity ; sinon c'est IUSR), pas l'administrateur qui les a copiés.
  3. 03
    Créer les sitesÀ la console (Add Website…) ou en script : un pool en No Managed Code — il n'y a aucun code .NET ici — le site, et son binding http/*:80:<hôte>.
  4. 04
    Déclarer les noms dans le DNSDeux CNAME vers srv-web01.orion.local, comme au chapitre précédent.
PowerShell — droits, DNS, vérification
# Sur la VM IIS : lecture + exécution pour l'identité de chaque pool
icacls "C:\sites\guitare"  /grant "IIS AppPool\guitare:(OI)(CI)RX"  /T
icacls "C:\sites\poissons" /grant "IIS AppPool\poissons:(OI)(CI)RX" /T

# Sur le contrôleur de domaine : un alias par site, jamais un enregistrement A
Add-DnsServerResourceRecordCName -ZoneName orion.local -Name guitare  -HostNameAlias srv-web01.orion.local
Add-DnsServerResourceRecordCName -ZoneName orion.local -Name poissons -HostNameAlias srv-web01.orion.local

# Vérification : on attend 200 pour chacun
Invoke-WebRequest http://guitare.orion.local  -UseBasicParsing | Select-Object StatusCode
Invoke-WebRequest http://poissons.orion.local -UseBasicParsing | Select-Object StatusCode

Ce qu'on contrôle dans le navigateur

  • L'accueil s'affiche sans /index.html dans l'URL → le Default Document est bon.
  • Une URL inexistante renvoie la page 404 du site, pas celle d'IIS → les httpErrors sont pris en compte.
  • Le pied de page affiche le nom d'hôte réellement utilisé → on vérifie que c'est bien le binding attendu qui a répondu.
  • Une page générée en JavaScript est vide → le fichier .js n'est pas servi : vérifier les types MIME et le filtrage des requêtes.

Erreur 500.19 au premier chargement

La section httpErrors est verrouillée au niveau serveur sur certaines installations. On la déverrouille une fois : Set-WebConfiguration //System.webServer/httpErrors -Metadata overrideMode -Value Allow -PSPath IIS:/. À défaut, retirer le bloc <httpErrors> du web.config concerné — le reste de la configuration fonctionne sans lui. Le 500.19 a d'autres causes : XML mal formé, élément d'un module non installé (URL Rewrite par exemple), ou web.config illisible par IIS. La page d'erreur détaillée, consultée sur le serveur, cite la ligne fautive.

À retenir

Un web.config posé à la racine d'un site porte sa configuration avec lui : document par défaut, page 404, compression, en-têtes de sécurité, types MIME, filtrage. C'est ce qui rend un site déplaçable — mais une section verrouillée au niveau serveur fait échouer tout le fichier en 500.19, pas seulement la ligne fautive.

Question éclair

Le site poissons s'affiche, mais sa galerie, générée par un fichier .js, reste vide. La console du navigateur montre un 404 sur ce .js, alors qu'il est bien dans le dossier. Que vérifies-tu en premier ?

Un fichier présent mais servi en 404, c'est IIS qui refuse de le livrer : extension sans type MIME connu, ou extension bloquée par le Request Filtering. Le journal IIS (C:\inetpub\logs\LogFiles) donne le sous-code : 404.3 pour un type MIME manquant, 404.7 pour une extension refusée par le filtrage.

08

Le service FTP

Le FTP n'est pas installé avec le rôle : il s'ajoute par Add roles and features → Web Server (IIS) → FTP Server. C'est l'illustration du chapitre 03 — un service de rôle qui arrive après coup, sans rien réinstaller.

Ensuite, dans IIS Manager : clic droit sur le nœud Sites → Add FTP Site… (un clic droit sur un site web existant propose plutôt Add FTP Publishing…, qui greffe le FTP sur ce site et son dossier).

ÉcranValeur du labo
Nom du siteftp
SSLNo SSL — labo uniquement : sans SSL, identifiants et fichiers circulent en clair
AuthenticationBasic (comptes du domaine) ; Anonymous donnerait un accès sans mot de passe
AuthorizationSpecified roles or user groups : ORION\Domain Users
PermissionsRead et Write

Puis clic droit sur le site FTP → Edit Bindings… et ajouter le nom d'hôte ftp.orion.local — à déclarer dans le DNS comme au chapitre 06, donc là aussi en alias CNAME vers srv-web01.orion.local. La connexion se fait ensuite depuis FileZilla ou WinSCP sur ftp://ftp.orion.local, avec un compte du domaine.

Piège : le nom d'hôte FTP

Le protocole FTP n'a pas d'en-tête Host comme HTTP. Dès que le site FTP a un nom d'hôte virtuel dans son binding, IIS attend ce nom dans l'identifiant : ftp.orion.local|utilisateur (barre verticale). Un client qui envoie seulement utilisateur reçoit un 530 (connexion refusée) alors que le mot de passe est bon. Deux sorties : taper l'identifiant complet, ou laisser le binding FTP sans nom d'hôte s'il n'y a qu'un site FTP sur la machine.

Exercice 2 — le FTP qui publie le site

On veut que les fichiers déposés par FTP mettent à jour immédiatement le site guitare.orion.local. Qu'est-ce que cela impose, et quel est le risque introduit ?

Afficher la correction

Il faut que le site FTP pointe sur le même chemin physique que le site web (C:\sites\guitare) : un fichier déposé est alors servi au rechargement suivant, sans copie ni redémarrage.

Deux conséquences à assumer :

  • L'identité du pool doit garder la lecture, et le compte FTP l'écriture : deux jeux de droits NTFS sur le même dossier.
  • Surtout : n'importe quel membre de Domain Users peut alors modifier le contenu publié, et ses identifiants circulent en clair puisque le labo est en No SSL. En production : FTPS, un groupe dédié au lieu de Domain Users, et l'écriture limitée au strict nécessaire.

Labo vs production

No SSL + Basic, c'est un mot de passe de domaine envoyé en clair sur le réseau. Acceptable dans un labo isolé, jamais ailleurs : en production, c'est FTPS (ou SFTP via un autre service), un groupe dédié plutôt que Domain Users, et des permissions réduites au dossier concerné.

Question éclair

Le site FTP a le binding ftp.orion.local. Dans FileZilla, ORION\alice et son bon mot de passe donnent 530 User cannot log in. Que tapes-tu dans le champ identifiant ?

FTP n'envoie pas d'en-tête Host : avec un nom d'hôte virtuel, IIS le lit dans l'identifiant, sous la forme nom-d-hôte|utilisateur. Sans lui, IIS ne sait pas à quel site FTP rattacher la connexion et la refuse.

Les gestes d'IIS en PowerShell, une vérification de bout en bout depuis le client, et les codes d'erreur HTTP qui disent où chercher.

PowerShell — SRV-WEB01 : un site par nom d'hôte, en script (module WebAdministration)
New-Item -ItemType Directory C:\inetpub\cafe

À toi de taper

Liste les bindings (protocole, port, nom d'hôte) du site cafe.

Voir la solution

Get-WebBinding -Name cafe — on doit y lire http *:80:cafe.orion.local.

À toi de taper

Redémarre le pool d'applications cafe.

Voir la solution

Restart-WebAppPool -Name cafe (ou Start-WebAppPool s'il est arrêté). Un 503 qui revient après un redémarrage : regarder pourquoi le pool s'arrête (journal Système, protection rapide contre les échecs).

À retenir

Un site = un dossier + un pool + un binding (IP, port, nom d'hôte) + un nom dans le DNS. Le code HTTP dit la couche : 404 contenu, 401 authentification (401.3 = ACL NTFS), 403 refus d'IIS, 500 application, 503 pool arrêté. Le sous-code est dans le journal IIS (colonne sc-substatus).
