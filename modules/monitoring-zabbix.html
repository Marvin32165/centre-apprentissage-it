01

Pourquoi superviser

Le monitoring (ou supervision) consiste à surveiller l'état et l'utilisation des machines du parc : serveurs, bases de données, équipements réseau. À cette surveillance s'ajoute la mise en place d'alertes, pour être prévenu automatiquement quand une valeur sort des clous.

Les trois objectifs

ObjectifCe que ça veut dire
SurveillerConnaître en continu l'état réel des machines
Être alertéNe pas découvrir le problème par l'utilisateur qui appelle
AnticiperÊtre proactif plutôt que réactif : agir avant la panne

Ce que ça apporte concrètement

  • Détecter les problèmes potentiels — un disque qui sature se voit des semaines avant de bloquer un service.
  • Réduire les temps d'arrêt — prévenir avant la coupure plutôt que réparer après.
  • Optimiser les performances — une RAM constamment à ~90 % signale un sous-dimensionnement, une fuite mémoire ou une machine compromise.
  • Mieux gérer les ressources — repérer le trop comme le trop peu, donc arbitrer les achats sur des chiffres.
  • Améliorer la sécurité — suivi des comptes, des connexions, des services qui démarrent.
  • Rassurer les utilisateurs — savoir que quelqu'un surveille change la perception du service.

À retenir

La supervision ne sert pas à faire de jolis graphes : elle sert à déplacer le moment où on apprend le problème. Réactif, on l'apprend par l'utilisateur ; proactif, on l'apprend avant lui. Le troisième objectif — anticiper — est celui qui justifie tout le chapitre 09 de ce module.

02

Architecture de Zabbix

Zabbix est un logiciel de monitoring open source et gratuit : une interface web en PHP, installée généralement sous Linux, avec les données stockées dans une base, et un agent déposé sur les machines à surveiller.

ÉlémentRôle
Zabbix ServerLe cœur : collecte, évalue les conditions de déclenchement, lance les actions. Écoute sur le port 10051/TCP (agents actifs, proxies)
Zabbix DatabaseStocke la configuration et les données collectées (mots de passe des utilisateurs hachés)
Zabbix Web interfaceLa console d'administration en PHP, servie par Nginx ou Apache (HTTP par défaut, HTTPS à configurer), avec des permissions par groupe d'utilisateurs
Zabbix AgentsInstallés sur les machines surveillées, ils remontent les données. Écoutent sur le port 10050/TCP (vérifications passives)
Zabbix ProxiesCollectent pour le compte du serveur et lui transmettent les données par lots : sites distants, montée en charge. Un proxy n'évalue pas les triggers, c'est toujours le serveur qui décide
Commandline utilitieszabbix_get (interroger un agent), zabbix_sender (envoyer une valeur au serveur)

Le tableau de bord

Le dashboard réunit sur une même page :

  • une carte du réseau où chaque hôte porte son état (vert = OK, rouge = en problème) ;
  • les problèmes par sévérité — Disaster, High, Average, Warning, Information, Not classified — regroupés par groupe d'hôtes ;
  • des graphiques de métriques dans le temps, avec le détail au survol.

À retenir

Quatre briques à ne pas confondre : le serveur décide, la base conserve, le frontend affiche, l'agent mesure. Le proxy n'apparaît que lorsqu'on supervise un site distant ou qu'un seul serveur ne suffit plus. Toute la suite du module installe ces briques dans cet ordre.

Question éclair

L'entreprise ouvre une agence de 40 serveurs, reliée au siège par un VPN parfois coupé. On veut la superviser sans perdre de données pendant les coupures. Que places-tu sur le site distant ?

Le proxy collecte sur place et garde les valeurs dans sa propre base locale le temps de la coupure, puis les transmet au serveur. Les triggers, eux, restent évalués par le serveur central : une seule console, une seule configuration.

03

Le réseau NAT du labo

Objectif : donner aux VM un réseau privé qui sort vers Internet à travers la machine hôte. C'est la machine hôte qui joue la passerelle NAT. Le TP avait son propre plan d'adressage ; on le transpose ici sur le lab Orion : réseau 172.16.50.0/24, commutateur LABOPS.

Hôte Hyper-V172.16.50.1Passerelle NAT — carte du commutateur interne LABOPS
SRV-ZBX01172.16.50.40Ubuntu Server — serveur Zabbix : base, frontend, agent
SRV-FILE01172.16.50.20Windows Server 2025 supervisé par agent
  1. 01
    Créer un commutateur interneSur l'hôte Hyper-V, nommé LABOPS.
  2. 02
    Créer le NATEn PowerShell administrateur sur l'hôte (voir la commande ci-dessous).
  3. 03
    Adresser la carte de l'hôte172.16.50.1/24, sans passerelle ni DNS — c'est elle, la passerelle.
  4. 04
    Rattacher la VMAssigner le commutateur LABOPS à la machine virtuelle.
  5. 05
    Adresser la VM172.16.50.40/24, passerelle 172.16.50.1, DNS 172.16.50.10 (SRV-AD01) — ou un résolveur public tant que le domaine n'existe pas.
PowerShell — sur la machine hôte, en administrateur
New-NetNat -Name "LABOPS-NAT" -InternalIPInterfaceAddressPrefix 172.16.50.0/24

# La sortie confirme Active : True — le NAT est monté côté hôte,
# il reste à adresser la carte vEthernet (LABOPS) en 172.16.50.1/24.

Vérifier

Sur l'hôte, le NAT existe ; depuis la VM, la passerelle puis Internet répondent.

PowerShell — hôte, puis bash — SRV-ZBX01
Get-NetNat | Select-Object Name, InternalIPInterfaceAddressPrefix, Active   # sur l'hôte
ping -c 2 172.16.50.1      # sur la VM : la passerelle
ping -c 2 1.1.1.1          # sur la VM : Internet, par le NAT

Sortie attendue (hôte)

Name        InternalIPInterfaceAddressPrefix Active
----        -------------------------------- ------
LABOPS-NAT  172.16.50.0/24                     True

La passerelle répond mais pas Internet : le NAT manque ou couvre un autre préfixe (Windows n'accepte qu'un seul NAT de ce type : Get-NetNat, puis Remove-NetNat de l'ancien). La passerelle ne répond pas : la carte vEthernet (LABOPS) n'a pas son adresse .1, ou la VM n'est pas sur ce commutateur.

À retenir

Un commutateur interne ne sort nulle part tout seul : c'est New-NetNat sur l'hôte, plus l'adresse .1 posée sur sa carte, qui en font une passerelle. Si les VM se pinguent entre elles mais n'atteignent pas Internet, c'est presque toujours l'un de ces deux gestes qui manque — pas la configuration de la VM.

Question éclair

SRV-ZBX01 pingue 172.16.50.1, mais apt update échoue : aucun dépôt joignable, même par adresse IP. Que vérifies-tu en premier ?

La passerelle répond, donc la VM, le commutateur et l'adresse .1 de l'hôte sont bons. Si même une IP publique est injoignable, c'est la traduction d'adresses qui manque : New-NetNat absent, ou créé sur un autre préfixe.

04

Ubuntu Server et MySQL

La VM Linux porte tout : la base, le serveur Zabbix et le frontend. Le dimensionnement se choisit selon les besoins réels — ici 2 vCPU et 8 Go de RAM, mémoire dynamique décochée, génération 2 avec Secure Boot désactivé.

À l'installation d'Ubuntu

  • Configuration réseau manuelle sur l'interface : adresse 172.16.50.40/24, passerelle 172.16.50.1, DNS 172.16.50.10.
  • Stockage : Use an entire disk, valeurs par défaut. Le disque est découpé en trois — une partition ESP fat32 montée sur /boot/efi, une ext4 sur /boot, et le reste en volume physique LVM portant la racine / en ext4.
  • Cocher Install OpenSSH server : c'est ce qui permet de quitter la console Hyper-V et de travailler en SSH dès le premier redémarrage.
Bash — sur la VM Ubuntu
# Rafraîchir le catalogue PUIS appliquer : l'un ne sert à rien sans l'autre
sudo apt update && sudo apt upgrade -y

# Base de données : Zabbix y stocke sa configuration et ses métriques
sudo apt install mysql-server -y
sudo systemctl start mysql     # démarre maintenant
sudo systemctl enable mysql    # fera repartir au prochain boot
sudo systemctl status mysql    # q pour quitter l'affichage

Lire la sortie de systemctl status

LigneCe qu'on veut voir
Loadedenabled — le service démarrera tout seul au boot
Activeactive (running) en vert — le service tourne
Status"Server is operational"

Aucune sortie = tout va bien

Sous Linux, une commande qui réussit est généralement silencieuse. systemctl start qui ne dit rien a fonctionné ; c'est status qu'on interroge pour en avoir la preuve.

À retenir

start agit maintenant, enable agit au prochain démarrage. Les deux sont nécessaires pour un service d'infrastructure — un serveur de supervision qui ne repart pas après un redémarrage est exactement l'inverse de ce qu'on cherche à construire.

Installer Zabbix

La page zabbix.com/download génère les commandes d'installation à partir de six choix. Changer une seule valeur change l'URL du dépôt et la liste des paquets — d'où l'importance de noter la combinaison retenue.

Bash — dépôt et paquets

Créer la base, puis importer le schéma

MySQL — création de la base et de l'utilisateur
-- mysql -uroot -p
create database zabbix character set utf8mb4 collate utf8mb4_bin;
create user zabbix@localhost identified by '<mot de passe de l'utilisateur zabbix>';
grant all privileges on zabbix.* to zabbix@localhost;

-- Autorisation TEMPORAIRE, nécessaire uniquement à l'import qui suit
set global log_bin_trust_function_creators = 1;
quit;
Bash — import du schéma, puis retour en arrière
# Le mot de passe demandé est celui de l'utilisateur zabbix, pas celui de root
zcat /usr/share/zabbix/sql-scripts/mysql/server.sql.gz | mysql --default-character-set=utf8mb4 -uzabbix -p zabbix

# Puis, dans mysql -uroot -p : set global log_bin_trust_function_creators = 0;

L'étape qu'on saute

Sans l'import du schéma, la base reste vide et zabbix-server refuse de démarrer — sans dire clairement pourquoi. C'est aussi la seule raison d'être du log_bin_trust_function_creators = 1, qu'on remet à 0 aussitôt après : une autorisation posée pour une opération se retire quand l'opération est finie.

Brancher le serveur et le frontend

FichierLigne à poserPourquoi

Le nom du service PHP suit la version de PHP fournie par la distribution : php8.5-fpm sur Ubuntu 26.04, php8.3-fpm sur Ubuntu 24.04. En cas de doute, systemctl list-units 'php*-fpm*'.

Vérifier

Le serveur tourne et écoute pour les agents ; Nginx sert l'interface.

sudo ss -tlnp | grep -E ':10051|:8080'

Sortie attendue (extrait)

Pas de 10051 : le serveur ne tourne pas — lire /var/log/zabbix/zabbix_server.log (le plus souvent DBPassword faux ou schéma non importé). Pas de 8080 : la ligne listen de /etc/zabbix/nginx.conf est restée commentée.

Terminer dans le navigateur

Sur http://172.16.50.40:8080/, l'assistant déroule : Welcome → Check of pre-requisites → Configure DB connection (mot de passe de l'utilisateur zabbix) → Settings (nom du serveur Zabbix) → récapitulatif → Install.

La première connexion se fait avec le compte par défaut Admin / zabbix, qu'on change immédiatement dans User settings → Profile → Change password. Le Global view confirme alors l'installation : Zabbix server is running : Yes, un hôte disponible — le serveur lui-même, qui se supervise via son propre agent — et aucun problème en cours.

À retenir

Trois valeurs doivent coïncider ou rien ne fonctionne : le mot de passe donné à create user, celui écrit dans DBPassword, et celui saisi dans l'assistant web. Et le compte Admin / zabbix par défaut est public : le changer fait partie de l'installation, pas du durcissement optionnel.

06

L'agent sur Windows Server

L'agent se télécharge sur zabbix.com/download_agents en MSI, pour Windows Server 2016+, amd64, chiffrement OpenSSL. Sa version suit celle du serveur installé au chapitre précédent — ici 7.4.

Champ de l'installeurValeur
Host nameSRV-FILE01
Zabbix server IP/DNS172.16.50.40
Agent listen port10050 par défaut
Server or Proxy for active checks172.16.50.40
Add agent location to the PATHcoché

Les valeurs saisies se retrouvent dans C:\Program Files\Zabbix Agent\zabbix_agentd.conf : Server=172.16.50.40 (section Passive checks), ServerActive=172.16.50.40 et Hostname=SRV-FILE01 (section Active checks).

Passif et actif : qui appelle qui

Passive checks

  • C'est le serveur qui vient interroger l'agent.
  • Sur le port 10050/TCP, entrant sur la machine supervisée.
  • Réglé par Server=.

Active checks

  • C'est l'agent qui contacte le serveur.
  • Il récupère la liste des éléments à collecter, puis envoie les valeurs au port 10051/TCP du serveur (sortant pour l'agent).
  • Réglé par ServerActive= et Hostname=.

Agent 1 ou agent 2

Zabbix propose deux agents. Un seul suffit par machine, et le serveur ne fait pas la différence : même protocole, même port 10050, mêmes modes passif et actif, mêmes UserParameter. Ce labo installe l'agent 1 partout.

CritèreAgent 1 — zabbix_agentdAgent 2 — zabbix_agent2
LangageCGo (reprend une partie du code C)
PlateformesLinux, Windows et les Unix (AIX, BSD, Solaris, macOS…)Linux et Windows seulement
ExtensionUserParameter, modules chargeables en CUserParameter, plugins Go — pas de modules C
Supervision intégréeLe système : CPU, mémoire, disques, réseau, journaux, services WindowsIdem + systemd, Docker, PostgreSQL, MySQL, Redis, certificats TLS, S.M.A.R.T.…
ExécutionPlusieurs processus, vérifications actives en sérieUn seul processus, vérifications en parallèle
Tampon des valeursEn mémoire, perdu à l'arrêtEn mémoire, ou persistant sur disque
Paquet Linux / service Windowszabbix-agent / Zabbix Agentzabbix-agent2 / Zabbix Agent 2

Lequel choisir

Agent 2 par défaut sur un Linux ou un Windows récent : il sait tout ce que fait l'agent 1 et supervise en plus les applications sans script maison. Agent 1 sur une plateforme que l'agent 2 ne couvre pas, ou quand on dépend d'un module en C. Les templates propres à l'agent 2 portent « agent 2 » dans leur nom : attachés à un hôte en agent 1, leurs items passent en Not supported.

À retenir

La distinction n'est pas théorique, elle décide du sens des flux à ouvrir. En passif, le pare-feu de la machine supervisée doit accepter le 10050 entrant ; en actif, c'est l'agent qui sort, et c'est le Hostname= qui l'identifie auprès du serveur.

Question éclair

Un hôte n'utilise que des items Zabbix agent (active). Quel flux le pare-feu doit-il laisser passer ?

En actif, c'est l'agent qui ouvre la connexion, vers le port d'écoute du serveur (10051, ou celui d'un proxy). Le 10050 entrant sur l'agent ne sert qu'aux vérifications passives — et à zabbix_get.

07

Déclarer l'hôte et vérifier

Installer l'agent ne suffit pas : tant que l'hôte n'existe pas dans l'interface, personne ne lui demande rien. Data collection → Hosts → Create host.

ChampValeur
Host nameSRV-FILE01
TemplatesGroupe Operating systems → Windows by Zabbix agent
Host groupsVirtual machines
InterfacesAdd → Agent, IP 172.16.50.20, port 10050

Le piège

Le Host name doit être strictement identique au Hostname= du fichier de configuration de l'agent, casse comprise. Sinon les active checks sont refusés par le serveur — et on cherche longtemps du côté du réseau un problème qui est une différence de majuscule.

Vérifier que les informations remontent

  • Data collection → Hosts : la pastille ZBX passe au vert quand l'agent répond (gris = pas encore contacté, rouge = erreur, cause affichée au survol).
  • Monitoring → Latest data, filtré sur l'hôte : des valeurs arrivent — CPU, mémoire, disques, services.
  • Dashboards → Global view : le nombre d'hôtes disponibles passe de 1 à 2.

Exercice 1 — la pastille reste rouge

L'agent est installé, l'hôte est créé avec le template Windows, mais la pastille ZBX reste rouge. Dans quel ordre vérifies-tu, et pourquoi cet ordre ?

Afficher la correction
  1. Le ping entre les deux VM — inutile de chercher plus haut si la couche réseau ne passe pas. Les deux sont sur LABOPS, donc ça doit répondre (si le pare-feu Windows autorise l'ICMP).
  2. Le service et le pare-feu Windows sur le port 10050/TCP — le serveur interroge l'agent en passif ; si le service est arrêté ou le port filtré, le serveur n'obtient rien et affiche l'erreur au survol de la pastille. Depuis SRV-ZBX01, zabbix_get -s 172.16.50.20 -k agent.ping tranche.
  3. Server=172.16.50.40 dans zabbix_agentd.conf — l'agent refuse les requêtes d'une adresse qui n'y figure pas.
  4. La correspondance exacte du Hostname — dernier point parce qu'il ne casse que les active checks, pas la disponibilité passive.

Le principe est le même que partout : on remonte les couches du bas vers le haut, du câble vers l'application. Et on lit le message d'erreur au survol avant de deviner.

À retenir

Un template est ce qui transforme un hôte vide en hôte supervisé : il apporte d'un coup les éléments à collecter, les graphes et les conditions de déclenchement. On ne crée presque jamais d'item à la main — on attache le bon template, et on l'adapte.

À toi de taper

Depuis SRV-ZBX01, demande à l'agent de SRV-FILE01 (172.16.50.20) la clé agent.ping, comme le ferait une vérification passive.

Voir la réponse

zabbix_get -s 172.16.50.20 -k agent.ping — la réponse 1 prouve que le réseau, le pare-feu, le service et la ligne Server= sont bons d'un coup. Le paquet zabbix-get s'installe à part s'il manque (apt install zabbix-get).

Question éclair

Tu crées l'hôte SRV-FILE01 avec son interface agent, mais sans lier de template. La pastille ZBX passe au vert. Que vois-tu dans Latest data ?

La disponibilité (pastille) et la collecte sont deux choses. C'est le template qui apporte les items, donc les valeurs, puis les triggers qui les évaluent.

08

Exploiter Zabbix au quotidien

Une fois les hôtes supervisés, l'usage courant tient en deux réflexes : regarder les courbes, et déléguer les comptes à l'annuaire plutôt que de les gérer dans Zabbix.

Lire les données

  • Graphes : depuis le tableau de bord ou la liste des hôtes, clic sur la machine → Graphs. Zabbix affiche les graphes fournis par le template — CPU, mémoire, disques, réseau — avec le détail des valeurs au survol.
  • Valeurs brutes : Monitoring → Latest data, filtré sur l'hôte, quand on veut le chiffre exact plutôt que la courbe.

Authentification LDAP

Zabbix peut déléguer la connexion à l'Active Directory au lieu de gérer ses propres comptes : Users → Authentication → LDAP settings, puis connexion avec un compte AD.

Récupérer les groupes, pas les comptes

Mieux vaut mapper les groupes AD que les utilisateurs un par un : les droits se gèrent alors une seule fois par groupe, et un nouvel arrivant ajouté au bon groupe AD obtient automatiquement son accès à Zabbix. Cela suppose d'activer le provisionnement JIT (Enable JIT provisioning, depuis Zabbix 6.4) avec un mappage groupe AD → groupe d'utilisateurs Zabbix ; sans lui, l'utilisateur doit déjà exister dans Zabbix pour que sa connexion LDAP soit acceptée. C'est exactement la logique des droits par groupe du module Windows Server.

À retenir

Un outil de supervision qui gère ses propres comptes devient vite un annuaire parallèle : comptes d'anciens collègues toujours actifs, mots de passe jamais changés. Déléguer à l'annuaire et raisonner par groupe fait disparaître le problème à la source.

09

Un parc qui se répare seul

L'énoncé de l'exercice : tous les services Windows supervisés doivent redémarrer seuls quand ils s'arrêtent, et en bonus Zabbix doit nettoyer les fichiers temporaires de la machine. Zabbix ne se contente plus d'alerter — il agit.

La chaîne complète
service arrêté ──► trigger (tag type=WinService) ──► action ──► script sur l'agent
                                                                 net start <service>
BriqueRôle ici
Discovery (LLD)Le template Windows by Zabbix agent découvre chaque service et crée pour lui un trigger « is not running »
TriggerSe déclenche quand un service est arrêté ; son tag permet de le repérer, sa description transporte le nom du service
ScriptLa commande à exécuter sur la machine (net start …)
ActionLa règle « si un problème porte ce tag → lancer ce script »
AgentExécute réellement la commande — à condition d'y être autorisé

Pas à pas

Le chemin d'une alerte, de la mesure à la notification

  1. Étape 1 · agent → serveur

    La collecte

    Sur SRV-FILE01, l'item vfs.fs.size[C:,pfree] (pourcentage d'espace libre sur C:) est relevé à son intervalle. En passif, le serveur le demande sur le port 10050 de l'agent ; en actif, l'agent l'envoie au port 10051 du serveur.

    Une clé, un intervalle, un sens de connexion : rien n'est mesuré sans item.

  2. Étape 2 · serveur → base

    L'item stocke la valeur

    Le serveur applique l'éventuel prétraitement, puis écrit la valeur dans l'historique de la base. Elle apparaît dans Monitoring → Latest data et dans les graphes.

    Une valeur = une ligne d'historique, horodatée, rattachée à un item.

  3. Étape 3 · serveur

    Le trigger est réévalué

    Chaque nouvelle valeur fait recalculer les triggers qui utilisent l'item. Syntaxe actuelle (depuis Zabbix 5.4) : fonction(/hôte/clé,paramètres), par exemple last(/SRV-FILE01/vfs.fs.size[C:,pfree])<10. Dans un template, l'hôte est remplacé par le nom du template, et le seuil par une macro {$…} modifiable par hôte.

    Le trigger est une expression vraie ou fausse, évaluée par le serveur — jamais par l'agent.

  4. Étape 4 · serveur

    Le problème s'ouvre

    L'expression devient vraie : le trigger passe de OK à PROBLEM et génère un événement. Le problème s'affiche dans Monitoring → Problems et sur le tableau de bord, avec sa sévérité et ses tags.

    Changement d'état = événement ; un événement de problème = une ligne dans Problems.

  5. Étape 5 · serveur

    Une action correspond

    Le serveur compare l'événement aux Trigger actions (Alerts → Actions) : groupe d'hôtes, sévérité, nom ou valeur de tag. Si aucune condition ne correspond, il ne se passe rien d'autre — le problème reste seulement affiché.

    L'action est un filtre : conditions vraies → opérations lancées.

  6. Étape 6 · serveur → destinataire ou agent

    Les opérations s'exécutent

    Envoyer un message à un utilisateur ou à un groupe par un type de média (e-mail, Teams, SMS…), ou lancer un script sur l'agent ou le serveur. Les macros comme {HOST.NAME} ou {TRIGGER.NAME} sont remplacées par leurs valeurs. Le résultat se lit dans Reports → Action log.

    Une notification n'arrive que si l'utilisateur a un média configuré et les droits sur l'hôte.

  7. Étape 7 · serveur

    Le retour à la normale

    Après nettoyage, l'espace libre repasse au-dessus du seuil : l'expression redevient fausse, un événement OK ferme le problème, et les opérations de rétablissement de l'action (par exemple « Resolved: … ») partent.

    Un problème se ferme tout seul quand la condition disparaît ; l'acquittement (Acknowledge) sert seulement à dire « je m'en occupe ».

  1. 01
    Autoriser les commandes distantes sur l'agentAjouter AllowKey=system.run[*] dans zabbix_agentd.conf, puis redémarrer le service Zabbix Agent. Par défaut l'agent refuse toute commande system.run.
  2. 02
    Cloner le trigger prototypeData collection → Hosts → SRV-FILE01 → Discovery → Windows services discovery → Trigger prototypes, sélectionner celui qui dit … is not running et le cloner.
  3. 03
    Adapter le cloneDescription : {#SERVICE.NAME} et rien d'autre. Tags : tag type, valeur WinService.
  4. 04
    Créer le scriptAlerts → Scripts → Create script : scope Action operation, type Script, Execute on Zabbix agent, commande net start "{TRIGGER.DESCRIPTION}".
  5. 05
    Créer l'actionAlerts → Actions → Trigger actions : condition Tag value type equals WinService ; opération = le script, sur le groupe d'hôtes Virtual machines.

Deux pièges, toujours les mêmes

La description du trigger doit contenir le nom court du service et rien d'autre : c'est elle que le script récupère via {TRIGGER.DESCRIPTION} pour former une commande valide — d'où les guillemets, qui sauvent les noms de service contenant des espaces. Et la valeur du tag doit être écrite à l'identique dans le trigger et dans la condition de l'action : WinService d'un côté et winservice de l'autre, et l'action ne se déclenche jamais.

Bonus — nettoyer les fichiers temporaires

Un fichier C:\Scripts\cleanup_temp.bat créé au Bloc-notes (le passer par un here-string PowerShell depuis cmd ne fonctionne pas) :

cleanup_temp.bat
del /q /f /s "%TEMP%\*"
del /q /f /s "C:\Windows\Temp\*"

rem /q pas de confirmation · /f force les fichiers en lecture seule · /s sous-dossiers

Puis un item planifié sur l'hôte — Items → Create item — de type Zabbix agent, clé system.run[C:\Scripts\cleanup_temp.bat,nowait], type d'information Text, update interval 0 et un intervalle personnalisé Scheduling h3 (tous les jours à 3 h 00).

Exercice 2 — pourquoi 0 et nowait ?

L'item est réglé avec un update interval à 0 et la clé se termine par ,nowait. Que se passerait-il sans l'un et sans l'autre ?

Afficher la correction

Sans 0 : l'item garderait son interrogation régulière (une minute par défaut) en plus de la planification. Le nettoyage tournerait donc toutes les minutes au lieu d'une fois par nuit. Mettre l'intervalle à 0 désactive la collecte périodique : l'item ne s'exécute plus que selon le Scheduling h3.

Sans nowait : l'agent attendrait la fin du script avant de rendre la main. Un nettoyage un peu long dépasserait le délai d'attente et l'item passerait en erreur — alors que le script, lui, aurait bien tourné. nowait lance la commande et rend la main immédiatement.

Dans les deux cas l'item dépend aussi de AllowKey=system.run[*] posé à l'étape 01 : sans lui, l'agent refuse, quel que soit le réglage.

À retenir

AllowKey=system.run[*] autorise toutes les commandes : pratique en labo, à restreindre en production (AllowKey=system.run[net start *]). Un serveur de supervision qui peut exécuter n'importe quoi sur tout le parc est une cible de choix — l'auto-remédiation se paie en surface d'attaque, et se limite donc à ce dont elle a besoin.

Question éclair

Le service Spooler s'arrête : le problème apparaît bien dans Problems, mais le service ne redémarre pas et Reports → Action log est vide. Où regardes-tu ?

Un Action log vide veut dire qu'aucune action n'a correspondu à l'événement : l'étape 5 du pas à pas a échoué. Compare le tag du trigger (type = WinService) et la condition de l'action, au caractère près. Un refus de l'agent, lui, laisserait une ligne en échec dans le journal.

S'entraîner : la pastille ZBX et l'agent

Neuf fois sur dix, une supervision qui ne remonte rien vient de la relation entre l'agent et le serveur : qui parle à qui, sur quel port, sous quel nom. Ce chapitre en fait un réflexe.

ModeQui ouvre la connexionPortRéglage de l'agent qui doit concorder
PassifLe serveur interroge l'agentTCP 10050 (sur l'agent)Server= doit contenir l'adresse du serveur
ActifL'agent envoie au serveurTCP 10051 (sur le serveur)ServerActive= = le serveur, et Hostname= = le nom de l'hôte exactement comme dans l'interface

Vérifier

Le serveur obtient-il une réponse de l'agent ?

bash — sur le serveur Zabbix
zabbix_get -s 172.16.50.20 -k agent.ping

Sortie attendue

1

Connection refused : l'agent n'écoute pas (service arrêté). La commande attend puis échoue sur un délai dépassé : le pare-feu de l'hôte bloque 10050 (le pare-feu Windows ignore la demande sans répondre). Check access restrictions in Zabbix agent configuration : l'agent refuse la connexion, l'adresse du serveur n'est pas dans Server=. Ça marche ici mais la pastille reste rouge : l'interface de l'hôte dans Zabbix pointe vers une autre adresse.

À toi de taper

Sur SRV-FILE01, redémarre l'agent Zabbix installé dans ce module (l'agent 1, service Zabbix Agent) après une modification de sa configuration.

Voir la solution

Restart-Service "Zabbix Agent" — guillemets obligatoires, le nom contient une espace. Une modification de zabbix_agentd.conf (comme AllowKey ou un UserParameter) n'est lue qu'au démarrage. Avec l'agent 2, le service s'appelle Zabbix Agent 2 et le fichier zabbix_agent2.conf.

Scénario de panne

Les données « actives » n'arrivent pas

Un nouveau serveur est déclaré dans Zabbix sous le nom SRV-FILE01. Les éléments passifs remontent, mais tous les éléments en vérification active restent vides.

Qu'est-ce que ce symptôme élimine ?

Reste ce qui ne concerne que l'actif : ServerActive= et Hostname=.

Le journal de l'agent dit : host [srv-file01] not found. La cause ?

L'agent annonce srv-file01, le serveur attend SRV-FILE01 : pour lui, cet hôte n'existe pas.

Correction : Hostname=SRV-FILE01 dans la configuration de l'agent, puis redémarrer l'agent. Les données actives arrivent dès que l'agent a rechargé sa liste de vérifications actives.

À retenir

Passif : serveur → agent:10050, autorisé par Server=. Actif : agent → serveur:10051, identifié par Hostname= au caractère près. zabbix_get depuis le serveur tranche en une commande.
