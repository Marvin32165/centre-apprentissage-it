01

Concepts & rôles RDS

RDS (Remote Desktop Services) déporte l'exécution sur le serveur : le poste client n'affiche qu'une image. Le rôle se découpe en plusieurs services de rôle qui collaborent.

RôleSigleFonction
Session HostRDSHExécute réellement les sessions et les applications des utilisateurs
Connection BrokerRDCBRépartit les connexions, gère les collections et la reconnexion aux sessions
Web AccessRDWAPortail web : l'utilisateur voit ses bureaux et RemoteApp publiés dans le navigateur
GatewayRD GatewayPasserelle sécurisée (HTTPS) pour accéder au RDS depuis Internet sans VPN
LicensingRD LicensingGère les licences d'accès client (RDS CAL)

Session-based vs VDI

Session-based (RDSH)

  • Plusieurs utilisateurs partagent un même serveur.
  • Léger, économique, idéal pour applications métier.
  • Le déploiement de ce labo.

VDI (bureaux virtuels)

  • Une VM complète par utilisateur.
  • Isolation maximale, plus gourmand.
  • Pour postes personnalisés / lourds.

À retenir

Le trio de base : RDSH exécute, RDCB répartit, RDWA publie. La Gateway ajoute l'accès sécurisé depuis l'extérieur. En session-based, plusieurs utilisateurs se partagent un serveur — c'est le modèle le plus courant.

02

Topologie du labo

L'environnement orion.local (réseau 192.168.1.x) : un contrôleur de domaine, deux Session Hosts pour la redondance, un Broker, un Web Access et un client.

DC192.168.1.10Contrôleur de domaine + DNS
RDSH1192.168.1.11Session Host n°1
RDSH2192.168.1.12Session Host n°2 (redondance / charge)
RDCB192.168.1.13Connection Broker
RDWA192.168.1.14Web Access — portail rdwa.orion.local
CLIENT192.168.1.15Poste de test

À retenir

Le plan d'adressage se lit comme l'architecture : un rôle par machine, et deux Session Hosts — parce que c'est là que s'exécute le travail des utilisateurs, donc là que la panne se voit. Le Broker, lui, est unique : c'est le point de passage de toutes les connexions, donc la machine à surveiller en premier.

03

Déploiement session-based

Le déploiement se pilote depuis le Server Manager du contrôleur de domaine, qui orchestre l'installation des rôles sur les serveurs distants en une seule passe.

  1. 01
    Ajouter les serveurs au poolSur le DC : Manage → Add Servers, sélectionner les 3 VM (RDSH, RDCB, RDWA).
  2. 02
    Lancer l'installation RDSManage → Add Roles and Features → Remote Desktop Services installation → Standard deployment → Session-based.
  3. 03
    Affecter les rôlesDésigner chaque serveur pour son rôle (RDSH = Session Host, RDCB = Connection Broker, RDWA = Web Access), puis Deploy.
  4. 04
    Vérifier la vue d'ensembleDans Remote Desktop Services → Overview, le schéma du déploiement doit afficher les trois rôles au vert.

Astuce

Tous les serveurs doivent être membres du domaine et visibles dans le pool avant de lancer le déploiement. Le Broker (RDCB) est le point d'orchestration : c'est lui qui « connaît » toute la ferme RDS.

04

Collections & RemoteApp

Une collection de sessions regroupe un ou plusieurs Session Hosts et définit qui y a accès. On y publie ensuite soit un bureau complet, soit des RemoteApp (applications isolées qui s'ouvrent comme des fenêtres locales).

  1. 01
    Créer la collectionRemote Desktop Services → Collections → Tasks → Create Session Collection. Nom : Collection1, choisir les Session Hosts, valider les groupes d'utilisateurs autorisés. Décocher l'option de disques de profil utilisateur si non nécessaire, puis Create.
  2. 02
    Publier des RemoteAppDans la collection : Tasks → Publish RemoteApp Programs, sélectionner les applications à exposer (ex. WordPad, une appli métier).
  3. 03
    Tester côté clientLe client ouvre https://rdwa.orion.local/RDWeb, s'authentifie et lance la RemoteApp — elle s'affiche comme une fenêtre locale.

À retenir

Bureau complet ou RemoteApp : la collection est l'unité de publication et de contrôle d'accès. La RemoteApp donne l'illusion d'une application locale alors qu'elle s'exécute sur le RDSH — idéal pour distribuer une seule appli métier sans publier tout le bureau.

05

Certificat du Web Access

Le portail RD Web Access est servi en HTTPS : il lui faut un certificat. En labo, on en génère un auto-signé pour le nom rdwa.orion.local (en production, on le ferait signer par la CA d'entreprise — voir le module Sécurité / PKI).

PowerShell — sur RDWA
# Certificat auto-signé pour le portail Web Access
New-SelfSignedCertificate -DnsName "rdwa.orion.local" `
    -CertStoreLocation "cert:\LocalMachine\My" `
    -NotAfter (Get-Date).AddYears(2) `
    -KeyLength 4096 -KeyExportPolicy Exportable `
    -FriendlyName "RDWA"

# Puis : certlm.msc → Personal → Certificates pour le consulter/exporter

Labo vs production

Un certificat auto-signé déclenche une alerte sur le client (chaîne de confiance non remontée). En production, on déploie un certificat signé par la CA d'entreprise et distribué par GPO — la même logique de PKI que pour Exchange.

Auto-évaluation

Teste-toi

Réponds de tête — à voix haute si possible — avant de déplier la correction. Une question qui bloque désigne le chapitre à relire : son numéro est rappelé avec la réponse.

  1. Que font respectivement RDSH, RDCB et RDWA ?

    Voir la réponse

    RDSH (Session Host) exécute réellement les sessions et les applications ; RDCB (Connection Broker) répartit les connexions, gère les collections et la reconnexion ; RDWA (Web Access) publie le portail web où l'utilisateur voit ses bureaux et RemoteApp. Chapitre 01.

  2. Quel service de rôle permet d'atteindre le RDS depuis Internet sans VPN ?

    Voir la réponse

    La RD Gateway : une passerelle qui encapsule le trafic RDP en HTTPS. Chapitre 01.

  3. Session-based ou VDI : quelle différence, et lequel pour distribuer une application métier ?

    Voir la réponse

    En session-based, plusieurs utilisateurs partagent un même serveur — léger et économique : c'est le bon choix pour une appli métier. En VDI, chacun a sa VM complète — isolation maximale, mais bien plus gourmand. Chapitre 01.

  4. Que faut-il avoir fait avant de lancer le déploiement RDS depuis le Server Manager ?

    Voir la réponse

    Tous les serveurs doivent être membres du domaine et ajoutés au pool (Manage → Add Servers). Le Broker est le point d'orchestration : c'est lui qui « connaît » toute la ferme. Chapitre 03.

  5. Où s'exécute réellement une RemoteApp, et pourquoi l'utilisateur ne s'en rend-il pas compte ?

    Voir la réponse

    Sur le RDSH : seul l'affichage est renvoyé au client, dans une fenêtre qui se comporte comme une application locale. D'où l'intérêt pour publier une seule appli sans exposer tout le bureau. Chapitre 04.

  6. Pourquoi le portail https://rdwa.orion.local/RDWeb déclenche-t-il une alerte en labo ?

    Voir la réponse

    Le certificat est auto-signé : sa chaîne ne remonte à aucune racine de confiance du client. En production, on le fait signer par la CA d'entreprise et on distribue la racine par GPO. Chapitre 05.

Les sigles du module

Le vocabulaire à savoir traduire sans hésiter — si l'un d'eux ne te dit rien, le chapitre correspondant mérite une relecture.

RDSRemote Desktop Services — le rôle Windows Server qui déporte l'exécution des sessions et des applications sur le serveur.
RDSHRemote Desktop Session Host — le serveur qui exécute réellement les sessions et les applications.
RDCBRemote Desktop Connection Broker — répartit les connexions, gère les collections et la reconnexion aux sessions.
RDWARemote Desktop Web Access — le portail web où l'utilisateur retrouve ses bureaux et RemoteApp publiés.
RD GatewayPasserelle qui encapsule le RDP en HTTPS pour un accès depuis Internet, sans VPN.
RDS CALClient Access License — la licence d'accès client, gérée par le rôle RD Licensing.
VDIVirtual Desktop Infrastructure — une VM complète par utilisateur, par opposition au session-based.
RemoteAppApplication publiée seule : elle s'exécute sur le RDSH mais s'affiche comme une fenêtre locale.
CollectionL'unité de publication et de contrôle d'accès : un ou plusieurs Session Hosts + les groupes autorisés.
