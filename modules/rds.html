Ce que tu sauras faire à la fin

  • Nommer chaque service de rôle RDS et dire ce qu'il fait, et choisir entre session-based et VDI.
  • Déployer un RDS session-based sur quatre serveurs, depuis le Server Manager ou en PowerShell, et le vérifier.
  • Créer une collection, y publier des RemoteApp et voir qui est connecté où.
  • Configurer les licences avant la fin des 120 jours de grâce.
  • Créer, affecter et faire approuver le certificat du déploiement, et expliquer le rôle de la passerelle.

Prérequis : Windows Server (le domaine Orion). La partie certificats se comprend mieux après Exchange & PKI.

Le plan des machines est celui du lab Orion.

01

Les rôles RDS

RDS (Remote Desktop Services) déporte l'exécution sur le serveur : le poste client n'affiche qu'une image. Le rôle se découpe en services de rôle, chacun sur sa machine dans un déploiement propre.

Service de rôleSigleCe qu'il fait
Session HostRDSHExécute réellement les sessions et les applications des utilisateurs
Connection BrokerRDCBRépartit les connexions entre hôtes, reconnecte un utilisateur à sa session, porte la configuration du déploiement
Web AccessRDWAPortail web (/RDWeb) qui liste les bureaux et RemoteApp publiés
GatewayRDGFait passer RDP dans HTTPS (443) pour un accès depuis Internet, sans VPN
LicensingRDLDélivre les licences d'accès client (RDS CAL) — obligatoires après 120 jours

Session-based (RDSH)

Plusieurs utilisateurs partagent un même serveur Windows Server. Léger, économique : le modèle le plus courant, et celui du lab.

VDI

Une VM Windows complète par utilisateur. Isolation maximale, coûteux en ressources ; pour des postes très personnalisés.

À retenir

RDSH exécute, RDCB répartit et retient, RDWA publie, la Gateway ouvre l'accès externe, le Licensing délivre les CAL. En session-based, plusieurs utilisateurs partagent un serveur.

Question éclair

Le Wi-Fi d'une utilisatrice coupe en pleine saisie. Elle se reconnecte et retrouve sa session ouverte, sur le même hôte que tout à l'heure, alors qu'il y en a deux. Quel service de rôle a fait ça ?

Le broker garde la trace de chaque session : à la reconnexion, il renvoie l'utilisatrice vers l'hôte qui détient sa session déconnectée, au lieu d'en ouvrir une nouvelle ailleurs. Get-RDUserSession l'interroge.

02

Le déploiement sur le lab Orion

Le TP du cours monte un déploiement standard : un contrôleur de domaine qui orchestre, deux hôtes de session pour la redondance, un broker et un accès web. Transposé sur le lab Orion :

SRV-AD01172.16.50.10Contrôleur de domaine + DNS — on y pilote le déploiement depuis le Server Manager
SRV-RDSH1172.16.50.51Hôte de session n° 1
SRV-RDSH2172.16.50.52Hôte de session n° 2 (redondance, répartition)
SRV-RDCB172.16.50.53Connection Broker (et serveur de licences dans le lab)
SRV-RDWA172.16.50.54Web Access — portail https://rdwa.orion.local/RDWeb
CLIENT-WIN11DHCPPoste de test

Les quatre serveurs RDS sont membres du domaine, et leur DNS pointe vers les DC. Le nom rdwa.orion.local est un alias (CNAME) vers srv-rdwa.orion.local : c'est ce nom-là que les utilisateurs taperont, et celui que devra porter le certificat (chapitre 06).

À retenir

Un rôle par machine, deux hôtes de session parce que c'est là que la panne se voit. Le broker est le point de passage de toutes les connexions : c'est la machine à surveiller (et à doubler en production).

03

Déployer en session-based

Le déploiement se pilote depuis un seul serveur, qui installe les rôles sur les autres en une passe. Dans le TP, c'est le Server Manager de SRV-AD01 ; la même chose existe en PowerShell.

1
Ajouter les serveurs au pool

Sur SRV-AD01 : Manage → Add Servers, ajouter SRV-RDSH1, SRV-RDSH2, SRV-RDCB et SRV-RDWA.

2
Lancer l'installation RDS

Manage → Add Roles and Features → Remote Desktop Services installation → Standard deployment → Session-based desktop deployment.

3
Affecter les rôles

RD Connection Broker = SRV-RDCB, RD Web Access = SRV-RDWA, RD Session Host = SRV-RDSH1 et SRV-RDSH2. Cocher Restart the destination server automatically if required, puis Deploy.

4
Contrôler

Remote Desktop Services → Overview : le schéma montre les rôles installés.

PowerShell — le même déploiement (sur SRV-AD01, module RemoteDesktop)
New-RDSessionDeployment -ConnectionBroker srv-rdcb.orion.local `
-WebAccessServer srv-rdwa.orion.local `
-SessionHost srv-rdsh1.orion.local, srv-rdsh2.orion.local

Vérifier

Quels serveurs portent quels rôles ?

PowerShell
Get-RDServer -ConnectionBroker srv-rdcb.orion.local

Sortie attendue

Server                 Roles
------                 -----
srv-rdcb.orion.local   {RDS-CONNECTION-BROKER}
srv-rdwa.orion.local   {RDS-WEB-ACCESS}
srv-rdsh1.orion.local  {RDS-RD-SERVER}
srv-rdsh2.orion.local  {RDS-RD-SERVER}

Le déploiement échoue sur un serveur : il n'est pas joignable par WinRM depuis SRV-AD01, ou pas dans le pool. Les serveurs doivent être membres du domaine et visibles dans le Server Manager avant de lancer l'assistant.

À toi de taper

Écris la commande qui déploie le RDS session-based du lab, en une seule ligne : broker srv-rdcb.orion.local, Web Access srv-rdwa.orion.local, hôtes de session srv-rdsh1.orion.local et srv-rdsh2.orion.local. Les noms complets (FQDN) sont exigés.

Voir la solution

New-RDSessionDeployment -ConnectionBroker srv-rdcb.orion.local -WebAccessServer srv-rdwa.orion.local -SessionHost srv-rdsh1.orion.local,srv-rdsh2.orion.local. Les trois paramètres sont nommés : ils peuvent venir dans n'importe quel ordre. Sans noms, les valeurs se lisent par position : broker, hôtes de session, Web Access. Les trois attendent des noms complets (FQDN) ; -SessionHost accepte une liste, séparée par des virgules ou écrite @("…","…").

À retenir

Un seul point de pilotage, quatre rôles sur quatre serveurs, et Get-RDServer pour vérifier qui fait quoi. La plupart des commandes *-RD* visent le broker (-ConnectionBroker) : c'est lui qui détient la configuration.

04

Collections et RemoteApp

Une collection regroupe des hôtes de session et dit qui y a accès. On y publie soit des bureaux complets, soit des RemoteApp : des applications isolées qui s'ouvrent comme des fenêtres locales.

1
Créer la collection

Remote Desktop Services → Collections → Tasks → Create Session Collection : nom Collection1, les deux hôtes de session, les groupes d'utilisateurs autorisés. Décocher les disques de profil utilisateur (User Profile Disks) si on n'en a pas besoin.

2
Publier des RemoteApp

Dans la collection : Tasks → Publish RemoteApp Programs, cocher les applications.

3
Tester

Depuis le client : https://rdwa.orion.local/RDWeb, s'authentifier, lancer la RemoteApp.

PowerShell — la collection et une RemoteApp
New-RDSessionCollection -CollectionName "Collection1" `
    -SessionHost srv-rdsh1.orion.local, srv-rdsh2.orion.local -ConnectionBroker srv-rdcb.orion.local
New-RDRemoteApp -CollectionName "Collection1" -DisplayName "Bloc-notes" `
    -FilePath "C:\Windows\System32\notepad.exe" -ConnectionBroker srv-rdcb.orion.local

WordPad n'existe plus

Les supports de cours publient souvent WordPad en exemple. Il a été retiré de Windows Server 2025 (et de Windows 11 24H2) : sur un hôte de session 2025, publier le Bloc-notes, la calculatrice ou une vraie application métier.

Vérifier

Qui est connecté, et où ?

PowerShell
Get-RDUserSession -ConnectionBroker srv-rdcb.orion.local

Sortie attendue

CollectionName  DomainName  UserName  HostServer             SessionState
--------------  ----------  --------  ----------             ------------
Collection1     ORION       sso       srv-rdsh1.orion.local  STATE_ACTIVE

Un utilisateur ne voit rien dans le portail : il n'est pas dans le groupe autorisé de la collection. Une RemoteApp ne s'ouvre pas : le programme n'existe pas au même chemin sur tous les hôtes de la collection.

À toi de taper

Écris la commande qui crée la collection Collection1, en une seule ligne, avec les hôtes de session srv-rdsh1.orion.local et srv-rdsh2.orion.local, et le broker srv-rdcb.orion.local.

Voir la solution

New-RDSessionCollection -CollectionName "Collection1" -SessionHost srv-rdsh1.orion.local,srv-rdsh2.orion.local -ConnectionBroker srv-rdcb.orion.local. -SessionHost n'a pas de position : il se nomme toujours. Le nom de la collection, lui, est le premier paramètre positionnel : New-RDSessionCollection "Collection1" -SessionHost … est donc équivalent.

À retenir

La collection est l'unité de publication et de contrôle d'accès. Une RemoteApp doit être installée à l'identique sur tous les hôtes de session de sa collection.

Question éclair

La RemoteApp « Compta » s'ouvre pour certains utilisateurs et affiche une erreur pour d'autres. Get-RDUserSession montre que les erreurs viennent toutes de SRV-RDSH2. Cause probable ?

Le broker répartit les utilisateurs entre les hôtes de la collection : une RemoteApp doit exister au même chemin sur chacun. Installer l'application sur SRV-RDSH2 (en mode installation : change user /install, puis change user /execute), ou la retirer de la collection en attendant.

05

Les licences RDS

Un déploiement RDS fonctionne sans licence… pendant 120 jours. C'est la période de grâce : ensuite, les connexions sont refusées tant qu'un serveur de licences activé ne délivre pas de CAL (Client Access License).

Complément au TP — le TP du cours s'arrête avant les licences ; ce chapitre suit la documentation Microsoft. Dans un lab, la période de grâce suffit, mais il faut savoir que le compteur tourne.

Par utilisateur (Per User)

Une CAL par personne, quel que soit le nombre d'appareils. Le bon choix quand chacun se connecte depuis plusieurs postes, ou depuis chez lui. Demande un domaine AD ; le serveur de licences compte les CAL attribuées mais ne bloque pas : rester en règle est ta responsabilité.

Par périphérique (Per Device)

Une CAL par appareil, quel que soit le nombre de personnes. Pour des postes partagés en équipes (accueil, atelier). À la première connexion, l'appareil reçoit une CAL temporaire de 90 jours, remplacée par une permanente s'il en reste ; ce mode-là est réellement contrôlé.

PowerShell — ajouter le rôle de licences et régler le mode
Add-RDServer -Server srv-rdcb.orion.local -Role RDS-LICENSING -ConnectionBroker srv-rdcb.orion.local
Set-RDLicenseConfiguration -LicenseServer srv-rdcb.orion.local -Mode PerUser -ConnectionBroker srv-rdcb.orion.local
# puis : activer le serveur de licences et installer les CAL (console RD Licensing Manager)

Vérifier

Combien de jours de grâce reste-t-il ?

PowerShell (administrateur) — sur un hôte de session
$ts = Get-CimInstance -Namespace root/CIMV2/TerminalServices -ClassName Win32_TerminalServiceSetting
Invoke-CimMethod -InputObject $ts -MethodName GetGracePeriodDays

Sortie attendue

DaysLeft ReturnValue
-------- -----------
     117           0

Le Server Manager affiche « The licensing mode for the Remote Desktop Session Host server is not configured » : le mode et le serveur de licences ne sont pas réglés (Set-RDLicenseConfiguration).

Piège : la version des CAL

Une CAL donne accès aux hôtes de sa version ou d'une version antérieure : des hôtes de session Windows Server 2025 demandent des CAL RDS 2025. Et le serveur de licences doit être de la même version que les CAL qu'il délivre, ou plus récent. On met donc à jour le serveur de licences avant les hôtes. Pour administrer un serveur sans le rôle RDSH, aucune CAL n'est nécessaire : Windows Server accepte deux connexions d'administration simultanées.

À retenir

120 jours de grâce, puis plus de connexion sans CAL. Choisir Per User ou Per Device selon l'usage, désigner le serveur de licences, et l'activer. Dans un lab, on note la date de fin de grâce.

Question éclair

Un atelier a 3 postes partagés par 30 ouvriers en trois équipes, qui n'utilisent jamais d'autre appareil. Quelles CAL achètes-tu ?

On compte ce qui est le moins nombreux : 3 appareils contre 30 personnes. Mode PerDevice : Set-RDLicenseConfiguration -Mode PerDevice -LicenseServer srv-rdcb.orion.local -ConnectionBroker srv-rdcb.orion.local. Le jour où les ouvriers se connectent de chez eux, le calcul s'inverse.

06

Le certificat : le créer, l'affecter, le faire accepter

Le portail Web Access et les connexions RDP sont chiffrés en TLS : il leur faut un certificat au nom que tapent les utilisateurs. Le TP en crée un auto-signé. Il reste deux étapes que l'on oublie : l'affecter au déploiement, et le faire reconnaître par les clients.

PowerShell — sur SRV-RDCB : créer (TP du cours), exporter, affecter
$cert = New-SelfSignedCertificate -DnsName "rdwa.orion.local" -CertStoreLocation "Cert:\LocalMachine\My" `
    -NotAfter (Get-Date).AddYears(2) -KeyLength 4096 -KeyExportPolicy Exportable -FriendlyName "RDS"
$mdp = Read-Host -AsSecureString "Mot de passe du PFX"
Export-PfxCertificate -Cert $cert -FilePath "C:\Lab\rds.pfx" -Password $mdp
Export-Certificate -Cert $cert -FilePath "C:\Lab\rds.cer"   # partie publique, pour les clients
foreach ($role in "RDWebAccess", "RDPublishing", "RDRedirector") {
    Set-RDCertificate -Role $role -ImportPath "C:\Lab\rds.pfx" -Password $mdp -ConnectionBroker srv-rdcb.orion.local -Force
}

Le même réglage existe dans l'interface : Overview → Tasks → Edit Deployment Properties → Certificates, un rôle à la fois. Tant que cette étape n'est pas faite, le portail continue de présenter son certificat par défaut, même si le nouveau est dans le magasin.

Que le client fasse confiance

Un certificat auto-signé n'est garanti par personne : le client affiche une alerte. Pour un lab, on importe le certificat public (.cer) dans les Autorités de certification racines de confiance des postes, à la main (Import-Certificate -FilePath rds.cer -CertStoreLocation Cert:\LocalMachine\Root) ou mieux par GPO (Computer Configuration → Policies → Windows Settings → Security Settings → Public Key Policies → Trusted Root Certification Authorities). En production, on demande le certificat à l'autorité de certification d'entreprise (module Exchange & PKI) : tous les postes du domaine lui font déjà confiance.

Vérifier

Le portail présente-t-il le bon certificat ?

PowerShell
Get-RDCertificate -ConnectionBroker srv-rdcb.orion.local

Sortie attendue

Role          Level          ExpiresOn   IssuedTo
----          -----          ---------   --------
RDRedirector  Untrusted      …           CN=rdwa.orion.local
RDPublishing  Untrusted      …           CN=rdwa.orion.local
RDWebAccess   Untrusted      …           CN=rdwa.orion.local
RDGateway     NotConfigured

Untrusted est normal ici : c'est le niveau que Microsoft attribue à un certificat auto-signé. Avec un certificat de la CA d'entreprise ou d'une autorité publique, la colonne affiche Trusted. NotConfigured : aucun certificat valide pour ce rôle.

Un rôle toujours en NotConfigured : Set-RDCertificate n'a pas été passé pour lui. Alerte « le nom ne correspond pas » : l'utilisateur tape un nom qui n'est pas dans le certificat (srv-rdwa au lieu de rdwa). Alerte « non approuvé » : le certificat n'est pas dans les racines de confiance du poste.

Un certificat, plusieurs noms

Les rôles RDRedirector et RDPublishing sont portés par le broker : le client y voit le nom srv-rdcb.orion.local. Un certificat qui ne porte que rdwa.orion.local peut donc encore déclencher une alerte de nom à la connexion. Plus propre : un certificat qui porte les deux noms, par exemple New-SelfSignedCertificate -DnsName "rdwa.orion.local", "srv-rdcb.orion.local" …

À retenir

Un certificat RDS se crée au bon nom, s'affecte aux rôles (Set-RDCertificate) et doit être reconnu par les clients (racine de confiance par GPO, ou CA d'entreprise). Sans les deux dernières étapes, l'alerte reste.

Question éclair

Le certificat est affecté et approuvé par GPO. Pourtant, un utilisateur qui ouvre https://srv-rdwa.orion.local/RDWeb reçoit une alerte. Pourquoi ?

Le certificat ne porte que rdwa.orion.local. Le navigateur compare le nom tapé à ceux du certificat : srv-rdwa n'y est pas. Donner aux utilisateurs l'adresse https://rdwa.orion.local/RDWeb (un raccourci, un favori par GPO), ou ajouter le nom au certificat.

07

Accéder de l'extérieur : la passerelle

Ouvrir le port 3389 sur Internet est l'une des premières causes de compromission : les robots le scannent en permanence. La passerelle RD fait passer RDP dans HTTPS, sur le port 443, avec une authentification avant même d'atteindre un serveur.

Complément au TP — non déployé en séance ; principes issus de la documentation Microsoft.

1
Le rôle

Add-RDServer -Server srv-rdwa.orion.local -Role RDS-GATEWAY -ConnectionBroker srv-rdcb.orion.local -GatewayExternalFqdn rds.exemple.be : souvent sur le même serveur que le Web Access, en DMZ.

2
Les stratégies

CAP (Connection Authorization Policy) : qui a le droit de passer. RAP (Resource Authorization Policy) : vers quels serveurs.

3
Le certificat

Public cette fois (nom externe, autorité reconnue par tous les clients), affecté au rôle RDGateway.

4
L'exposition

Seul le port 443 (TCP) est publié vers la passerelle — plus, en option, 3391 (UDP) pour le transport UDP, plus fluide ; s'il est fermé, la passerelle se contente de 443. 3389 n'est jamais ouvert sur Internet.

Pas à pas

De l'URL RDWeb à la RemoteApp à l'écran

  1. Étape 1 · Navigateur → SRV-RDWA (HTTPS, 443)

    Le portail

    L'utilisateur ouvre https://rdwa.orion.local/RDWeb et s'authentifie avec son compte du domaine. Le serveur présente le certificat du rôle RDWebAccess.

    Première vérification du certificat : nom et confiance.

  2. Étape 2 · SRV-RDWA → SRV-RDCB

    La liste des ressources

    Le Web Access demande au broker les bureaux et RemoteApp publiés dans les collections auxquelles l'utilisateur a droit (par ses groupes), et les affiche.

    Une ressource absente ici = un problème de groupe autorisé sur la collection.

  3. Étape 3 · SRV-RDWA → navigateur

    Le fichier .rdp

    Un clic télécharge un petit fichier .rdp, signé avec le certificat RDPublishing. Il contient l'adresse du broker, la collection visée et, si elle est configurée, celle de la passerelle. Le client Bureau à distance (mstsc) l'ouvre.

    La signature permet au client de savoir qui a publié la ressource.

  4. Étape 4 · mstsc → passerelle (HTTPS 443, UDP 3391)

    Depuis l'extérieur seulement : la passerelle

    Le client ouvre un tunnel HTTPS vers la passerelle, s'y authentifie ; la passerelle vérifie la CAP (cet utilisateur peut-il passer ?) puis la RAP (vers ce serveur ?). Sur le réseau interne, le client saute cette étape.

    Seul 443 est exposé ; RDP voyage à l'intérieur du tunnel.

  5. Étape 5 · mstsc → SRV-RDCB (RDP, 3389)

    Le broker choisit l'hôte

    Le broker regarde si l'utilisateur a déjà une session déconnectée dans la collection : si oui, il le renvoie vers cet hôte ; sinon, vers l'hôte le moins chargé. Le client est redirigé (rôle RDRedirector).

    Reconnexion et répartition de charge se décident ici.

  6. Étape 6 · mstsc → SRV-RDSH1 (RDP, 3389) ; SRV-RDSH1 → serveur de licences

    La session s'ouvre

    L'hôte de session ouvre la session de l'utilisateur et s'adresse au serveur de licences : CAL par périphérique délivrée (ou temporaire), ou CAL par utilisateur comptée. Tant que court la période de grâce, l'absence de serveur de licences n'empêche pas la connexion.

    Après 120 jours sans serveur de licences configuré, c'est ici que la connexion est refusée.

  7. Étape 7 · SRV-RDSH1 → poste

    La RemoteApp à l'écran

    L'application tourne sur SRV-RDSH1 ; le poste n'affiche que sa fenêtre, comme une application locale. Fermer la dernière RemoteApp ferme en principe la session ; une coupure réseau la laisse déconnectée sur l'hôte, prête à être reprise à l'étape 5.

    Le calcul est sur le serveur, l'affichage sur le poste.

À retenir

Jamais de 3389 ouvert sur Internet : la passerelle RD encapsule RDP dans HTTPS (443), filtre par CAP et RAP, et présente un certificat public. Ajouter une MFA sur la passerelle est la mesure suivante.

Question éclair

Le directeur veut ouvrir sa RemoteApp depuis chez lui. Un collègue propose de rediriger le port 3389 du pare-feu vers SRV-RDCB, avec un mot de passe solide. Que réponds-tu ?

Exposer RDP directement, même sur un autre port, laisse n'importe qui sur Internet tenter sa chance. La passerelle RD n'expose que HTTPS, authentifie avant d'atteindre un serveur, filtre par CAP et RAP, et peut recevoir une MFA.
