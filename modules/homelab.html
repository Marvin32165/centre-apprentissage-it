Ce que tu sauras faire à la fin

  • Décrire une stack Docker Compose propre : image, conteneur, volume, un dossier par service.

01

C'est quoi, un homelab

Un homelab est un environnement informatique personnel — d'un simple Raspberry Pi à un vieux serveur d'entreprise — sur lequel on apprend, on teste et on héberge ses propres services. C'est le complément idéal des modules Proxmox et Linux.

Pourquoi s'en monter un

  • Apprendre en vrai — rien ne remplace un service qu'on installe, casse et répare soi-même.
  • Reprendre le contrôle de ses données — son cloud, ses médias, ses mots de passe chez soi.
  • Automatiser sa maison — DNS local, domotique, sauvegardes centralisées.
  • Un CV vivant — un homelab documenté vaut mieux qu'une ligne « je connais Docker ».

Le matériel : commencer petit

OptionPour quiAtouts
Raspberry PiDébuter, faible consoSilencieux, ~5 W, parfait pour Pi-hole
Mini-PC (NUC, Tiny)Le meilleur rapportx86, silencieux, tient plein de conteneurs
PC recyclé / tourRécup gratuiteExtensible (RAM, disques), idéal Proxmox
Serveur d'occasionAller loinBeaucoup de RAM/cœurs — mais bruit & conso

À retenir

Un homelab n'a pas besoin d'être gros : un mini-PC ou un vieux PC sous Proxmox suffit pour démarrer. On commence petit, on ajoute des services au fil de l'envie et des besoins.

02

Docker & Compose : la brique de base

Docker empaquette une application et toutes ses dépendances dans un conteneur : ça tourne pareil partout, ça s'installe et se supprime proprement. C'est le format standard du self-hosting moderne.

Image, conteneur, volume

  • Image — le modèle figé d'une appli (ex. nginx:latest).
  • Conteneur — une instance qui tourne, créée à partir d'une image.
  • Volume — le stockage persistant : les données survivent à la suppression du conteneur.

Docker Compose : décrire sa stack en YAML

Plutôt que de longues commandes, on décrit les services dans un fichier docker-compose.yml, versionnable et rejouable (Compose v2 préfère le nom compose.yaml, mais lit les deux). Exemple minimal :

docker-compose.yml
services:
  web:
    image: nginx:latest
    container_name: mon-web
    ports:
      - "8080:80"          # hôte:conteneur
    volumes:
      - ./site:/usr/share/nginx/html:ro
    restart: unless-stopped  # redémarre tout seul
Lancer & gérer la stack
docker compose up -d      # démarrer en arrière-plan
docker compose logs -f    # suivre les journaux
docker compose pull && docker compose up -d  # mettre à jour
docker compose down       # tout arrêter proprement

À toi de taper

Dans le dossier du docker-compose.yml, lance toute la stack en arrière-plan, pour récupérer ton terminal.

Voir la solution

docker compose up -d (ou --detach). Avec -d, les conteneurs tournent en arrière-plan et le terminal est rendu. Sans -d, up reste attaché et affiche les journaux de tous les conteneurs : Ctrl+C arrête alors la stack.

Astuce

Ajoute Portainer pour piloter tes conteneurs depuis une interface web, et Diun pour être averti des nouvelles versions d'images. Méfiance avec les outils qui mettent à jour automatiquement : Watchtower, le plus connu, n'est plus maintenu (dépôt archivé en décembre 2025), et une mise à jour majeure appliquée la nuit peut casser un service sans que tu le saches. Garde chaque service dans son propre dossier avec son docker-compose.yml et un .env.

À retenir

Docker Compose = ta stack décrite dans un fichier .yml versionnable. Volumes pour les données persistantes, restart: unless-stopped pour la résilience, un dossier par service. C'est reproductible et propre.

Question éclair

Tu fais docker compose pull puis docker compose down et up -d sur ta stack Nextcloud. Qu'est-ce qui garantit que tes fichiers sont toujours là ?

Mettre à jour un service Docker, c'est jeter le conteneur et en recréer un depuis la nouvelle image. Seul ce qui est dans un volume ou un bind mount survit — c'est aussi ce qu'il faut sauvegarder.

03

Reverse proxy & HTTPS

Sans reverse proxy, chaque service vit sur un port différent (:8080, :9000…) et sans chiffrement. Un reverse proxy met tout derrière de jolis noms en https:// et gère les certificats automatiquement.

Navigateurhttps://jelly.lab.exemple.beUn nom, un cadenas
Reverse proxy:443Aiguille selon le nom + termine le TLS
Jellyfin:8096Service réel, en HTTP interne
Nextcloud:8080Autre service derrière le même proxy

Quel proxy choisir

  • Nginx Proxy Manager (NPM) — interface web, idéal pour débuter : on ajoute un « proxy host » et on clique pour obtenir un certificat Let's Encrypt.
  • Traefik — puissant, config par labels Docker, auto-découverte des conteneurs. Plus technique.
  • Caddy — minimaliste, HTTPS automatique en une ligne de config.

Pour un certificat valide (cadenas vert) sans exposer le service, on utilise un domaine réel et le challenge DNS de Let's Encrypt : le certificat est émis sans ouvrir de port entrant. C'est le prolongement du module PKI & certificats.

Quel nom de domaine pour la maison ?

Let's Encrypt ne délivre de certificat que pour un domaine public qui t'appartient (ex. lab.exemple.be, des sous-domaines servis seulement par ton DNS local). Pour un nom purement interne, sans certificat public, utilise un suffixe réservé : home.arpa (RFC 8375) ou .internal (réservé par l'ICANN en 2024). .lan ou .local ne sont pas faits pour ça : .local est réservé au mDNS.

À retenir

Un reverse proxy = un point d'entrée unique qui aiguille par nom de domaine et gère le HTTPS. Débute avec Nginx Proxy Manager ; passe à Traefik quand tu veux l'auto-découverte. Certificats via Let's Encrypt (challenge DNS = pas de port à ouvrir).

Question éclair

Ton Nginx Proxy Manager doit obtenir un certificat Let's Encrypt pour jellyfin.home.arpa. La demande échoue. Pourquoi ?

Une autorité publique vérifie que tu contrôles le domaine. Pour home.arpa, personne ne le contrôle publiquement. Solution : un vrai domaine (ex. lab.exemple.be) avec le challenge DNS, ou une petite autorité de certification interne dont tu installes la racine sur tes appareils.

04

DNS local & filtrage — Pi-hole

Pi-hole est un serveur DNS pour tout ton réseau qui bloque pubs et traceurs à la source. Bonus : il sert de DNS local pour donner des noms à tes machines (au lieu de retenir des IP).

Comment ça marche

On déclare le Pi-hole comme serveur DNS du réseau (dans le DHCP de la box/routeur). Chaque requête DNS passe par lui : il répond 0.0.0.0 (mode de blocage par défaut, NULL) pour les domaines publicitaires, et transmet le reste à un DNS amont (ou à Unbound pour de la résolution récursive privée).

Ce que Pi-hole apporte

  • Blocage pubs/traceurs sur tous les appareils
  • DNS local : nas.home.arpa → 192.168.1.20
  • Statistiques de requêtes du réseau

Bonnes pratiques

  • Prévoir un DNS de secours (sinon plus d'Internet si le Pi-hole tombe) — idéalement un second Pi-hole : un DNS public en secondaire laisse passer les pubs, car les clients l'interrogent parfois
  • Le mettre sur une IP fixe
  • Alternative équivalente : AdGuard Home

À retenir

Pi-hole = DNS + bloqueur de pub pour tout le réseau, et un annuaire local pour nommer tes services. Point de vigilance : c'est un point unique de défaillance — prévois un DNS de secours et une IP fixe.

Question éclair

Tu as mis dans le DHCP de la box le Pi-hole en DNS 1 et 1.1.1.1 en DNS 2, « au cas où ». Des pubs réapparaissent par moments. Pourquoi ?

Le DNS 2 ne sert pas seulement quand le Pi-hole est en panne : il suffit que le Pi-hole tarde à répondre pour qu'un appareil passe au suivant, et certains systèmes interrogent leurs serveurs à tour de rôle. Pour garder le filtrage et la redondance, le DNS 2 doit être un second Pi-hole (ou AdGuard Home) sur une autre machine.

06

Stockage & NAS

Tôt ou tard, il faut de l'espace fiable et partagé : c'est le rôle du NAS (Network Attached Storage). On y centralise fichiers, médias et données de conteneurs.

Faire son NAS

  • Solutions clé en main — TrueNAS (basé ZFS), Unraid (souple pour disques de tailles mixtes), OpenMediaVault (léger, sur Debian).
  • Sur Proxmox — un pool ZFS (cf. module Proxmox) partagé en SMB/NFS, ou une VM TrueNAS avec passthrough des disques.

Partager un dossier (SMB & NFS)

  • SMB/CIFS — le partage universel, lu par Windows, macOS et Linux. Idéal pour les postes.
  • NFS — partage Unix→Unix, plus léger, parfait entre serveurs/VM.

RAID n'est pas une sauvegarde

Un miroir ou un RAIDZ protège d'une panne disque, pas d'une suppression accidentelle, d'un rançongiciel ou d'un incendie. Le NAS reste une source à sauvegarder ailleurs (chapitre suivant).

À retenir

Un NAS centralise le stockage et le partage (SMB pour les postes, NFS entre serveurs). TrueNAS/Unraid/OMV clé en main, ou ZFS sur Proxmox. RAID = disponibilité, pas sauvegarde.

Question éclair

Ton NAS ZFS en miroir est chiffré par un rançongiciel arrivé depuis un PC de la maison via le partage SMB. Que t'apporte le miroir ?

Le RAID protège d'une panne de disque. Contre la suppression, l'erreur humaine ou le rançongiciel, il faut des versions anciennes hors d'atteinte : snapshots ZFS non accessibles en écriture depuis le partage, et une sauvegarde sur une autre machine, dont une copie hors ligne ou hors site.

07

Sauvegardes & résilience

Un homelab sans sauvegarde, c'est une perte de données qui attend son heure. La bonne nouvelle : quelques outils rendent ça simple et automatique.

Que sauvegarder

  • Les volumes Docker et fichiers docker-compose.yml (toute ta config).
  • Les VM/CT côté hyperviseur (backups Proxmox, cf. son chapitre dédié).
  • Les données du NAS (documents, photos, médias irremplaçables en priorité).

Avec quoi

  • Restic / Borg / Kopia — sauvegarde chiffrée, dédupliquée, incrémentale, vers un disque externe ou du cloud.
  • Proxmox Backup Server — pour les VM et conteneurs.
  • rsync — pour de la simple recopie de dossiers.

Règle du 3-2-1

3 copies, sur 2 supports, dont 1 hors site. Et surtout : teste une restauration. Une sauvegarde jamais restaurée n'est qu'une hypothèse — automatise le backup, vérifie qu'il tourne, restaure pour de vrai de temps en temps.

08

Accès distant sécurisé

Accéder à son homelab depuis l'extérieur est tentant — et c'est le premier moyen de se faire pirater si on s'y prend mal. La règle : ne jamais exposer un service directement sur Internet. On passe par un tunnel chiffré.

Les bonnes approches

VPN — WireGuard

  • Un tunnel chiffré vers ton réseau maison
  • Un seul port UDP à rediriger sur la box (par convention 51820/UDP), ou zéro avec un relais
  • Moderne, rapide, simple à configurer

Mesh VPN — Tailscale

  • Basé sur WireGuard, zéro port à ouvrir
  • Relie tes appareils comme un réseau privé
  • Le plus simple pour débuter

Ne fais surtout pas ça

Ouvrir un port forwarding direct vers un service (RDP, une appli web, un NAS) est l'une des causes de compromission les plus fréquentes : des robots balaient en permanence tout Internet à la recherche de ces ports. Passe toujours par un VPN (WireGuard/Tailscale). Si un service doit vraiment être public, mets-le derrière un reverse proxy durci, avec authentification et à jour.

Pour aller plus loin

Chaînes de référence pour ce module : TechnoTim (homelab, Docker, reverse proxy) et TechHut (self-hosting). L'infra tourne idéalement sur Proxmox, et la sécurité se travaille avec le module Cybersécurité.

À retenir

Accès distant = VPN uniquement (WireGuard, ou Tailscale pour le zéro-config). Jamais de port forwarding direct vers un service. Un homelab bien fait est invisible depuis Internet.

Question éclair

Tu veux consulter ton Jellyfin depuis l'hôtel. Quelle solution n'expose aucun service du homelab à Internet ?

Avec WireGuard, seul le port du VPN est ouvert, et il ne répond rien à un paquet qui ne porte pas une clé connue : un scanner ne voit même pas qu'il existe. Tailscale n'ouvre aucun port. Une fois dans le tunnel, on joint Jellyfin comme à la maison.

09

S'entraîner : vérifier ses services

Un homelab sert à apprendre l'exploitation : savoir vérifier qu'un service tourne, qu'il répond, et ce qui se passe quand il tombe.

Vérifier

Le DNS local répond-il, et filtre-t-il ?

bash
dig @192.168.1.53 debian.org +short             # résolution normale
dig @192.168.1.53 doubleclick.net +short        # domaine bloqué

Sortie attendue

151.101.2.132
0.0.0.0

La première adresse varie (c'est celle que renvoie le DNS amont) ; la seconde, 0.0.0.0, est la réponse de blocage par défaut de Pi-hole.

Aucune réponse : le conteneur est arrêté ou le port 53 n'est pas publié. Tout le réseau perd Internet quand le DNS local tombe : c'est le point unique de défaillance du chapitre 04 — d'où un second DNS sur une autre machine.

À toi de taper

Demande à ton Pi-hole (192.168.1.53) l'adresse IPv4 de example.com, en réponse courte.

Voir la solution

dig @192.168.1.53 example.com +short. @192.168.1.53 désigne le serveur à interroger : sans lui, dig s'adresse aux serveurs listés dans /etc/resolv.conf, pas forcément au Pi-hole, et le test ne prouverait rien. +short ne garde que la réponse, et sans type indiqué, dig cherche un enregistrement A.

Scénario de panne

Plus rien ne marche à la maison

Un matin, aucun appareil de la maison n'ouvre de site web, mais ping 1.1.1.1 répond depuis le PC.

Ping vers une IP OK, sites KO : où chercher ?

Le mini-PC qui hébergeait le DNS a redémarré après une mise à jour, et le conteneur n'avait pas de politique de redémarrage.

Correction : restart: unless-stopped dans le compose, et un second serveur DNS distribué par le DHCP de la box. Leçon : tout service dont dépend toute la maison mérite un plan B.

À retenir

Vérifier un service, c'est vérifier qu'il répond (dig, curl), pas seulement qu'il tourne. Et tout ce dont dépend tout le réseau — DNS, DHCP — a besoin d'une redondance ou d'un redémarrage automatique.
