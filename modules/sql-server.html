SQL Server
Exploitation et diagnostic — le moteur vu depuis Windows, le réseau et le stockage

Ce que tu sauras faire à la fin

  • Installer une instance nommée et la faire tourner sous un compte de service géré, sans mot de passe à gérer.
  • Rendre l'instance joignable à distance : protocole, port fixe, pare-feu — et savoir tester chaque couche séparément.
  • Créer une base correctement dimensionnée, et expliquer pourquoi la croissance automatique n'est pas une stratégie.
  • Mettre en place une stratégie de sauvegarde, vérifier une sauvegarde et restaurer à un instant précis.
  • Donner des droits au moindre privilège : login, user, rôle, permission — et démêler les quatre.
  • Diagnostiquer un blocage, un interblocage, un journal plein ou une instance qui refuse de démarrer, sans redémarrer à l'aveugle.
  • Traduire un besoin métier en RPO / RTO, et monter un groupe de disponibilité Always On sur deux nœuds.

Prérequis : Windows Server (domaine Active Directory, services), Stockage & clustering pour le dernier chapitre.

Ce module est le prérequis de la partie pratique du module SharePoint Server SE, qui reprend cette installation avec ses contraintes propres (collation, comptes de service, disques dédiés).

01

Le moteur, l'instance et ses fichiers

Le vocabulaire d'abord. Instance, base système, fichier de données : tout le module s'appuie dessus, et la moitié des messages d'erreur aussi.

Un SGBD entre l'application et les fichiers

SQL Server est un SGBD — système de gestion de base de données. Il s'interpose entre celui qui veut les données et les fichiers qui les contiennent :

ApplicationERP, CRM, site web
RéseauTCP/IP, DNS, pare-feu
SQL Serverle moteur, un service Windows
Fichiers.mdf (données) · .ldf (journal)

Quatre rôles : stocker proprement, manipuler (ajouter, chercher, modifier), sécuriser les accès, protéger contre la perte. L'administrateur système intervient sur toute la chaîne sauf la manipulation, qui est du développement.

La posture de tout le module

Un incident « SQL Server » est très souvent un incident Windows, réseau ou stockage qui se présente sous un nom SQL. C'est pour ça que ce module ressemble plus à de l'administration système qu'à du développement.

L'instance : l'unité d'administration

Une instance est une copie active du moteur, qui tourne comme un service Windows. Une même machine peut en porter plusieurs, totalement indépendantes : chacune a sa configuration, ses bases, sa sécurité et ses jobs. Un login créé sur l'une n'existe pas sur l'autre.

Cette dernière ligne du tableau explique la moitié du chapitre 05 : c'est l'instance nommée, avec son port dynamique, qui impose le service SQL Server Browser ou un port fixe.

Les quatre bases système

Créées par l'installation, elles portent le fonctionnement de l'instance elle-même. On ne les touche pas, mais en incident elles sont souvent la réponse.

La requête à connaître par cœur
-- les bases, leur etat et leur modele de recuperation
SELECT name, database_id, state_desc, recovery_model_desc
FROM sys.databases;

Les fichiers d'une base

Une base, ce sont toujours au moins deux fichiers, qui ne jouent pas du tout le même rôle.

DATA — .mdf / .ndf

Les tables, les index, les données. Un fichier principal .mdf, plus autant de .ndf secondaires qu'on veut pour répartir sur plusieurs disques. Ce qu'on surveille : la croissance et l'espace libre.

LOG — .ldf

Le journal des transactions : la trace de chaque modification. C'est lui qui permet d'annuler une transaction et de rejouer ce qui n'avait pas été écrit après une coupure. Ce qu'on surveille : la croissance et la chaîne de sauvegardes.

Les fichiers d'une base, en Mo
USE GESTION;
SELECT name, type_desc, physical_name, size * 8.0 / 1024 AS SizeMB
FROM sys.database_files;

Le * 8.0 / 1024 qui revient partout

SQL Server stocke les tailles en pages de 8 Ko. La conversion en mégaoctets revient dans toutes les requêtes de dimensionnement : autant la reconnaître tout de suite.

À retenir

Le .ldf n'est pas un fichier de log au sens Windows : ce n'est pas un historique lisible qu'on peut effacer quand il gêne. C'est ce qui permet au moteur d'annuler et de rejouer — le supprimer à la main rend la base irrécupérable.

La collation ne se change pas

La collation d'instance devient le défaut de toutes les bases créées ensuite et celle de tempdb. En changer après coup impose de réinstaller ou de reconstruire les bases système. Une collation mal choisie se paie en comparaisons qui échouent entre une base et une table temporaire — à harmoniser avec l'application, dès le départ.

Créer l'arborescence AVANT de lancer le setup

L'assistant accepte des chemins qui n'existent pas et les crée lui-même — on perd alors la maîtrise de l'organisation, et il faut ensuite déplacer des fichiers à chaud. La convention qui tient : sur chaque volume dédié, un dossier au nom de l'instance, contenant un data et un backup. Le nom d'instance dans le chemin est ce qui permet à une seconde instance de cohabiter sans mélanger ses fichiers.

Préparer les dossiers
New-Item -ItemType Directory -Path D:\INSPIRATION\data -Force
New-Item -ItemType Directory -Path D:\INSPIRATION\backup -Force
New-Item -ItemType Directory -Path G:\INSPIRATION\data -Force

Le fichier qui rejoue l'installation

Le ConfigurationFile.ini écrit par l'assistant contient l'intégralité des choix faits. Il permet de rejouer exactement la même installation sur une autre machine — c'est ce qui rend possible la symétrie exigée par un cluster (chapitre 14).

03

Le compte de service géré (gMSA)

Sous quelle identité tourne le moteur ? La réponse par défaut est un compte système local, qui ne sait rien faire sur le réseau. La bonne réponse, en domaine, est un group Managed Service Account.

Le problème que ça résout

Compte utilisateur classique

Un mot de passe, qu'il faut choisir, stocker, faire tourner — et changer dans le service à chaque rotation. En pratique : il n'expire jamais, il est connu de trois personnes, et il finit dans un fichier texte.

gMSA

Un compte de domaine dont Active Directory gère le mot de passe : 240 caractères, renouvelé automatiquement, jamais connu de personne. On ne le saisit nulle part — le champ mot de passe reste vide.

Le montage, en trois temps

1
Sur le contrôleur de domaine

Créer la clé racine KDS (une seule fois pour la forêt), un groupe qui contiendra les machines autorisées, puis le compte de service lui-même.

2
Sur le serveur SQL

Installer le compte sur la machine, puis vérifier qu'elle sait bien récupérer son mot de passe.

3
Dans le Configuration Manager

Affecter le compte au service du moteur et à celui de l'Agent, mot de passe laissé vide.

Sur le contrôleur de domaine
# Cle racine KDS - une seule fois par foret
# le -10h contourne le delai de replication de 10 h, acceptable en labo
Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))

# Le compte, autorise pour les machines du groupe GM_GMSA_SQL
New-ADServiceAccount GMSA_SQL -DNSHostName gmsa_sql.orion.local `
    -PrincipalsAllowedToRetrieveManagedPassword GM_GMSA_SQL
Sur le serveur SQL
# Rafraichir le ticket Kerberos de la machine, sinon elle ignore
# qu'elle vient d'entrer dans le groupe (sinon : redemarrer)
klist purge -li 0x3e7
gpupdate /force /target:computer

Install-ADServiceAccount GMSA_SQL
Test-ADServiceAccount GMSA_SQL   # doit renvoyer True

Le désigner pendant l'installation, pas après

Si le gMSA est désigné dans l'assistant d'installation, celui-ci pose lui-même les bonnes ACL NTFS sur les dossiers de données. Créé après coup, il faut repasser à la main par le Configuration Manager — et surtout jamais par services.msc, qui change le compte sans poser les droits sur les fichiers, le registre et les groupes locaux.

Deux détails qui font perdre une heure

Le compte apparaît partout avec un $ final (ORION\GMSA_SQL$) : c'est un compte d'ordinateur, pas d'utilisateur. Et dans le sélecteur Active Directory, il faut cocher « Ordinateurs » pour voir le compte machine du serveur SQL — sans quoi la recherche ne renvoie rien.

Vérifier, toujours

Test-ADServiceAccount doit renvoyer True, et la colonne Log On As du Configuration Manager doit afficher le compte sur le moteur et sur l'Agent. Le SQL Server Browser, lui, reste sous NT AUTHORITY\LOCALSERVICE : normal, il n'annonce qu'un port.

04

Configuration Manager : services et protocoles

La console MMC qui gère tout ce qui fait fonctionner et communiquer SQL Server sur Windows. C'est par elle qu'on passe, pas par les services Windows.

Cinq volets

Services · comptes de service · réseau serveur · ports et IP · alias client. Le raccourci est souvent introuvable dans le menu Démarrer : l'outil se lance par son fichier MMC, dont le numéro suit la version du moteur.

Ouvrir l'outil
# SQL Server 2022 -> 16 | 2019 -> 15 | 2017 -> 14 | 2025 -> 17
C:\Windows\SysWOW64\SQLServerManager16.msc

Jamais services.msc pour modifier

Pour regarder si un service tourne, services.msc fait l'affaire. Pour modifier quoi que ce soit — et surtout changer un compte de service — seul le Configuration Manager pose les ACL NTFS, les droits registre et les appartenances aux groupes locaux qui vont avec.

Les quatre services, et leurs noms exacts

ServiceNom (instance nommée)Rôle
SQL ServerMSSQL$INSPIRATIONLe moteur : requêtes, transactions, mémoire, I/O. Arrêté, les bases sont indisponibles.
SQL Server AgentSQLAgent$INSPIRATIONJobs, planifications, alertes, maintenance.
SQL Server BrowserSQLBrowserUn seul par machine. Annonce le port des instances nommées sur UDP 1434.
SQL Server VSS WriterSQLWriterUn seul par machine. Support des sauvegardes VSS. Absent de SSMS.

Deux pièges de lecture

Dans l'arbre du Configuration Manager, les entrées marquées (32bit) sont des vestiges : les ignorer. Et l'Agent reste souvent en démarrage Manual après une installation — à passer en Automatic, sinon aucune sauvegarde planifiée ne repart après un redémarrage.

Activer TCP/IP

SQL Server Network Configuration → Protocols for INSPIRATION → TCP/IP → Enable, puis redémarrer le service du moteur. Sans le redémarrage, le changement n'est pas pris en compte — et on cherche le problème ailleurs pendant vingt minutes.

À retenir

Le Configuration Manager est l'outil qu'on rouvre le plus souvent : services, comptes, protocoles, ports, alias. Il mérite d'être épinglé à la barre des tâches — et c'est le premier endroit à regarder quand « SQL ne répond plus ».

05

Réseau : TCP/IP, port et pare-feu

Le moteur tourne, le local fonctionne, et rien ne se connecte depuis l'extérieur. Trois couches à traiter dans l'ordre — et surtout à tester séparément.

Les trois protocoles

ProtocolePortéeÀ en faire
Shared Memoryuniquement depuis la machine elle-mêmeToujours activé, le plus rapide en local. C'est la porte de secours : si le local passe et que le distant échoue, le problème est réseau, pas SQL.
TCP/IPle réseauCelui à activer dès qu'un client distant doit se connecter. Désactivé par défaut sur une installation Developer.
Named Pipesréseau, via SMBHéritage. À laisser désactivé : il dépend du partage de fichiers et traverse mal les pare-feu.

Port fixe ou port dynamique

Port fixePort dynamique
Attributionchoisi une foisau démarrage du service — change à chaque redémarrage
Par défaut surl'instance par défaut (1433)les instances nommées
Pare-feuune règle, écrite une foisimpossible à filtrer proprement
Browserfacultatif si le client vise SERVEUR,PORTindispensable

Bonne pratique : fixer le port, le documenter, l'ouvrir dans le pare-feu, puis tester depuis un poste client. Concrètement, dans les propriétés TCP/IP, onglet IP Addresses : relever le port dynamique attribué, le reporter dans TCP Port de la section IPAll, et vider TCP Dynamic Ports.

Vider, pas mettre zéro

Le champ TCP Dynamic Ports doit être laissé vide. Un 0 n'est pas « aucun port dynamique » : c'est la valeur qui réactive l'attribution dynamique. Le port redevient alors variable au prochain redémarrage, et la règle de pare-feu ne protège plus rien.

Ouvrir le pare-feu
# UDP 1434 : c'est le Browser qui repond "l'instance ecoute sur tel port"
New-NetFirewallRule -DisplayName "SQL Browser (UDP 1434)" `
    -Direction Inbound -Protocol UDP -LocalPort 1434 -Action Allow

# Le port fixe du moteur
New-NetFirewallRule -DisplayName "SQL Server (TCP 1433)" `
    -Direction Inbound -Protocol TCP -LocalPort 1433 -Action Allow

Set-Service SQLBrowser -StartupType Automatic
Start-Service SQLBrowser

La portée de la règle

Ouvrir un port « pour tout le monde » n'est acceptable qu'en labo. En production, restreindre aux machines ou sous-réseaux qui en ont besoin (-RemoteAddress) et à un profil précis (-Profile Domain) : c'est le moindre privilège appliqué au réseau.

Tester, couche par couche

Dans cet ordre, jamais un autre
# 0. le nom se resout-il, et vers la bonne IP ?
Resolve-DnsName SQL

# 1. le port repond-il ? (reseau + pare-feu, sans SQL)
Test-NetConnection SQL -Port 1433

# 2. la connexion SQL passe-t-elle ?  -E = authentification Windows
sqlcmd -S SQL,1433 -E -Q "SELECT @@VERSION"
sqlcmd -S SQL\INSPIRATION -E -Q "SELECT @@SERVERNAME"

Ce que la dernière ligne isole

La forme SERVEUR\INSTANCE est celle qui passe par le Browser. Si elle échoue alors que SERVEUR,PORT fonctionne, c'est le Browser ou l'UDP 1434 qu'il faut regarder — pas le moteur. Ces deux commandes séparent en dix secondes un problème de service d'un problème de résolution de port.

Les alias

Un alias associe un nom court à un couple serveur/port/protocole. Le principe ressemble à du DNS, mais la portée est strictement locale : l'alias n'existe que sur la machine où il est défini. L'intérêt est que l'application utilise un nom stable, même si le serveur ou le port changent.

Le piège 32 / 64 bits

Les alias 32 bits et 64 bits sont deux listes distinctes. Une application 32 bits ne voit pas les alias 64 bits, et inversement : un alias « qui ne marche pas » a très souvent été créé du mauvais côté. Et comme un alias masque la vraie cible, il se documente au même titre que le port.

06

Mémoire, parallélisme et tempdb

Trois réglages qui ne se voient pas tant que tout va bien, et qui expliquent une bonne part des lenteurs quand ça va mal.

max server memory

SQL Server aime la RAM, Windows aussi. Par défaut, le moteur est autorisé à prendre presque toute la mémoire de la machine : il met les données en cache et ne les rend pas spontanément. Le système d'exploitation finit par manquer de mémoire, se met à pager sur disque, et la machine entière ralentit — SQL Server compris.

RAM totale16 Goce que la machine possède
Windows + agents4 Goréservé : OS, antivirus, supervision
max server memory12 Goce qu'on configure
Plafonner la mémoire
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

EXEC sp_configure 'max server memory';          -- lire
EXEC sp_configure 'max server memory', 12288;   -- 12 Go, en Mo
RECONFIGURE;

Deux oublis classiques

max server memory est une option avancée : il faut activer show advanced options ne serait-ce que pour la lire. Et rien n'est appliqué avant RECONFIGURE — sp_configure ne fait qu'enregistrer la valeur souhaitée.

MaxDOP

Maximum Degree Of Parallelism : le nombre maximal de processeurs qu'une seule requête peut mobiliser. À 0, il n'y a pas de limite — une grosse requête peut occuper tous les cœurs et faire attendre tout le monde. À 1, le parallélisme est désactivé. L'assistant d'installation propose désormais une valeur calculée d'après la machine : la laisser est raisonnable tant qu'on n'a pas de raison mesurée d'en changer.

tempdb

Recréée à chaque démarrage du service, elle repart à la taille configurée, pas à celle qu'elle avait atteinte : un dimensionnement trop petit se paie à chaque redémarrage. Plusieurs fichiers de données répartissent la contention, et un volume dédié lui évite de concurrencer les données et le journal.

Les fichiers de tempdb
SELECT physical_name, size * 8.0 / 1024 AS SizeMB
FROM tempdb.sys.database_files;

À retenir

Ces trois paramètres se décident, se documentent, et ne se changent pas en production sans mesure préalable. Une valeur par défaut n'est pas un choix, c'est une absence de choix — et elle se remarque le jour où la charge arrive.

07

Créer et dimensionner une base

Une base mal créée fonctionne parfaitement le premier jour. Les problèmes arrivent en exploitation — et la plupart des options ne se corrigent plus aussi facilement.

Deux façons de créer

CREATE DATABASE
-- le minimum : tout au defaut, herite de la base model
CREATE DATABASE GESTION;

-- la version qui decide, et c'est celle qu'on veut
CREATE DATABASE GESTION
ON PRIMARY
( NAME = GESTION_Data,
  FILENAME = 'D:\INSPIRATION\data\GESTION.mdf',
  SIZE = 512MB, FILEGROWTH = 128MB )
LOG ON
( NAME = GESTION_Log,
  FILENAME = 'G:\INSPIRATION\data\GESTION_log.ldf',
  SIZE = 256MB, FILEGROWTH = 128MB );

Pourquoi la première forme est un piège

CREATE DATABASE GESTION; fonctionne, et c'est bien le problème : la base hérite des tailles et de la croissance de model, c'est-à-dire de valeurs qui ne correspondent à rien du besoin réel. C'est le point de départ de tous les problèmes de dimensionnement.

Le bouton Script de SSMS

Quand la base est créée via l'interface, cliquer Script avant de valider : on obtient exactement la commande ci-dessus, avec les vrais chemins et les vraies tailles. Une trace rejouable — et la seule façon de recréer la même base à l'identique ailleurs.

Le recovery model

L'option la plus structurante. Elle se choisit selon le RPO — combien de données l'organisation accepte de perdre (chapitre 14) — et pas selon une préférence technique.

ModèleComportement
SIMPLELe journal est tronqué automatiquement ; pas de restauration à un instant précis. Suffisant en labo ou pour une base reconstructible.
FULLToutes les transactions sont conservées jusqu'à la sauvegarde du journal ; restauration à la seconde près possible.
BULK_LOGGEDVariante de FULL, journalisation allégée pour les opérations en masse. Le temps d'un import, puis on en sort.

Passer en FULL ne suffit pas

Le modèle n'est qu'une moitié de la décision. Sans sauvegardes de journal effectivement planifiées, une base en FULL conserve toutes ses transactions et son .ldf grossit jusqu'à saturer le disque. FULL sans sauvegarde de journal est pire que SIMPLE : on a les inconvénients des deux et les garanties d'aucun.

Les autres options

  • Collation — se fixe à la création. CI = insensible à la casse, AS = sensible aux accents. C'est ce couple qui fait qu'en SQL Server, WHERE nom = 'dupont' ramène aussi DUPONT.
  • Owner — mettre sa ou un compte dédié, sinon la base devient orpheline le jour où le compte créateur est supprimé.
  • Auto Close et Auto Shrink — à laisser OFF.
  • Auto Create / Update Statistics — à laisser ON.
  • Page Verify — CHECKSUM : ce qui permet de détecter une corruption venue du stockage.

Dimensionnement et croissance automatique

L'auto-growth est une sécurité, pas une stratégie. Pendant une croissance, le moteur demande de la place au système de fichiers, et l'écriture est suspendue le temps de l'allocation.

À éviter

Taille initiale trop petite · croissance en pourcentage (chaque palier est plus gros que le précédent) · autogrowth de 1 Mo sur une grosse base · aucune surveillance du disque.

À privilégier

Taille initiale proche du besoin réel · croissance fixe en Mo · un MAXSIZE défini · des volumes supervisés, avec alerte avant saturation.

Mesurer avant de décider
SELECT name,
       size * 8.0 / 1024 AS SizeMB,
       growth,
       is_percent_growth
FROM sys.database_files;

is_percent_growth à 1 signale une croissance en pourcentage — le cas à corriger. À 0, growth est exprimé en pages de 8 Ko, à convertir comme la taille.

Exercice — lire un dimensionnement

Une base de 40 Go a été créée avec SIZE = 8MB et FILEGROWTH = 10%. Combien pèse la croissance suivante quand le fichier atteint 40 Go, et pourquoi est-ce un problème ?

Afficher la correction

10 % de 40 Go = 4 Go d'un coup. Deux conséquences : l'allocation de 4 Go suspend les écritures le temps de se faire (et sans Instant File Initialization, Windows remplit d'abord la zone de zéros), et le disque doit avoir 4 Go libres à cet instant précis, sinon la transaction échoue.

Le vrai problème est que l'incrément grandit avec le fichier : plus la base est grosse, plus la pause est longue, exactement au moment où elle est le moins tolérable. D'où la règle : croissance fixe en Mo, jamais en pourcentage.

Le shrink n'est pas de la maintenance

Réduire un fichier dépanne pour récupérer de la place ponctuellement. Mais un shrink provoque des pauses I/O et fragmente massivement les index : il impose donc une reconstruction d'index derrière. Un fichier qui regrossit après un shrink signale un mauvais dimensionnement, pas un besoin de shrink périodique. À ne jamais automatiser.

08

Gérer une base existante

Les propriétés d'une base disent en une page si elle est saine. Encore faut-il savoir quoi y lire — et reconnaître les valeurs par défaut qui se font passer pour des choix.

Ce que dit la page General

Dernière sauvegarde de la base, dernière sauvegarde du journal, statut, propriétaire, taille, espace disponible, collation. Last Database Backup: None sur une base en mode FULL, c'est le point de départ du journal qui gonfle.

« Unlimited » n'est pas un plafond réfléchi

Dans l'onglet Files, Unlimited pour les données et Limited to 2 097 152 Mo pour le journal sont les valeurs par défaut. Elles ressemblent à des décisions, elles n'en sont pas : personne n'a évalué la volumétrie attendue.

Les opérations courantes

Mettre une base hors ligne, et la remettre
SELECT name, state_desc FROM sys.databases;

ALTER DATABASE GESTION SET OFFLINE;
ALTER DATABASE GESTION SET ONLINE;

-- pour reprendre la main tout de suite : ANNULE les transactions
-- en cours des autres utilisateurs. Se decide, ne s'improvise pas.
ALTER DATABASE GESTION SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

L'état d'une base

ÉtatCe qu'il signifieCe qu'on fait

OFFLINEsortie volontairementla remettre en ligne — et chercher qui l'a sortie, et pourquoi
RESTORINGrestauration en cours, ou arrêtée à NORECOVERYterminer la chaîne, ou finir par WITH RECOVERY
RECOVERY_PENDINGla recovery n'a pas pu se terminer — souvent un fichier ou un volume inaccessiblene rien forcer : lire le journal du moteur, rendre le fichier accessible, relancer

À retenir

RECOVERY_PENDING et SUSPECT sont les deux états où l'envie d'agir vite fait le plus de dégâts. Ce sont des symptômes de problèmes sous SQL Server — un disque, un volume démonté, un fichier supprimé — et la réponse commence toujours par lire le journal du moteur, pas par relancer le service.

09

Sauvegarder et restaurer

Le cœur du métier. Trois types de sauvegarde, une chaîne à respecter, et une vérité désagréable : un fichier .bak ne prouve rien tant qu'on ne l'a pas restauré.

Les trois types

TypeContenuFréquence typique
Fulltoute la baseune fois par semaine
Differentialtout ce qui a changé depuis la dernière fullune fois par jour
Transaction Logles transactions depuis la dernière sauvegarde de journalplusieurs fois par jour

Différentiel ≠ incrémental

Une base à laquelle on ajoute des données par blocs : ABCD lundi, EF mardi, GH mercredi. Ce que contient réellement le fichier écrit chaque jour :

JourFullDifférentielIncrémental (= journal)
LundiABCDABCDABCD
MardiABCDEFEFEF
MercrediABCDEFGHEFGHGH

Le différentiel de mercredi contient EFGH — tout ce qui a changé depuis la full de lundi, y compris ce que mardi avait déjà sauvegardé. D'où la différence au moment qui compte, la restauration :

Fichiers à restaurerLe risque
Fullun seulaucun, mais le plus gros et le plus long à écrire
Différentielfull + dernier diffles diff intermédiaires ne servent à rien
Incrémentalfull + toute la chaîne, dans l'ordreun maillon manquant casse tout
Les trois sauvegardes
BACKUP DATABASE GESTION TO DISK = 'D:\backup\GESTION_FULL.bak'
    WITH INIT, COMPRESSION, CHECKSUM;

BACKUP DATABASE GESTION TO DISK = 'D:\backup\GESTION_DIFF.bak'
    WITH DIFFERENTIAL;

BACKUP LOG GESTION TO DISK = 'D:\backup\GESTION_LOG.trn';

Append est le défaut, et c'est un piège

Par défaut, SQL Server ajoute la sauvegarde au fichier .bak existant : une sauvegarde quotidienne écrite au même endroit pendant six mois donne un fichier énorme dont il faut extraire le bon jeu. WITH INIT écrase — soit un fichier par sauvegarde avec un nom horodaté, soit l'écrasement assumé.

Copy-only backup

Une copie ponctuelle « hors chaîne » : elle ne devient pas le nouveau point de référence des différentiels et ne tronque pas le journal. C'est l'option à cocher pour rafraîchir un environnement de test sans casser la stratégie en place. L'oublier est une erreur classique : le différentiel du lendemain se référera à cette sauvegarde ad hoc, qui n'est peut-être plus là.

Vérifier une sauvegarde

Sans rien restaurer
RESTORE VERIFYONLY   FROM DISK = 'D:\backup\GESTION_FULL.bak';
RESTORE HEADERONLY   FROM DISK = 'D:\backup\GESTION_FULL.bak';
RESTORE FILELISTONLY FROM DISK = 'D:\backup\GESTION_FULL.bak';
  • VERIFYONLY — le média est-il lisible et complet ?
  • HEADERONLY — que contient ce fichier : quelle base, quel type, quand.
  • FILELISTONLY — les noms logiques des fichiers, indispensables pour écrire un MOVE.

Une sauvegarde non restaurée est une hypothèse

VERIFYONLY vérifie le média, pas la restaurabilité de bout en bout : il ne dit rien de la chaîne de journaux, ni des droits, ni de la place disponible sur la cible. La seule preuve est une restauration réellement effectuée — et chronométrée, puisque c'est elle qui donne le RTO réel.

Restaurer sans écraser la production

Le réflexe qui évite les catastrophes : ne pas restaurer sur la base en incident, mais à côté, sous un autre nom. On récupère les données utiles, on vérifie, et seulement ensuite on décide.

Restauration parallèle
RESTORE DATABASE GESTION_Recovery
FROM DISK = 'D:\backup\GESTION_FULL.bak'
WITH MOVE 'GESTION'     TO 'D:\data\GESTION_Recovery.mdf',
     MOVE 'GESTION_log' TO 'G:\data\GESTION_Recovery_log.ldf',
     NORECOVERY;

RESTORE LOG GESTION_Recovery
FROM DISK = 'D:\backup\GESTION_LOG.trn'
WITH RECOVERY;
Mot-cléEffet
MOVERedirige chaque fichier vers un nouveau chemin — obligatoire quand la base d'origine existe encore, sinon on écrase ses fichiers.
NORECOVERYLaisse la base en attente d'autres restaurations (état RESTORING). À mettre sur toutes les étapes sauf la dernière.
RECOVERYTermine la restauration et rend la base utilisable. Une fois passé, plus aucun journal ne peut être appliqué : c'est irréversible.

Revenir juste avant l'erreur

Point-in-time : le DELETE accidentel de 10 h 30
-- 10:00 FULL | 10:20 LOG | 10:29 donnees OK | 10:30 DELETE
RESTORE LOG GESTION_Recovery
FROM DISK = 'D:\backup\GESTION_LOG.trn'
WITH STOPAT = '2026-09-02T10:29:50', RECOVERY;

STOPAT dit au moteur : rejoue les transactions du journal, mais arrête-toi à cette seconde. Trois conditions : la base doit être en FULL, la chaîne de journaux doit être intacte, et l'heure exacte se détermine prudemment — trop tard on rejoue la suppression, trop tôt on perd du travail légitime.

L'historique vit dans msdb

La table msdb.dbo.backupset enregistre ce qui a réellement été sauvegardé (type D = full, I = différentiel, L = journal). Attention : cet historique n'est pas dans les fichiers .bak. Si msdb est purgée, l'historique disparaît alors que les sauvegardes sont là — et une ligne dans msdb ne prouve pas que le fichier existe encore sur le disque.

Restaurer ailleurs laisse des orphelins

Restaurer sur une autre instance laisse des utilisateurs orphelins : la base arrive avec ses users, mais leurs logins étaient dans master et n'ont pas suivi. Le recollage se fait par ALTER USER [nom] WITH LOGIN = [nom] — voir le chapitre suivant.

Logins, users, rôles, permissions

Quatre notions distinctes, qu'une commodité de l'interface fait constamment confondre. Les démêler, c'est la moitié du dépannage d'une connexion.

La chaîne

LOGINinstance« puis-je me connecter au serveur ? »
USERbase« puis-je lire ou écrire ici ? »
RÔLEserveur / baseun paquet de permissions
PERMISSIONobjetSELECT sur telle table

Login ≠ User

Le login vit dans master, le user vit dans la base. Un login sans user se connecte à l'instance… et ne voit aucune donnée. C'est l'onglet User Mapping de SSMS qui entretient la confusion : il crée le user et lui donne ses rôles d'un seul geste, si bien qu'on oublie qu'il s'agit de deux objets différents — jusqu'au jour où on restaure une base ailleurs et qu'on récupère des utilisateurs orphelins.

La chaîne complète, en commandes
-- 1. un login au niveau de l'instance
CREATE LOGIN [ORION\svc] FROM WINDOWS;

-- 2. un user dans la base, rattache a ce login
USE GESTION;
CREATE USER svc FOR LOGIN [ORION\svc];

-- 3. un role, plutot que des permissions une par une
ALTER ROLE db_datareader ADD MEMBER svc;

-- 4. ou une permission precise sur un objet
GRANT SELECT ON dbo.Clients TO svc;

Les rôles à connaître

Rôles serveur (sur un login)

sysadmin — tout, et ignore même les DENY : DBA uniquement.
securityadmin — gère les logins, donc aussi dangereux que sysadmin.
dbcreator, serveradmin, processadmin, bulkadmin…
public — tout login en est membre : ne rien lui donner.

Rôles base (sur un user)

db_owner — tout sur la base, y compris la supprimer.
db_datareader / db_datawriter — lire / modifier toutes les tables.
db_ddladmin, db_backupoperator, db_accessadmin…
db_denydatareader — interdit, et l'emporte.

La combinaison type d'un compte applicatif

db_datareader + db_datawriter sur sa base, et rien d'autre. Pas db_owner « pour que ça marche », et surtout pas sysadmin. L'erreur la plus fréquente en entreprise est d'ajouter sysadmin pour résoudre un simple problème de permission.

GRANT, DENY, REVOKE

CommandeEffet
GRANTAccorde un droit.
DENYInterdit explicitement. L'emporte sur tout GRANT, y compris hérité d'un rôle.
REVOKEAnnule un GRANT ou un DENY — il remet à neutre.

REVOKE n'est pas DENY

Priorité : DENY > GRANT > rien. REVOKE remet simplement à neutre — si le droit vient aussi d'un rôle dont l'utilisateur est membre, il le garde. C'est la source classique du « j'ai retiré le droit et il accède toujours ». Et sysadmin passe outre tout, même un DENY.

11

Maintenance et SQL Server Agent

Sauvegarder ne suffit pas. Une base qui vit se dégrade de trois façons indépendantes — et c'est l'Agent qui automatise la réponse.

Trois dégradations, trois réponses

Intégrité, index, statistiques
-- 1. corruption des pages sur le disque
DBCC CHECKDB('GESTION') WITH NO_INFOMSGS;

-- 2. fragmentation des index
ALTER INDEX IX_Exemple ON dbo.Clients REBUILD;

-- 3. statistiques perimees
UPDATE STATISTICS dbo.Clients;

Ne jamais ignorer une erreur de CHECKDB

Une corruption non traitée continue d'être sauvegardée : au bout de quelques semaines, toutes les sauvegardes de la chaîne portent le problème, et il n'y a plus de point de retour sain. Et les options de réparation — REPAIR_ALLOW_DATA_LOSS en tête — sont un dernier recours, pas la réponse normale : leur nom dit exactement ce qu'elles font. Devant une corruption, le premier réflexe est de restaurer.

REORGANIZEREBUILD
Effetréordonne les pages sur placereconstruit l'index entièrement
Coûtléger, toujours en ligne, interruptiblelourd, verrouille la table (sauf ONLINE = ON, Enterprise)
Journalécrit peuécrit beaucoup — le journal gonfle d'autant
Statistiquesinchangéesmises à jour au passage

Repères d'usage : moins de 5 % de fragmentation → ne rien faire ; entre 5 et 30 % → REORGANIZE ; au-delà → REBUILD. L'ordre naturel est celui des trois commandes : intégrité, puis index, puis statistiques — inutile de reconstruire les index d'une base dont on n'a pas vérifié qu'elle est saine.

Pourquoi des statistiques périmées font mal

Elles décrivent la distribution des valeurs d'une colonne : c'est sur elles que l'optimiseur estime le nombre de lignes qu'une requête va ramener, donc choisit son plan. Périmées, elles produisent un mauvais plan — et la requête devient lente sans que le code ni les données aient changé. Un symptôme classique à connaître avant de chercher ailleurs.

Le SQL Server Agent

Le planificateur de l'instance : il exécute des jobs — sauvegardes, CHECKDB, reconstruction d'index, scripts métier — à heure dite, et sait prévenir quand ça échoue. C'est un service à part du moteur, qui tourne sous le même compte gMSA.

Page d'un jobCe qu'il faut savoir
GeneralLe propriétaire décide des droits d'exécution : un job appartenant à un compte trop faible échoue sur une permission. La description n'est pas décorative — c'est elle qu'on lit à 3 h du matin.
StepsChaque étape a un type, une base de contexte, et surtout un flux succès/échec. C'est là qu'on évite qu'un REBUILD se lance alors que le CHECKDB a échoué.
SchedulesZéro, une ou plusieurs planifications ; elles peuvent être partagées entre jobs.
AlertsDéclenche le job sur une erreur, une gravité ou un compteur — l'inverse du planning : c'est l'incident qui appelle le job.
NotificationsÀ configurer sur When the job fails. Un job planifié dont personne ne regarde le résultat n'est pas une sauvegarde, c'est une impression de sauvegarde.

Agent arrêté = silence total

Si le service est arrêté, SSMS affiche Agent XPs disabled et rien de planifié ne s'exécute — sans autre avertissement qu'un dossier Jobs silencieux. Et s'il est en démarrage Manual, tout repart… jusqu'au prochain redémarrage du serveur. Le passer en Automatic est ce qui rend la planification fiable.

Avant de relancer un job en échec, lire son historique

Clic droit → View History donne le détail par étape, avec le message d'erreur exact. Relancer d'abord et regarder ensuite fait perdre l'information : si la seconde exécution réussit, on ne saura jamais pourquoi la première a échoué — et elle recommencera.

Sauvegarder msdb

Les jobs et leur historique vivent dans msdb. Cette base système doit être sauvegardée comme les autres, sinon toute la planification disparaît avec le serveur.

Diagnostiquer un incident

Une méthode, puis les trois incidents qu'on rencontre vraiment : le blocage, l'interblocage, le journal plein.

Ne pas réparer avant de comprendre

Observerconstater les faits, sans interpréter
Mesurerdepuis quand, combien, quelle ressource
Identifiernommer la cause, pas le symptôme
Corrigerl'action la moins risquée
Vérifierle symptôme a disparu, rien d'autre n'a cassé
Documenterpour la prochaine fois, et pour les autres

Les six questions qui structurent l'observation : quel est le symptôme réellement observé ? depuis quand ? qui est impacté — un poste, un service, tout le monde ? quelle ressource est saturée ? quel changement est récent ? quelle action est la moins risquée ?

Le mauvais réflexe

Redémarrer SQL Server sans diagnostic efface les informations qui auraient permis de comprendre — sessions en cours, compteurs, cache — et allonge l'interruption au lieu de la réduire. Le symptôme disparaît parfois ; la cause revient. Ce n'est pas interdit pour autant : c'est une action de dernier recours, à prendre après avoir relevé ce qui peut l'être, et suivie d'une analyse à froid.

Identifier qui fait quoi

Du réflexe rapide aux DMV
EXEC sp_who2;   -- colonne BlkBy = le SPID de la session BLOQUANTE

-- ce qui tourne maintenant, avec le texte de la requete
SELECT r.session_id, r.status, r.cpu_time, r.total_elapsed_time,
       r.blocking_session_id, t.text
FROM sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.session_id <> @@SPID;

Les deux colonnes qu'on oublie de lire

host_name et program_name de sys.dm_exec_sessions : c'est souvent là qu'on découvre que « la base est lente » veut dire « un export Excel tourne depuis 40 minutes depuis le poste du service compta ».

Blocage

Une session attend une ressource détenue par une autre. Session A fait BEGIN TRAN puis UPDATE : elle prend un verrou et le garde tant qu'il n'y a ni COMMIT ni ROLLBACK. Session B tente le même UPDATE : elle attend, indéfiniment.

Ce n'est pas une anomalie

Le blocage est le mécanisme normal d'isolation qui protège les données. Il devient un incident quand il dure — et la cause est presque toujours la même : une transaction ouverte et jamais validée. Une fenêtre SSMS laissée en plan après un BEGIN TRAN, ou une application qui ne fait pas son COMMIT.

KILL est une décision, pas un diagnostic

KILL 55 s'utilise après avoir identifié qui bloque et pourquoi, jamais pour faire taire un symptôme. Il déclenche le rollback de la transaction : cela prend du temps — souvent autant que le travail à annuler — et les verrous restent tenus pendant ce temps. Tuer une grosse transaction ne libère donc pas la base tout de suite, et peut allonger l'attente. KILL 55 WITH STATUSONLY donne l'avancement du rollback.

Interblocage

Un cycle : A tient R1 et attend R2, B tient R2 et attend R1. Aucune ne peut avancer. SQL Server détecte le cycle, choisit une victime, annule sa transaction (erreur 1205) et libère l'autre.

BlocageInterblocage
Natureune attenteun cycle
Issuese résout dès que le verrou est relâchéinsoluble sans victime
Qui agitpersonne, ou l'administrateur si ça dureSQL Server, automatiquement

Les deadlocks se regardent après coup

On n'assiste jamais à un interblocage en direct : il est tranché en quelques secondes. Les cas passés se retrouvent dans la session Extended Events system_health, active par défaut sur toute instance. Un interblocage récurrent est un problème applicatif — deux traitements qui prennent leurs verrous dans un ordre différent : le rôle de l'administrateur est de le documenter et de le remonter, pas de le corriger côté serveur.

Journal de transactions plein

Erreur 9002. Le réflexe interdit est d'agrandir le fichier ou de basculer en SIMPLE « pour que ça reparte » : chercher la cause avant d'agrandir.

Trois mesures complémentaires
SELECT name, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases;

DBCC SQLPERF(LOGSPACE);      -- taille et % d'occupation

log_reuse_wait_descCe qu'on fait
LOG_BACKUPUne sauvegarde de journal est attendue — la lancer. Le cas le plus fréquent.
ACTIVE_TRANSACTIONUne transaction est ouverte — l'identifier avec DBCC OPENTRAN.

Deux erreurs à ne jamais commettre

La taille physique du .ldf ne diminue pas quand le journal est tronqué : l'espace redevient réutilisable à l'intérieur du fichier, c'est tout. Voir un .ldf toujours aussi gros après une sauvegarde de journal est donc normal.
Et supprimer un .ldf à la main rend la base irrécupérable : il contient les transactions pas encore écrites dans le .mdf. C'est l'une des rares manipulations vraiment sans retour.

Quand SQL Server ne démarre pas

Le cas où la tentation de réinstaller est la plus forte, et où elle est la plus mauvaise. Dans l'ordre : service → message → error log → event viewer → compte → disques → paramètres.

Ne pas réinstaller sans diagnostic

La réinstallation n'est presque jamais la solution, et elle détruit les indices. Un démarrage échoué laisse des traces précises dans les journaux. Les causes réelles sont presque toujours dans la liste : un compte de service dont la machine est sortie du groupe, une ACL perdue sur les dossiers, un disque plein, un volume non monté, ou master devenue inaccessible.

14

Haute disponibilité

Cluster de basculement et groupes de disponibilité Always On : avant tout montage technique, deux chiffres décident de l'architecture — pas l'inverse.

RPO et RTO

RPO — Recovery Point Objective

Combien de données peut-on se permettre de perdre ? Cela dimensionne la fréquence des sauvegardes, en particulier celles du journal. Un RPO de 15 minutes impose un backup de journal toutes les 15 minutes.

RTO — Recovery Time Objective

Combien de temps peut-on rester indisponible ? Cela dimensionne la technologie : une restauration se compte en heures, une bascule de cluster en secondes.

Ces chiffres viennent du métier

Ils se négocient et s'écrivent — ce ne sont pas des choix techniques. Un RPO de zéro et un RTO de zéro n'existent pas : ils se paient, en matériel et en complexité.

Haute disponibilité ≠ reprise d'activité

Haute disponibilité (HA)Reprise d'activité (DR)

Un cluster ne remplace pas des sauvegardes

Une base corrompue, une table supprimée par erreur ou un chiffrement par rançongiciel se répliquent fidèlement sur le second nœud. Seule une sauvegarde permet de revenir en arrière. Les deux approches sont complémentaires, jamais alternatives.

Le cluster de basculement Windows

Le Windows Server Failover Cluster est la fondation Windows sur laquelle s'appuient les solutions de HA de SQL Server. Il ne sait rien de SQL : il surveille des nœuds, tient un quorum, et bascule des ressources.

Sur les deux nœuds
Install-WindowsFeature failover-clustering `
    -IncludeAllSubFeature -IncludeManagementTools

Puis, dans le Failover Cluster Manager : Create Cluster (nom + IP du cluster), puis Add Node pour le second serveur. Le nom du cluster est un objet ordinateur créé dans l'AD — d'où l'obligation que les deux nœuds soient membres du même domaine.

La symétrie est tout le sujet

Le second nœud doit recevoir une installation rigoureusement identique : même édition, même build exact, mêmes fonctionnalités, même nom d'instance, mêmes chemins de fichiers, même compte de service, même port. Une base ne peut être montée sur le second nœud que si ses dossiers existent, au même endroit. D'où l'intérêt d'installer depuis le ConfigurationFile.ini de la première installation (chapitre 02).

Le quorum n'est pas optionnel

Avec deux nœuds, chacun voyant l'autre disparaître se croirait légitime : les deux monteraient les mêmes ressources et les données divergeraient — c'est le split-brain. Le quorum ajoute une voix départageante (disque, partage de fichiers ou témoin cloud). Sans lui, une simple coupure réseau entre les deux machines suffit à casser le cluster.

Always On : les groupes de disponibilité

Le cluster sait basculer des ressources ; les availability groups répliquent les bases elles-mêmes, en continu, entre deux instances — chacune gardant ses propres disques. À activer dans le Configuration Manager sur chaque serveur, avec redémarrage du service, puis à monter avec l'assistant de SSMS.

Onglet de l'assistantCe qui s'y joue
ReplicasLes instances participantes, le mode de bascule, la lisibilité du secondaire. Automatic Failover se coche des deux côtés — la bascule doit marcher dans les deux sens.
EndpointsLe port de communication entre réplicas (5022 par défaut). À ouvrir dans le pare-feu des deux nœuds, faute de quoi le groupe ne se synchronise jamais.
Backup PreferencesPrefer Secondary : les sauvegardes tournent sur le secondaire et n'entament plus les ressources de production.
ListenerLe nom unique auquel les clients se connectent, porté par le cluster : il suit le réplica primaire lors d'une bascule. C'est ce qui rend le basculement transparent — sans listener, il faut reconfigurer chaque client.
Read-Only RoutingRedirige vers le secondaire lisible les clients qui annoncent ApplicationIntent=ReadOnly : les rapports et exports cessent de peser sur le primaire.
Availability modeEffet
Synchronous commitLe primaire attend l'accusé du secondaire avant de valider : aucune perte de données (RPO = 0), au prix d'un peu de latence. Seul mode qui autorise la bascule automatique.
Asynchronous commitAucune latence, mais perte possible des dernières transactions et bascule manuelle. Le mode d'un réplica distant, pour du DR.

Une base n'est pas toujours éligible

L'assistant refuse une base qui n'est pas en recovery model FULL et qui n'a pas eu au moins une sauvegarde complète. Ce n'est pas une contrainte arbitraire : sans chaîne de journaux, il n'y a rien à répliquer en continu.

À retenir

Un groupe de disponibilité tient le RTO (bascule en secondes) et le RPO (nul en mode synchrone) face à une panne de serveur. Il ne protège de rien d'autre. Les sauvegardes restent la seule machine à remonter le temps.
