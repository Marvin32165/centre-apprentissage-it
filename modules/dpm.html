System Center DPM
Sauvegarder et restaurer une infrastructure Windows

Ce que tu sauras faire à la fin

  • Préparer un SQL Server distant pour DPM : service sous gMSA, bonne collation, SSRS, fichiers de support et certificat de confiance.
  • Installer DPM 2025 avec une base distante, et dire quel compte le setup utilise réellement pour créer la base.
  • Ajouter un volume au pool de stockage et déployer les agents de protection sur les serveurs à sauvegarder.
  • Créer un groupe de protection et régler rétention, synchronisation et points de récupération sans les confondre.
  • Restaurer un fichier à son emplacement d'origine ou ailleurs, en choisissant quoi faire s'il existe encore.
  • Diagnostiquer l'erreur 811 depuis le journal du setup jusqu'à sa cause : un certificat que le client SQL refuse.

Prérequis : Windows Server (domaine, DNS) et SQL Server (installation, Configuration Manager, gMSA). Ce module clôt le parcours Infrastructure Windows : après lui, l'examen du parcours.

Le labo : trois serveurs Windows Server 2025 dans le domaine orion.local — un contrôleur de domaine, un SQL Server 2022 et le serveur DPM. C'est le premier des trois TP « System Center » : la supervision passe ensuite par Zabbix à la place de SCOM, et le support par Redmine à la place de SCSM.

01

DPM et son architecture

DPM (System Center Data Protection Manager) est l'outil de sauvegarde de la suite System Center. Il sauvegarde des serveurs Windows — volumes, dossiers, état du système, bases SQL ou Exchange — sur son propre stockage, et les restaure depuis une console unique.

SRV-AD01172.16.50.10Contrôleur de domaine + DNS — porte le compte de service gMSA
SRV-SQL01172.16.50.30SQL Server 2022 + Reporting Services — héberge la base de DPM
SRV-DPM01172.16.50.31Serveur DPM 2025 — console, et un volume réservé au pool de stockage

La base de DPM n'est pas sur le serveur DPM : elle vit sur un SQL Server distant (stand-alone dans l'assistant). C'est ce choix qui rend la préparation de SQL si importante — et qui est à l'origine de la principale panne du TP (chapitre 08).

Le vocabulaire

TermeCe que c'est
Agent de protectionService installé sur chaque serveur à sauvegarder. Sans agent, DPM ne voit pas le serveur.
Pool de stockageLes volumes du serveur DPM qui reçoivent les sauvegardes. DPM les formate et se les réserve.
Groupe de protectionDes données à sauvegarder + une seule politique : où, à quelle fréquence, combien de temps.
RéplicaLa première copie complète des données sur DPM.
SynchronisationRecopie des modifications vers le réplica, pour le tenir à jour.
Point de récupérationUne version figée et restaurable des données.
Vérification de cohérenceCompare le réplica à la source et corrige les écarts.

À retenir

Trois rôles, trois machines : l'annuaire (comptes, gMSA), la base (SQL distant) et DPM (console et stockage). Sur les serveurs protégés, un agent ; côté politique, des groupes de protection. Et une distinction qui revient partout : on synchronise souvent, mais on ne restaure qu'un point de récupération.

02

Le compte de service gMSA pour SQL

SQL Server tourne sous un gMSA (group Managed Service Account) : un compte de service géré par l'AD, dont le mot de passe change tout seul et que personne ne connaît. Le principe est détaillé dans le module SQL Server ; voici la séquence du TP.

Sur le contrôleur de domaine

D'abord la clé racine KDS, obligatoire avant tout gMSA :

PowerShell — SRV-AD01
# -10 h : clé utilisable tout de suite (lab seulement)
Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))
Get-KdsRootKey                # voir la clé en place

Puis une OU, un groupe qui contient le compte ordinateur du serveur SQL, et le compte lui-même, autorisé pour ce groupe :

PowerShell — SRV-AD01
New-ADServiceAccount gMSA-SQL -DNSHostName gmsa-sql.orion.local -PrincipalsAllowedToRetrieveManagedPassword GG-gMSA-SQL

Le −10 h, réservé au lab

Une clé KDS n'est normalement utilisable qu'après 10 heures, le temps d'être répliquée sur tous les contrôleurs de domaine. L'antidater la rend utilisable tout de suite : pratique en TP, à ne pas faire sur un domaine qui a plusieurs DC.

Sur le serveur SQL

SQL doit voir sa nouvelle appartenance au groupe : redémarrer le serveur, ou purger les tickets Kerberos du compte ordinateur. Puis tester le compte :

PowerShell — SRV-SQL01
klist purge -li 0x3e7
gpupdate /target:computer
Install-WindowsFeature RSAT-AD-PowerShell
Test-ADServiceAccount gMSA-SQL      # doit répondre True

À retenir

Clé KDS sur le DC, gMSA autorisé pour un groupe qui contient le serveur SQL, tickets rafraîchis côté SQL — et Test-ADServiceAccount doit répondre True avant d'aller plus loin.

03

Préparer SQL pour DPM

DPM est exigeant sur le serveur SQL qui porte sa base. Chaque point ci-dessous, oublié, se paie au moment du setup.

  1. 01
    SQL Server 2022Collation SQL_Latin1_General_CP1_CI_AS — DPM n'en accepte pas d'autre. Service SQL Server sous ORION\gMSA-SQL$, mot de passe vide (c'est l'AD qui le gère). Fichiers des bases sur un volume de données, pas sur C:.
  2. 02
    TCP/IP activéSQL Server Configuration Manager > Protocols for MSSQLSERVER > TCP/IP, puis redémarrage du service.
  3. 03
    Reporting ServicesInstallé et configuré (bases ReportServer et ReportServerTempDB) : DPM s'en sert pour ses rapports.
  4. 04
    DPM Support FilesDepuis le média DPM, l'option SQL Prep, installée sur le serveur SQL.
  5. 05
    Un certificat de confianceSans quoi le setup DPM échoue en erreur 811 : c'est tout le chapitre 08.

À retenir

La check-list de SQL : collation SQL_Latin1_General_CP1_CI_AS, service sous le gMSA, TCP/IP activé, SSRS configuré, DPM Support Files installés, certificat approuvé par le serveur DPM. La collation est la seule qui ne se rattrape pas sans réinstaller l'instance.

04

Installer DPM et prendre la console en main

Sur le futur serveur DPM : installer SSMS et sqlcmd, lancer le setup de DPM 2025, Install > Data Protection Manager, accepter la licence.

Écran / champValeur
Prerequisites checkUse stand-alone SQL Server
Instance of SQL Serverle nom du serveur SQL : SRV-SQL01
User Name / Passwordun compte administrateur (en production : un compte dédié)
DomainORION — le nom NetBIOS, pas orion.local

Le compte qui compte vraiment

Le setup crée la base en lançant un script avec sqlcmd -E : en authentification Windows de la session ouverte, pas avec le compte saisi dans l'assistant. Il faut donc être connecté sur le serveur DPM avec un compte du domaine qui est sysadmin sur SQL. Le setup crée ensuite sur SQL la base DPMDB_<nom du serveur> et un login pour le compte ordinateur de DPM (ORION\SRV-DPM01$).

La console : cinq espaces

En bas à gauche ; le ruban du haut change selon l'espace choisi. Le setup pose aussi un raccourci DPM Management Shell, le PowerShell avec le module DPM.

EspaceSert à
MonitoringLes alertes (critiques, avertissements, infos) et les jobs
ProtectionCréer et suivre les groupes de protection
RecoveryParcourir les points de récupération et restaurer
ReportingSix rapports : utilisation disque, récupérations, état des points…
ManagementLes agents (Production Servers), le stockage (Disk Storage), Azure, bandes

Tant qu'aucun groupe n'existe, l'espace Protection rappelle lui-même l'ordre à suivre : du stockage dans le pool, puis un agent sur chaque serveur à protéger. C'est l'ordre du chapitre suivant.

À retenir

SQL distant, domaine en NetBIOS, et une session ouverte avec un compte sysadmin sur SQL : c'est elle, et non le compte de l'assistant, qui crée la base.

05

Le stockage, puis les agents

Avant de protéger quoi que ce soit, DPM a besoin de deux choses : un endroit où écrire, et un agent sur chaque serveur à lire.

Le pool de stockage

Management > Disk Storage > Add : choisir le volume dans Available volumes, Add >, lui donner un Friendly Name, OK. Il apparaît ensuite dans le pool, état Healthy.

DPM formate le volume

Tout ce qui est dessus est perdu, et il est reformaté en ReFS. Dans l'explorateur, son nom devient un identifiant (GUID) : il appartient à DPM, on n'y dépose rien à la main.

Les agents de protection

Management > Production Servers > Add :

  1. 01
    Type de serveurWindows Servers (l'autre choix sert aux VM VMware).
  2. 02
    MéthodeInstall agents : DPM pousse l'agent lui-même. Attach agents sert à un serveur derrière un pare-feu, ou dont l'agent est déjà installé : DPM se contente de l'enregistrer.
  3. 03
    OrdinateursLes ordinateurs du domaine sont listés : ici le DC et le serveur SQL, Add >. Un ordinateur d'un autre domaine se saisit par son nom complet.
  4. 04
    IdentifiantsUn compte administrateur des ordinateurs cibles ; DPM ne s'en sert que pour installer l'agent.
  5. 05
    RedémarrageYes : DPM redémarre les serveurs si l'installation l'exige. Puis Install — Success pour chaque serveur.

Les serveurs apparaissent alors dans Unprotected computers with protection agent : ils ont un agent, mais restent non protégés tant qu'ils ne sont dans aucun groupe de protection.

À retenir

L'ordre est imposé : stockage d'abord (un volume que DPM formate et se réserve), agents ensuite. Un agent installé ne protège rien à lui seul — c'est le groupe de protection qui décide quoi sauvegarder.

06

Le groupe de protection

Un groupe de protection réunit des données et leur applique une politique unique. Protection > New, puis Next sur l'écran d'accueil.

ÉcranChoix du TP
Select protection group typeServers (Clients sert aux postes de travail)
Select group membersLe volume de données du DC et celui du serveur SQL. Par serveur : All Shares, All Volumes (dépliables jusqu'aux dossiers), System Protection (état du système ou Bare Metal Recovery), et les bases sur un SQL ou un Exchange
Select data protection methodNom Directory_Weekly, short-term protection using: Disk (Azure et bandes grisés : rien de configuré)
Specify short-term goalsRétention 5 jours, synchronisation toutes les 15 min, un point de récupération le vendredi à 19 h (via Modify…)
Review disk storageDPM calcule la place à réserver dans le pool pour chaque membre
Choose replica creation methodAutomatically over the network, Now (Manually passe par un support amovible, pour de gros volumes)
Choose consistency check optionsSeulement si un réplica devient incohérent
SummaryRelire, puis Create Group

Le volume du pool sur le serveur DPM n'est pas proposé comme membre : il reçoit les sauvegardes, DPM ne le protège pas lui-même. Une fois le groupe créé, ses membres passent par Replica creation in progress, puis OK avec un premier point de récupération.

Trois réglages à ne pas confondre

Synchronisation

  • Recopie les modifications vers le réplica.
  • Ici toutes les 15 min — ou juste avant chaque point de récupération.
  • Tient le réplica à jour, mais ne crée rien de restaurable.

Point de récupération

  • Une version figée et restaurable.
  • Par défaut 8 h, 12 h et 18 h ; ici le vendredi à 19 h.
  • La rétention dit combien de jours on les garde.

Exercice 1 — que peut-on restaurer ?

Avec le groupe du TP (synchronisation toutes les 15 min, un point de récupération le vendredi à 19 h, rétention 5 jours), un fichier est effacé par erreur le mercredi à 10 h. Une collègue propose de « restaurer l'état de 9 h 45, puisque DPM synchronise toutes les 15 minutes ». Est-ce possible ?

Afficher la correction

Non. La synchronisation tient le réplica à jour, mais on ne restaure qu'un point de récupération. Ici le dernier date du vendredi précédent à 19 h (encore dans les 5 jours de rétention) : on récupère le fichier tel qu'il était ce vendredi-là, et tout ce qui a été modifié depuis lundi est perdu. Pour des fichiers qui changent tous les jours, il faut des points de récupération quotidiens — les trois points par jour proposés par défaut existent pour ça — et une rétention qui couvre largement l'intervalle entre deux points.

À retenir

Un groupe = des membres + une politique : rétention, fréquence de synchronisation, points de récupération, création du réplica, vérification de cohérence. Et la question à se poser toujours : quel point de récupération pourrai-je restaurer, à n'importe quel moment de la semaine ?

07

Suivre les jobs, restaurer

Chaque opération de DPM est un job. Et une sauvegarde n'a de valeur que le jour où on la restaure : le TP s'arrête donc sur une restauration réelle.

Les jobs

Monitoring > Jobs > All jobs, regroupés avec Group by (statut, groupe, ordinateur, type). Les filtres à gauche (All jobs in progress, Failed jobs for yesterday and today…) aident à trouver ce qui a échoué.

Type de jobRôle
Replica creationLa première copie complète
Recovery pointUne version restaurable — quelques secondes une fois le réplica en place
Library rescanL'inventaire des bandes, lancé à l'installation

Restaurer un fichier

  1. 01
    Choisir le pointEspace Recovery : déplier le domaine, l'ordinateur, All Protected Volumes, le volume. Les dates en gras du calendrier ont des points de récupération ; choisir la date, puis l'heure dans Recovery time.
  2. 02
    SélectionnerLes fichiers, puis Recover : le Recovery Wizard s'ouvre sur un résumé de la sélection.
  3. 03
    Où restaurerRecover to the original location, ou alternate location pour un autre dossier.
  4. 04
    Si le fichier existe encoreCreate copy restaure à côté, Skip ne touche à rien, Overwrite remplace. Restore security : garder les droits de la destination ou ceux du point de récupération.
  5. 05
    RecoverPendant la restauration, les synchronisations du serveur concerné sont annulées. Le TP : Successful en 5 secondes.

À retenir

Une sauvegarde jamais restaurée n'est pas une sauvegarde, c'est une hypothèse. La restauration se teste dès le premier point de récupération, et Create copy est le choix prudent : il ne détruit rien de ce qui existe encore.

08

Dépanner l'erreur 811

Premier setup du TP : « The DPM database was not created », erreur 811. Le message ne dit rien de la cause. Le journal, si.

Lire le journal

C:\Program Files\Microsoft System Center 2025\DPM\DPMLogs\DpmSetup.log montre la base créée, puis l'exécution d'un script :

DpmSetup.log (extrait)
CREATE DATABASE ... DPMDB_...           → la base est créée
Execute the SQL script
  FileName  = ...\ODBC\180\Tools\Binn\SQLCMD.EXE
  Arguments = -b -E -d DPMDB_... -i master.sql -r -S SRV-SQL01
  Error code = 1                         → échec dans la même seconde

Les erreurs 14262 et 15151 qui suivent sont des conséquences : c'est le setup qui défait ce qu'il vient de commencer. Ce ne sont pas des causes.

Reproduire à la main

On relance, depuis le serveur DPM, la connexion du setup :

PowerShell — SRV-DPM01
& 'C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\180\Tools\Binn\SQLCMD.EXE' -b -E -S SRV-SQL01 -Q "SELECT SUSER_SNAME(), @@VERSION"
# Sqlcmd: Error: Microsoft ODBC Driver 18 for SQL Server : SSL Provider:
# The certificate chain was issued by an authority that is not trusted.

La cause, et la correction

Depuis sa version 18, le pilote ODBC chiffre toujours la connexion et exige un certificat de confiance. Or SQL Server présente par défaut un certificat auto-généré. Changer de version de pilote ne sert à rien : le setup appelle ce sqlcmd par un chemin écrit en dur. La correction se fait en deux temps :

Sur le serveur SQL

  • Créer un certificat pour le nom court et le nom complet du serveur.
  • Donner au compte du service SQL (le gMSA) la lecture de sa clé privée.
  • Le choisir pour l'instance (onglet Certificate du Configuration Manager), redémarrer SQL, l'Agent et SSRS, exporter le certificat.

Sur le serveur DPM

  • Importer ce certificat dans les autorités de certification racines de confiance.
  • Refaire le test sqlcmd : il doit répondre.
  • Désinstaller la tentative ratée, vérifier qu'il ne reste pas de base DPMDB_*, relancer le setup.

Deux pièges autour de la réinstallation

La liste « n'a pas pu supprimer » affichée à la désinstallation est générique : vérifier l'état réel avant de nettoyer quoi que ce soit. Et l'invitation à « effacer ou formater le stockage » ne vise jamais le disque système entier quand le pool n'est qu'une partition de ce disque.

Exercice 2 — la bonne erreur

Un journal de setup contient, dans l'ordre : la création de la base, l'exécution de master.sql avec Error code = 1, puis « 14262 @category_name ... does not exist » et « 15151 Cannot drop the role ». Un forum conseille de créer la catégorie manquante dans msdb. Que fais-tu ?

Afficher la correction

On ne crée rien dans msdb : 14262 et 15151 arrivent après l'échec, pendant le retour arrière du setup. La première erreur est le script lancé par sqlcmd : on reproduit cet appel à la main avec les mêmes arguments, et le vrai message apparaît — ici le certificat refusé. Règle générale : dans un journal, la cause est la première erreur, pas la plus bavarde.

À retenir

Erreur 811 = le sqlcmd ODBC 18 du setup refuse le certificat auto-généré de SQL. Remède : un certificat dédié sur SQL, approuvé sur DPM. C'est la chaîne de confiance déjà vue avec Exchange & PKI : un client ne fait confiance qu'à un certificat qu'il peut rattacher à une autorité qu'il connaît.
