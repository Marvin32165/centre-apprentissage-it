Du premier hello-world à une application multi-conteneurs décrite dans un fichier

Ce module prépare Homelab & Self-hosting, où chaque service auto-hébergé tourne en conteneur.

01

Conteneur ou VM ?

Docker est un système de packaging : il livre une application avec son environnement. Pour cela il isole des processus — il ne virtualise pas une machine.

Machine virtuelle

  • Un hyperviseur (type 1 ou type 2) émule du matériel.
  • Chaque VM embarque un système complet, noyau compris.
  • Lourde à démarrer, mais isolation forte.

Conteneur

  • Des processus isolés sur le noyau de l'hôte.
  • Ni hyperviseur, ni OS virtualisé : démarrage en une seconde.
  • Même architecture que l'hôte (x86_64 ≠ ARM).

Les deux piliers du noyau

  • namespaces — le processus ne voit pas les autres (processus, réseau, montages, utilisateurs).
  • cgroups — le processus ne consomme que ce qu'on lui accorde (CPU, mémoire).

Ce qu'on appelle « Docker Engine »

La commande docker n'est qu'un client. La chaîne complète : CLI → démon dockerd → containerd → runc → namespaces / cgroups. Le client parle au démon par la socket /var/run/docker.sock.

Docker dérive de LXC : LXC fournit des conteneurs « système » (un OS bas niveau, comme les CT de Proxmox), Docker des conteneurs d'application, avec l'outillage pour les construire et les distribuer.

À retenir

Un conteneur est un processus isolé, pas une petite VM : namespaces pour ne pas voir, cgroups pour ne pas déborder, et le noyau de l'hôte pour tout le monde.

02

Images, couches & registre

Une image est le modèle, le conteneur son exécution. Tout le vocabulaire de Docker découle de la façon dont les images sont stockées.

NotionCe qu'il faut en retenir
Image & UFSDes couches empilées par un système de fichiers en union (overlay2), partagées entre tous les conteneurs qui les utilisent.
Lecture seule & COWLes couches de l'image ne changent jamais : un conteneur écrit dans sa propre couche, et seule la différence est stockée (copy-on-write).
RegistreDocker Hub, public : docker pull pour télécharger, docker push pour publier. Un registre interne est possible.
VolumeUn répertoire de l'hôte monté dans le conteneur : la seule façon de garder des données (chapitre 06).
Composition / orchestrationCompose décrit une application de plusieurs conteneurs ; Swarm ou Kubernetes gèrent un cluster.
bash
docker search nginx        # chercher sur le Docker Hub
docker pull ubuntu:latest  # télécharger une image (nom:tag)
docker images              # les images présentes
docker rmi ubuntu:latest   # supprimer une image (rm = conteneur)

Officiel ou communautaire

Sur le Docker Hub, préférer les images officielles vérifiées : une image communautaire exécute le code de quelqu'un d'autre sur ta machine.

À retenir

L'image est immuable et partagée ; ce qu'un conteneur modifie reste dans sa couche d'écriture et disparaît avec lui.

03

Installer Docker proprement

Deux paquets possibles, docker.io (maintenu par la distribution) ou docker-ce (Docker Inc.) — l'un ou l'autre, jamais les deux. Le cours installe docker-ce depuis le dépôt officiel.

1
Préparer APT

ca-certificates, curl et gnupg, puis le dossier des clés /etc/apt/keyrings.

2
Importer la clé du dépôt

APT refuse un paquet dont il ne peut vérifier la signature : la clé prouve que les paquets viennent de Docker.

3
Déclarer le dépôt

Une ligne deb [arch=… signed-by=…] dans /etc/apt/sources.list.d/docker.list.

4
Installer

Le moteur, le client, containerd et les plugins Buildx et Compose.

bash — Debian / Ubuntu
sudo apt update
sudo apt install ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/$(. /etc/os-release && echo $ID)/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# étape 3 : la ligne du dépôt, écrite par tee (sudo echo > échouerait)
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
https://download.docker.com/linux/$(. /etc/os-release && echo $ID) \
$(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run hello-world

Ce qu'on ne fait pas en production

  • Le script get-docker.sh : code téléchargé exécuté en root, dernière version imposée (y compris majeure), pas prévu pour les mises à jour. Outil de labo seulement.
  • Laisser la version flotter : on choisit la version (apt-cache madison docker-ce) puis on la bloque avec apt-mark hold.
  • Ajouter n'importe qui au groupe docker : ce groupe équivaut à root, puisqu'un membre peut monter tout le disque de l'hôte dans un conteneur.

Pièges rencontrés en cours

Un guillemet typographique » copié depuis une diapo laisse le shell en attente (>) ; un espace après un \ de fin de ligne coupe la commande ; un « permission denied » sur la socket juste après l'installation signifie seulement qu'il manque sudo.

À retenir

En production : dépôt officiel, version figée, pas de script tout-en-un. Les mises à jour passent ensuite par le gestionnaire de paquets, comme le reste du système.

04

Lancer et piloter des conteneurs

docker run crée et lance un conteneur. Ses options vont avant le nom de l'image : tout ce qui suit l'image est la commande exécutée dedans.

OptionRôle
-i / -tinteractif / ouvrir un terminal — ensemble : -it
-den arrière-plan (démon)
--namenommer le conteneur plutôt que de subir un nom aléatoire
--rmsupprimer le conteneur dès qu'il s'arrête
-v / -pmonter un volume / publier un port (chapitres 06 et 07)
--privilegeddroits root sur l'hôte — à éviter

Entrer et sortir sans tout arrêter

GesteEffet
Ctrl+D ou exitquitte le shell ; si c'est le processus principal, le conteneur s'arrête (il n'est pas supprimé)
Ctrl+P puis Ctrl+Qse détacher sans arrêter le conteneur
docker exec -it NOM bashouvrir un nouveau shell : le quitter n'arrête rien
docker attach NOMse rattacher au processus principal — un Ctrl+D y arrête le conteneur
bash
docker run -it ubuntu:latest /bin/bash  # options AVANT l'image
docker ps --all                         # tous les conteneurs, arrêtés compris
docker stop NOM                         # arrêt propre : SIGTERM, puis SIGKILL après 10 s
docker start NOM                        # relancer un conteneur arrêté
docker logs --follow --tail 10 NOM      # journaux en continu
docker stats --no-stream                # ressources à un instant T
docker rm NOM                           # supprimer un conteneur arrêté
docker system prune                     # ménage des objets orphelins

PID 1

Dans un conteneur, le processus n° 1 est l'application, pas systemd : systemctl n'y fonctionne pas. Et ce qu'on installe à la main dans un conteneur disparaît quand il est recréé depuis son image.

À retenir

Pour intervenir dans un conteneur qui tourne : docker exec -it, et Ctrl+P Ctrl+Q pour en sortir. attach et Ctrl+D arrêtent le service.

05

Écrire un Dockerfile

Un Dockerfile est un fichier texte, une instruction par ligne, lu par docker build. Il produit une image ; le conteneur viendra ensuite avec docker run.

Dockerfile — l'exemple Python du cours
FROM python:3.8
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
InstructionQuandRôle
FROMbuildimage de base, toujours en premier (FROM scratch si aucune)
ARG / ENVbuild / build et exécutionparamètres de construction / variables d'environnement
WORKDIRbuildrépertoire de travail des instructions suivantes
COPY / ADDbuildcopier depuis le contexte ; ADD en fait plus, de façon implicite : préférer COPY
RUNbuildexécuter une commande ; chaque RUN crée une couche
EXPOSE—documente un port : ne publie rien
CMDlancementcommande par défaut, remplaçable en ligne de commande
ENTRYPOINTlancementcommande fixe ; CMD lui fournit alors ses arguments
bash
docker build -t mon-app .               # le point = le CONTEXTE de build
docker build -t mon-app -f AUTRE_NOM .  # fichier qui ne s'appelle pas Dockerfile
docker run -p 8000:5000 mon-app         # hôte:conteneur

Forme tableau

CMD ["python", "app.py"] lance le programme en PID 1. La forme chaîne CMD python app.py passe par /bin/sh -c : le shell ne transmet pas SIGTERM, et docker stop finit par tuer le conteneur au bout de 10 secondes.

À retenir

RUN construit, CMD propose, ENTRYPOINT impose. Et docker build prend un dossier (le contexte), pas un fichier : sans le point final, rien ne se construit.

06

Volumes & données persistantes

Les données écrites dans un conteneur disparaissent avec lui. Un volume est un stockage géré en dehors du cycle de vie du conteneur, et réutilisable par plusieurs.

bash
docker volume create mes_donnees
docker run -d --name web1 -v mes_donnees:/usr/share/nginx/html nginx
docker run -d --name web2 -v mes_donnees:/usr/share/nginx/html:ro nginx  # lecteur seul
docker volume ls
docker volume inspect mes_donnees                                        # → Mountpoint : /var/lib/docker/volumes/mes_donnees/_data
docker volume rm mes_donnees                                             # refusé tant qu'un conteneur l'utilise
  • docker volume prune ne supprime que les volumes anonymes inutilisés ; avec -a, les volumes nommés y passent aussi — donc des données.
  • Drivers : local par défaut ; NFS et CIFS passent par local avec des --opt ; d'autres drivers existent (GlusterFS, Azure File…).
  • Emplacement par défaut : data-root dans /etc/docker/daemon.json, à fixer avant de créer des données.
  • Partager un volume entre conteneurs : un seul écrivain, les autres en :ro.

À retenir

Tout ce qui doit survivre au conteneur — base de données, fichiers d'un site — va dans un volume monté au chemin attendu par l'application. Le conteneur, lui, reste jetable.

07

Le réseau des conteneurs

Par défaut, les conteneurs vivent derrière un pont docker0 (172.17.0.1/16) et un NAT : ils sortent librement, mais personne ne peut les joindre directement de l'extérieur.

bash
docker run -d -p 8080:80 nginx  # publier : port 80 du conteneur sur 8080 de l'hôte
docker network ls               # bridge, host, none installés d'office
docker network create --driver bridge labnet
docker run -d --name db --network labnet postgres:16
docker network inspect labnet   # conteneurs attachés, MAC, IPv4
docker network disconnect labnet db
DriverComportement
bridgeswitch virtuel + NAT ; sur un bridge créé, les conteneurs se joignent par leur nom
hostle conteneur prend l'interface et l'IP de l'hôte : plus de NAT, plus de ports partageables
macvlanune sous-interface dédiée par conteneur, directement sur le réseau physique
noneisolation totale : loopback seulement
overlayun seul réseau réparti sur plusieurs hôtes (Swarm)

Lecture de -p

Toujours hôte:conteneur. Et un port publié reste soumis au pare-feu de l'hôte : EXPOSE dans le Dockerfile n'ouvre rien du tout.

À retenir

Entrant : il faut un mappage de port. Entre conteneurs : un réseau créé, sur lequel le nom du conteneur sert de nom DNS.

08

Docker Compose

Les options de docker run sont nombreuses, à retaper à chaque fois, et une application a souvent plusieurs conteneurs. Compose les écrit une fois pour toutes dans un fichier YAML.

compose.yaml — application + base, comme au TP
services:
  app:
    build: .                         # image construite depuis le Dockerfile du dossier
    ports:
      - "8080:5000"
    environment:
      DB_HOST: db                    # le DNS interne résout le nom du service
    depends_on:
      - db
    restart: unless-stopped
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: change-moi  # obligatoire pour l'image postgres
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:
bash
docker compose up -d          # lancer, en arrière-plan
docker compose up -d --build  # après une modification du code
docker compose ps
docker compose logs app
docker compose exec app bash
docker compose down           # conteneurs + réseau supprimés, volumes GARDÉS
docker compose down -v        # … et les volumes : la base repart de zéro

Ce que le TP a montré

  • Seul le service qui a une clé ports: est joignable de l'extérieur.
  • depends_on fixe l'ordre de lancement, pas l'attente que la base soit prête.
  • Le code est copié dans l'image : sans --build, une modification d'app.py ne change rien.
  • Compose crée tout seul un réseau <projet>_default et un DNS interne ; le projet porte le nom du dossier.
  • restart: vaut no par défaut ; always, on-failure[:3] et unless-stopped sont les autres choix.

À retenir

Un compose.yaml est la mémoire d'une application : services, ports, volumes et redémarrage écrits une fois. down garde les données, down -v les efface.
