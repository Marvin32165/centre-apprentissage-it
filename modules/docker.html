01

Conteneur ou VM ?

Docker est un système de packaging : il livre une application avec son environnement. Pour cela il isole des processus — il ne virtualise pas une machine.

Machine virtuelle

  • Un hyperviseur (type 1 ou type 2) émule du matériel.
  • Chaque VM embarque un système complet, noyau compris.
  • Lourde à démarrer, mais isolation forte.

Conteneur

  • Des processus isolés sur le noyau de l'hôte.
  • Ni hyperviseur, ni OS virtualisé : démarrage en une seconde.
  • Même architecture que l'hôte (x86_64 ≠ ARM).

Les deux piliers du noyau

  • namespaces — le processus ne voit pas les autres (processus, réseau, montages, utilisateurs).
  • cgroups — le processus ne consomme que ce qu'on lui accorde (CPU, mémoire).

Ce qu'on appelle « Docker Engine »

La commande docker n'est qu'un client. La chaîne complète : CLI → démon dockerd → containerd → runc → namespaces / cgroups. Le client parle au démon par la socket /var/run/docker.sock.

Docker s'appuyait à ses débuts (2013-2014) sur LXC, avant d'utiliser sa propre bibliothèque, devenue runc. La différence d'usage demeure : LXC fournit des conteneurs « système » (un OS presque complet, comme les CT de Proxmox), Docker des conteneurs d'application — un processus principal — avec l'outillage pour les construire et les distribuer.

À retenir

Un conteneur est un processus isolé, pas une petite VM : namespaces pour ne pas voir, cgroups pour ne pas déborder, et le noyau de l'hôte pour tout le monde.

Question éclair

Sur ton serveur Debian (noyau Linux, processeur x86_64), un collègue veut lancer une image construite pour Windows Server. Que se passe-t-il ?

Un conteneur n'apporte pas de noyau : l'image doit correspondre au système (Linux / Windows) et à l'architecture (x86_64 / ARM) de l'hôte. Pour un autre OS, il faut une VM.

02

Images, couches & registre

Une image est le modèle, le conteneur son exécution. Tout le vocabulaire de Docker découle de la façon dont les images sont stockées.

NotionCe qu'il faut en retenir
Image & UFSDes couches empilées par un système de fichiers en union, partagées entre tous les conteneurs qui les utilisent : pilote overlay2 jusqu'à Docker Engine 28 (et sur une installation mise à jour), store d'images containerd sur une installation neuve de la version 29.
Lecture seule & COWLes couches de l'image ne changent jamais : un conteneur écrit dans sa propre couche, et seule la différence est stockée (copy-on-write).
RegistreDocker Hub, public : docker pull pour télécharger, docker push pour publier. Un registre interne est possible.
VolumeUn stockage géré par Docker (/var/lib/docker/volumes/…), monté dans le conteneur. À ne pas confondre avec le bind mount, un dossier choisi de l'hôte (-v /srv/site:/usr/share/nginx/html). Les deux survivent au conteneur (chapitre 06).
Composition / orchestrationCompose décrit une application de plusieurs conteneurs ; Swarm ou Kubernetes gèrent un cluster.
bash
docker search nginx        # chercher sur le Docker Hub
docker pull ubuntu:latest  # télécharger une image (nom:tag)
docker images              # les images présentes
docker rmi ubuntu:latest   # supprimer une image (rm = conteneur)

Officiel ou communautaire

Sur le Docker Hub, préférer les images officielles vérifiées : une image communautaire exécute le code de quelqu'un d'autre sur ta machine.

À retenir

L'image est immuable et partagée ; ce qu'un conteneur modifie reste dans sa couche d'écriture et disparaît avec lui.

03

Installer Docker proprement

Deux paquets possibles, docker.io (maintenu par la distribution) ou docker-ce (Docker Inc.) — l'un ou l'autre, jamais les deux. Le cours installe docker-ce depuis le dépôt officiel.

1
Préparer APT

ca-certificates, curl et gnupg, puis le dossier des clés /etc/apt/keyrings.

2
Importer la clé du dépôt

APT refuse un paquet dont il ne peut vérifier la signature : la clé prouve que les paquets viennent de Docker.

3
Déclarer le dépôt

Une ligne deb [arch=… signed-by=…] dans /etc/apt/sources.list.d/docker.list.

4
Installer

Le moteur, le client, containerd et les plugins Buildx et Compose.

bash — Debian / Ubuntu
sudo apt update
sudo apt install ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/$(. /etc/os-release && echo $ID)/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# étape 3 : la ligne du dépôt, écrite par tee (sudo echo > échouerait)
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
https://download.docker.com/linux/$(. /etc/os-release && echo $ID) \
$(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run hello-world

La documentation Docker actuelle télécharge la clé telle quelle (docker.asc, sans gnupg ni --dearmor) et déclare le dépôt dans un fichier au format DEB822, /etc/apt/sources.list.d/docker.sources. La méthode du cours, ci-dessus, reste lue par APT.

Ce qu'on ne fait pas en production

  • Le script get-docker.sh : code téléchargé exécuté en root, dernière version imposée (y compris majeure), pas prévu pour les mises à jour. Outil de labo seulement.
  • Laisser la version flotter : on choisit la version (apt-cache madison docker-ce) puis on la bloque avec apt-mark hold.
  • Ajouter n'importe qui au groupe docker : ce groupe équivaut à root, puisqu'un membre peut monter tout le disque de l'hôte dans un conteneur.

Pièges rencontrés en cours

Un guillemet typographique » copié depuis une diapo laisse le shell en attente (>) ; un espace après un \ de fin de ligne coupe la commande ; un « permission denied » sur la socket juste après l'installation signifie seulement qu'il manque sudo.

À retenir

En production : dépôt officiel, version figée, pas de script tout-en-un. Les mises à jour passent ensuite par le gestionnaire de paquets, comme le reste du système.

04

Lancer et piloter des conteneurs

docker run crée et lance un conteneur. Ses options vont avant le nom de l'image : tout ce qui suit l'image est la commande exécutée dedans.

OptionRôle
-i / -tinteractif / ouvrir un terminal — ensemble : -it
-den arrière-plan (démon)
--namenommer le conteneur plutôt que de subir un nom aléatoire
--rmsupprimer le conteneur dès qu'il s'arrête
-v / -pmonter un volume / publier un port (chapitres 06 et 07)
--privilegeddroits root sur l'hôte — à éviter

Entrer et sortir sans tout arrêter

GesteEffet
Ctrl+D ou exitquitte le shell ; si c'est le processus principal, le conteneur s'arrête (il n'est pas supprimé)
Ctrl+P puis Ctrl+Qse détacher sans arrêter le conteneur
docker exec -it NOM bashouvrir un nouveau shell : le quitter n'arrête rien
docker attach NOMse rattacher au processus principal — un Ctrl+D y arrête le conteneur
bash
docker run -it ubuntu:latest /bin/bash  # options AVANT l'image
docker ps --all                         # tous les conteneurs, arrêtés compris
docker stop NOM                         # arrêt propre : SIGTERM, puis SIGKILL après 10 s
docker start NOM                        # relancer un conteneur arrêté
docker logs --follow --tail 10 NOM      # journaux en continu
docker stats --no-stream                # ressources à un instant T
docker rm NOM                           # supprimer un conteneur arrêté
docker system prune                     # ménage des objets orphelins

Pas à pas

Ce qui se passe pendant docker run -d --name web -p 8080:80 nginx

  1. Étape 1 · CLI → dockerd

    Le client transmet la demande au démon

    docker envoie la requête à dockerd par la socket /var/run/docker.sock. Le client ne fait rien d'autre.

    Le client n'est qu'une télécommande : c'est le démon qui travaille, en root.

  2. Étape 2 · dockerd → registre

    L'image est cherchée, téléchargée si absente

    Pas de nginx:latest en local ? Le démon le tire du Docker Hub, couche par couche (Pulling fs layer). Les couches déjà présentes ne sont pas retéléchargées.

    Sans tag, c'est latest. Les couches sont partagées entre images.

  3. Étape 3 · dockerd

    Le conteneur est créé

    Une couche d'écriture vide est posée sur les couches de l'image (overlay2, ou le store containerd sur une installation neuve de Docker Engine 29), le conteneur reçoit un identifiant et le nom web. À ce stade il existe (docker ps -a) mais ne tourne pas : c'est ce que fait docker create seul.

    Image en lecture seule + couche d'écriture = le conteneur.

  4. Étape 4 · dockerd → noyau

    Le réseau est branché

    Un namespace réseau est créé ; une paire d'interfaces veth relie le conteneur au pont docker0, qui lui attribue une adresse en 172.17.0.x. Le -p 8080:80 devient une règle de NAT (DNAT) sur l'hôte.

    veth + pont docker0 + règle DNAT pour le port publié.

  5. Étape 5 · containerd → runc

    Le processus principal démarre, isolé

    containerd confie le lancement à runc, qui crée les namespaces (PID, montages, nom d'hôte…), applique les cgroups, puis exécute la commande de l'image : nginx devient le PID 1 du conteneur.

    Le conteneur vit tant que son PID 1 vit.

  6. Étape 6 · conteneur → dockerd

    La sortie part dans les journaux

    Ce que nginx écrit sur sa sortie standard et sa sortie d'erreur est capté par Docker : c'est ce que montre docker logs web. Avec -d, le terminal est rendu tout de suite.

    docker logs = stdout et stderr du PID 1.

  7. Étape 7 · docker stop → PID 1

    L'arrêt : SIGTERM, puis SIGKILL

    docker stop web envoie SIGTERM au PID 1 et attend 10 secondes ; s'il n'est pas sorti, SIGKILL. Le conteneur passe en Exited : sa couche d'écriture existe toujours, jusqu'à docker rm.

    Arrêté n'est pas supprimé ; rm efface la couche d'écriture, pas les volumes.

PID 1

Dans un conteneur, le processus n° 1 est l'application, pas systemd : systemctl n'y fonctionne pas. Et ce qu'on installe à la main dans un conteneur disparaît quand il est recréé depuis son image.

À retenir

Pour intervenir dans un conteneur qui tourne : docker exec -it, et Ctrl+P Ctrl+Q pour en sortir. attach et Ctrl+D arrêtent le service.

Question éclair

Tu as fait docker attach web sur un conteneur dont le processus principal est un shell, puis tapé exit. docker ps ne montre plus web. Où est-il ?

Quitter le PID 1 arrête le conteneur. docker ps -a le montre en Exited, et docker start -ai web le relance. Pour intervenir sans risque : docker exec -it web bash.

05

Écrire un Dockerfile

Un Dockerfile est un fichier texte, une instruction par ligne, lu par docker build. Il produit une image ; le conteneur viendra ensuite avec docker run.

Dockerfile — l'exemple Python du cours
FROM python:3.8
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
InstructionQuandRôle
FROMbuildimage de base, toujours en premier (FROM scratch si aucune)
ARG / ENVbuild / build et exécutionparamètres de construction / variables d'environnement
WORKDIRbuildrépertoire de travail des instructions suivantes
COPY / ADDbuildcopier depuis le contexte ; ADD en fait plus, de façon implicite : préférer COPY
RUNbuildexécuter une commande ; chaque RUN crée une couche
EXPOSE—documente un port : ne publie rien
CMDlancementcommande par défaut, remplaçable en ligne de commande
ENTRYPOINTlancementcommande fixe ; CMD lui fournit alors ses arguments
bash
docker build -t mon-app .               # le point = le CONTEXTE de build
docker build -t mon-app -f AUTRE_NOM .  # fichier qui ne s'appelle pas Dockerfile
docker run -p 8000:5000 mon-app         # hôte:conteneur

Forme tableau

CMD ["python", "app.py"] lance le programme en PID 1. La forme chaîne CMD python app.py passe par /bin/sh -c : le shell ne transmet pas SIGTERM, et docker stop finit par tuer le conteneur au bout de 10 secondes.

Bonnes pratiques d'un Dockerfile

Une image de base maintenue et légère : python:3.8, celle de l'exemple du cours, n'a plus de correctifs depuis octobre 2024 — on prendrait aujourd'hui une version supportée, en variante -slim. L'ordre des couches : copier requirements.txt et installer les dépendances avant le code, comme ci-dessus, pour que le cache serve à chaque reconstruction. Un .dockerignore pour ne pas envoyer .git, les secrets ou les environnements virtuels dans le contexte. Un utilisateur non root (USER) pour l'application. Et un tag précis plutôt que latest.

À retenir

RUN construit, CMD propose, ENTRYPOINT impose. Et docker build prend un dossier (le contexte), pas un fichier : sans le point final, rien ne se construit.

Question éclair

Ton Dockerfile contient EXPOSE 5000. Tu lances docker run -d mon-app, mais curl http://localhost:5000 depuis l'hôte échoue. Pourquoi ?

EXPOSE est une documentation pour qui lit l'image. Seul -p hôte:conteneur (ou ports: dans Compose) crée la règle de NAT. Pense aussi à faire écouter l'application sur 0.0.0.0 et non 127.0.0.1, sinon elle reste injoignable même avec -p.

06

Volumes & données persistantes

Les données écrites dans un conteneur disparaissent avec lui. Un volume est un stockage géré en dehors du cycle de vie du conteneur, et réutilisable par plusieurs.

bash
docker volume create mes_donnees
docker run -d --name web1 -v mes_donnees:/usr/share/nginx/html nginx
docker run -d --name web2 -v mes_donnees:/usr/share/nginx/html:ro nginx  # lecteur seul
docker volume ls
docker volume inspect mes_donnees                                        # → Mountpoint : /var/lib/docker/volumes/mes_donnees/_data
docker volume rm mes_donnees                                             # refusé tant qu'un conteneur l'utilise
  • docker volume prune ne supprime que les volumes anonymes inutilisés ; avec -a, les volumes nommés y passent aussi — donc des données.
  • Drivers : local par défaut ; NFS et CIFS passent par local avec des --opt ; d'autres drivers existent (GlusterFS, Azure File…).
  • Emplacement par défaut : /var/lib/docker. L'option data-root de /etc/docker/daemon.json le déplace, à fixer avant de créer des données. Sur une installation neuve de Docker Engine 29, images et conteneurs vont dans /var/lib/containerd, que data-root ne déplace pas ; les volumes restent sous /var/lib/docker.
  • Partager un volume entre conteneurs : un seul écrivain, les autres en :ro.

À retenir

Tout ce qui doit survivre au conteneur — base de données, fichiers d'un site — va dans un volume monté au chemin attendu par l'application. Le conteneur, lui, reste jetable.

Question éclair

Tu fais docker rm -f web1 sur le conteneur qui montait le volume nommé mes_donnees. Que deviennent les fichiers du volume ?

Le volume vit dans /var/lib/docker/volumes/mes_donnees/_data, indépendamment des conteneurs. Un nouveau docker run -v mes_donnees:/usr/share/nginx/html nginx retrouve tout.

07

Le réseau des conteneurs

Par défaut, les conteneurs vivent derrière un pont docker0 (172.17.0.1/16) et un NAT : ils sortent librement, mais personne ne peut les joindre directement de l'extérieur.

bash
docker run -d -p 8080:80 nginx  # publier : port 80 du conteneur sur 8080 de l'hôte
docker network ls               # bridge, host, none installés d'office
docker network create --driver bridge labnet
docker run -d --name db --network labnet postgres:16
docker network inspect labnet   # conteneurs attachés, MAC, IPv4
docker network disconnect labnet db
DriverComportement
bridgeswitch virtuel + NAT ; sur un bridge créé, les conteneurs se joignent par leur nom
hostle conteneur prend l'interface et l'IP de l'hôte : plus de NAT, plus de ports partageables
macvlanune sous-interface dédiée par conteneur, directement sur le réseau physique
noneisolation totale : loopback seulement
overlayun seul réseau réparti sur plusieurs hôtes (Swarm)

Lecture de -p

Toujours hôte:conteneur. EXPOSE dans le Dockerfile n'ouvre rien du tout : seul -p publie.

Piège de sécurité : -p passe à travers ufw

Un port publié n'est pas filtré par ufw. Docker écrit ses propres règles iptables (DNAT dans la table nat, puis chaîne FORWARD) : le paquet est redirigé vers le conteneur avant d'atteindre la chaîne INPUT, où vivent les règles d'ufw. Un ufw deny 8080 ne protège donc pas un -p 8080:80. Les parades : publier sur la boucle locale (-p 127.0.0.1:8080:80) quand seul un reverse proxy local doit joindre le service, ou filtrer dans la chaîne DOCKER-USER, prévue pour ça.

À retenir

Entrant : il faut un mappage de port. Entre conteneurs : un réseau créé, sur lequel le nom du conteneur sert de nom DNS.

Question éclair

Deux conteneurs, app et db, lancés avec docker run sans option --network. Depuis app, ping db répond « bad address », alors que ping 172.17.0.3 passe. Pourquoi ?

Le DNS interne de Docker ne fonctionne que sur un réseau créé : docker network create labnet, puis --network labnet pour les deux. Compose le fait tout seul avec son réseau <projet>_default.

08

Docker Compose

Les options de docker run sont nombreuses, à retaper à chaque fois, et une application a souvent plusieurs conteneurs. Compose les écrit une fois pour toutes dans un fichier YAML.

compose.yaml — application + base, comme au TP
services:
  app:
    build: .                         # image construite depuis le Dockerfile du dossier
    ports:
      - "8080:5000"
    environment:
      DB_HOST: db                    # le DNS interne résout le nom du service
    depends_on:
      - db
    restart: unless-stopped
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: change-moi  # obligatoire pour l'image postgres
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:
bash
docker compose up -d          # lancer, en arrière-plan
docker compose up -d --build  # après une modification du code
docker compose ps
docker compose logs app
docker compose exec app bash
docker compose down           # conteneurs + réseau supprimés, volumes GARDÉS
docker compose down -v        # … et les volumes : la base repart de zéro

Ce que le TP a montré

  • Seul le service qui a une clé ports: est joignable de l'extérieur.
  • depends_on fixe l'ordre de lancement, pas l'attente que la base soit prête.
  • Le code est copié dans l'image : sans --build, une modification d'app.py ne change rien.
  • Compose crée tout seul un réseau <projet>_default et un DNS interne ; le projet porte le nom du dossier.
  • restart: vaut no par défaut ; always, on-failure[:3] et unless-stopped sont les autres choix.

À retenir

Un compose.yaml est la mémoire d'une application : services, ports, volumes et redémarrage écrits une fois. down garde les données, down -v les efface.

Question éclair

Au docker compose up -d, le service app plante avec « connection refused » vers db, alors qu'il a bien depends_on: - db. Il repart si on le relance une minute après. Pourquoi ?

Par défaut, depends_on ne règle que l'ordre. Les parades : une politique restart sur app, une application qui réessaie, ou un healthcheck sur db combiné à depends_on: db: condition: service_healthy.

09

S'entraîner : lancer, vérifier, dépanner

Tout le module en exercices : les commandes à retrouver sans regarder, une application complète à monter et vérifier, et les trois pannes les plus fréquentes d'un conteneur.

À toi de taper

Lance un conteneur nginx en arrière-plan, nommé web, qui publie son port 80 sur le port 8080 de l'hôte.

Voir la solution

docker run -d --name web -p 8080:80 nginx — les options avant l'image, -p hôte:conteneur. Vérifier : curl -I http://localhost:8080 doit répondre HTTP/1.1 200 OK.

À toi de taper

Ouvre un shell bash dans le conteneur web qui tourne, sans l'arrêter en sortant.

Voir la solution

docker exec -it web bash (ou sh si l'image n'a pas bash). En sortir avec exit n'arrête rien : c'est un nouveau processus, pas le PID 1.

À toi de taper

Suis en continu les journaux du conteneur web, en partant des 20 dernières lignes.

Voir la solution

docker logs -f --tail 20 web — Ctrl+C arrête l'affichage, pas le conteneur.

À toi de taper

Après avoir modifié app.py, relance la pile Compose en arrière-plan en reconstruisant l'image.

Voir la solution

docker compose up -d --build. Sans --build, Compose réutilise l'ancienne image : le code modifié n'est pas pris en compte.

Vérifier

La pile Compose tourne-t-elle, et les deux services se voient-ils ?

bash
docker compose ps
docker compose exec app getent hosts db       # le nom du service se résout sur le réseau du projet

Sortie attendue (colonnes COMMAND et CREATED omises)

NAME          IMAGE         SERVICE   STATUS          PORTS
projet-app-1  projet-app    app       Up 2 minutes    0.0.0.0:8080->5000/tcp
projet-db-1   postgres:16   db        Up 2 minutes    5432/tcp
172.18.0.2      db

Un service en Restarting ou Exited : docker compose logs NOM dit pourquoi (variable manquante, base pas prête). Le nom db ne se résout pas : l'application n'est pas sur le même réseau Compose.

Scénario de panne

Le conteneur s'arrête aussitôt lancé

docker run -d --name test ubuntu rend la main, mais docker ps ne montre rien.

Que regardes-tu ?

CONTAINER ID   IMAGE    COMMAND       STATUS                     NAMES
3f2a1c…        ubuntu   "/bin/bash"   Exited (0) 3 seconds ago   test

Exited (0) : pourquoi s'est-il arrêté ?

Lancé en -d sans -it, bash n'a rien à lire et se termine aussitôt — et le conteneur avec lui.

Correction : docker run -dit --name test ubuntu pour garder un bash interactif détaché, ou lancer une image dont le processus principal est un service (nginx, postgres). docker logs et le code de sortie disent toujours pourquoi un conteneur s'arrête.

Scénario de panne

Les données de la base ont disparu

Après docker compose down puis up -d, la base PostgreSQL de l'application est vide.

Quelle est la première vérification ?

Pas de volume : les données vivaient dans la couche d'écriture du conteneur, supprimée par down.

Correction : un volume nommé (db_data:/var/lib/postgresql/data) déclaré dans volumes:. Et ne jamais taper down -v sans le vouloir : il supprime aussi les volumes.

À retenir

Les quatre réflexes : docker ps -a (l'état), docker logs (le pourquoi), docker exec -it (entrer sans casser), docker compose up -d --build (appliquer un changement de code). Et pas de volume = pas de données qui survivent.
