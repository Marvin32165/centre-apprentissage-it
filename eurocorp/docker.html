1Docker et Compose : les bases du labo

Une application = un dossier avec un docker-compose.yml (sans secret) et un .env (les valeurs). Compose lit le .env tout seul, remplace chaque ${VARIABLE} et crée réseau et conteneurs. Chaque service est joignable par les autres par son nom grâce au DNS interne de Compose.

Préparation

  1. Docker est installé sur la VM

    Voir Préparer, section 5. docker compose version doit répondre.

    Pas à pas.
    1. Connecte-toi en SSH à la VM Docker.
    2. docker --version et docker compose version.
    3. Si la commande est absente : retourne à la page Préparer, section « Créer les VM Linux (Docker) ».
    Pourquoi. Toutes les piles du labo sont décrites en Compose : sans le plugin Compose v2, aucune commande de cette page ne fonctionne.
    Vérifier. Les deux commandes renvoient une version ; sudo docker run --rm hello-world affiche son message.
  2. Un dossier par application
    Ubuntu
    sudo mkdir -p /opt/zabbix-lab && cd /opt/zabbix-lab

    Le dossier d'un projet donne son nom aux conteneurs, au réseau et aux volumes créés.

    Pas à pas.
    1. Crée le dossier de l'application : sudo mkdir -p /opt/zabbix-lab && cd /opt/zabbix-lab.
    2. Garde tous les fichiers de l'appli dedans (compose, .env, configurations).
    3. Lance toujours les commandes docker compose depuis ce dossier.
    Pourquoi. Compose nomme conteneurs, réseau et volumes d'après le dossier : deux applications dans le même dossier se mélangent.
    Vérifier. pwd affiche le dossier ; docker compose ps ne liste que cette application.
    Piège. Si tu renommes le dossier après le premier démarrage, Compose crée de nouveaux volumes vides : tu perds l'accès à tes données.
  3. Vérifier le compose avec l'outil du site

    Outil Compose : générateur Zabbix / Redmine, vérificateur pour n'importe quel compose (variables manquantes, ports en double, volumes non déclarés).

    Pas à pas.
    1. Ouvre la page Outil Compose.
    2. Colle le contenu de ton docker-compose.yml et, si l'outil le propose, celui du .env.
    3. Lis les avertissements : variables manquantes, ports en double, volumes non déclarés.
    Pourquoi. Une erreur de syntaxe ou un port déjà pris se trouve en quelques secondes avant le démarrage.
    Vérifier. L'outil ne signale aucune erreur bloquante.
    Piège. L'outil vérifie la forme, pas le résultat : le vrai test reste docker compose config sur la VM.

Installation

  1. Copier les fichiers du livrable

    Dossier 05-Docker/<appli>/ : docker-compose.yml, .env (valeurs jetables, commité volontairement ici), .env.example vide.

    Pas à pas.
    1. Depuis ton poste : scp -r 05-Docker/zabbix/* utilisateur@172.17.10.40:/opt/zabbix-lab/ (ou clone le dépôt privé sur la VM).
    2. Vérifie la présence de docker-compose.yml, .env et .env.example.
    3. Ne copie que le dossier de l'application concernée.
    Pourquoi. Les fichiers du livrable sont la source de vérité : reprendre ceux-là évite de retaper un compose à la main.
    Vérifier. ls -la montre les fichiers, .env compris (il commence par un point).
    Piège. Les valeurs du .env sont jetables et commitées volontairement dans ce dépôt : elles ne valent pas pour un autre usage.
  2. Protéger le .env
    Ubuntu
    sudo chmod 600 .env

    Git ne conserve pas ce droit : à refaire après chaque git clone.

    Pas à pas.
    1. sudo chmod 600 .env : lecture et écriture pour le propriétaire seulement.
    2. Vérifie : ls -l .env affiche -rw-------.
    Pourquoi. Le .env contient des mots de passe en clair : les autres comptes de la VM ne doivent pas pouvoir le lire.
    Vérifier. ls -l .env → -rw-------.
    Piège. Git ne conserve pas ce droit : refais-le après chaque git clone.

Configuration

  1. Règles du .env

    CLE=valeur sans espace autour du = · mots de passe alphanumériques (un $ s'écrit $$) · une variable du shell passe avant le fichier.

    Pas à pas.
    1. Une variable par ligne : CLE=valeur, sans espace autour du =.
    2. Mots de passe alphanumériques : un $ s'écrit $$ dans un fichier .env.
    3. Une variable déjà définie dans le shell passe avant le fichier : env | grep POSTGRES pour vérifier.
    Pourquoi. Une erreur de syntaxe dans le .env ne produit pas toujours d'erreur : la variable est simplement vide ou fausse.
    Vérifier. docker compose config affiche les valeurs réellement appliquées.
  2. Voir ce que Compose appliquera
    Ubuntu
    docker compose config -q                  # erreurs de syntaxe seulement
docker compose config | grep -i password   # une variable ne doit pas être vide

    Un nom de variable mal tapé ne provoque aucune erreur : Compose le remplace par une chaîne vide.

    Pas à pas.
    1. docker compose config -q : ne signale que les erreurs de syntaxe.
    2. docker compose config | grep -i password : vérifie qu'aucun mot de passe n'est vide.
    Pourquoi. Un nom de variable mal tapé ne produit aucune erreur : Compose le remplace par une chaîne vide.
    Vérifier. Aucune ligne PASSWORD: "" ; toutes les variables attendues ont une valeur.

Vérifications

  1. Démarrer et contrôler
    Ubuntu
    docker compose up -d
docker compose ps
docker logs <nom> --tail 50

    Tout doit être « Up ». Un conteneur qui redémarre en boucle : lire ses logs.

    Pas à pas.
    1. docker compose up -d : crée et démarre les conteneurs en arrière-plan.
    2. docker compose ps : tous doivent être « Up » (ou « healthy » quand un contrôle d'état existe).
    3. docker logs <nom> --tail 50 pour un conteneur qui redémarre en boucle.
    Pourquoi. Un conteneur « Up » ne veut pas dire que l'application fonctionne : les logs le disent.
    Vérifier. Tous les conteneurs « Up », aucune erreur dans les derniers logs.
  2. Un piège bien connu

    Changer un mot de passe de base dans le .env après le premier démarrage ne change pas celui de la base (lu seulement à la création du volume). Soit tu le changes dans la base, soit docker compose down -v (données perdues).

    Pas à pas.
    1. Pour changer un mot de passe de base après coup : modifie-le dans la base (ALTER USER ou l'équivalent), puis dans le .env.
    2. Ou, si les données sont jetables : docker compose down -v puis up -d (les volumes sont supprimés).
    Pourquoi. Le conteneur de base lit ses variables seulement à la création du volume. Changer le .env ensuite ne touche pas la base existante.
    Vérifier. L'application se connecte avec le nouveau mot de passe.
    Piège. down -v détruit toutes les données : jamais sur un volume utile.

2Zabbix 7.4 (BRU-DOCKER01)

Le serveur de supervision : PostgreSQL, serveur Zabbix (port 10051) et interface web, dans trois conteneurs. Le serveur Zabbix lui-même est supervisé par un quatrième conteneur : l'agent 2.

Préparation

  1. Variables du .env
    VariableRôleComment la choisir
    POSTGRES_DBNom de la base ZabbixLibre, ex. zabbix. Le compose l'utilise pour le serveur et la base.
    POSTGRES_USERCompte applicatifLibre, ex. zabbix.
    POSTGRES_PASSWORDMot de passe de ce compteAlphanumérique, 20 caractères ou plus. Lu seulement à la 1re création du volume.
  2. Nom DNS

    Enregistrement A zbx01 ou zabbix → 172.17.10.40 dans la zone eurocorp.lan (page Identité).

    Pas à pas.
    1. Sur un contrôleur de domaine : Add-DnsServerResourceRecordA -ZoneName eurocorp.lan -Name <nom> -IPv4Address <IP de la VM> -CreatePtr.
    2. Pour un alias : Add-DnsServerResourceRecordCName vers le nom de la VM.
    3. Teste depuis un poste : Resolve-DnsName <nom>.eurocorp.lan.
    Pourquoi. Les URL du labo utilisent des noms, pas des adresses : navigateurs, agents et certificats les attendent.
    Vérifier. Resolve-DnsName renvoie l'IP de la VM.

Installation

  1. Lancer la pile
    Ubuntu
    cd /opt/zabbix-lab
sudo docker compose up -d
docker ps                  # 3 conteneurs Up
docker logs zabbix-server

    Les trois : zabbix-postgres (la base), zabbix-server (le moteur), zabbix-web (l'interface, port 80 de la VM).

    Pas à pas.
    1. cd /opt/zabbix-lab puis sudo docker compose up -d.
    2. docker ps : trois conteneurs Up (zabbix-postgres, zabbix-server, zabbix-web).
    3. docker logs zabbix-server : cherche « server #0 started » sans erreur de base de données.
    Pourquoi. La base démarre d'abord, puis le serveur (moteur), puis l'interface web.
    Vérifier. Trois conteneurs Up ; http://IP-de-la-VM répond.
    Piège. Au premier démarrage, le serveur peut redémarrer une ou deux fois le temps que PostgreSQL soit prêt : c'est normal.

Configuration

  1. Première connexion

    http://zabbix.eurocorp.lan. Identifiants par défaut de Zabbix à changer tout de suite (compte Admin).

    Pas à pas.
    1. Ouvre l'URL du service dans un navigateur.
    2. Connecte-toi avec le compte par défaut de l'application (indiqué dans l'étape).
    3. Change tout de suite le mot de passe et note-le dans Infos.md.
    Pourquoi. Les identifiants par défaut sont publics : une application laissée avec eux est ouverte à n'importe qui sur le réseau.
    Vérifier. Tu es connecté avec le nouveau mot de passe, le compte par défaut n'ouvre plus rien.
    Piège. Un certificat auto-signé déclenche un avertissement du navigateur : normal en labo.
  2. Superviser Zabbix lui-même (agent en conteneur)

    Ajouter dans le compose un 4e service sous zabbix-web :

    docker-compose.yml
      zabbix-agent:
    image: zabbix/zabbix-agent2:alpine-7.4-latest   # même version que le serveur
    container_name: zabbix-agent
    restart: unless-stopped
    init: true
    privileged: true
    pid: host
    depends_on:
      - zabbix-server
    environment:
      ZBX_HOSTNAME: Zabbix server          # = nom exact de l'hôte dans Zabbix
      ZBX_SERVER_HOST: zabbix-server
    networks:
      - zabbix-backend
    Ubuntu
    sudo docker compose up -d zabbix-agent
docker exec zabbix-server zabbix_get -s zabbix-agent -k agent.version
    Pas à pas.
    1. Ouvre docker-compose.yml et ajoute le service zabbix-agent (bloc ci-dessous) sous zabbix-web.
    2. Mets la même version que le serveur (alpine-7.4-latest) et ZBX_HOSTNAME = nom exact de l'hôte dans Zabbix.
    3. docker compose up -d : seul le nouveau conteneur est créé.
    Pourquoi. Zabbix supervise ses propres ressources (processeur, mémoire, disque de la VM) comme n'importe quelle machine.
    Vérifier. docker compose ps : quatre conteneurs Up.
    Piège. Le nom ZBX_HOSTNAME doit correspondre exactement à celui de l'hôte dans l'interface, sinon les contrôles actifs sont ignorés.
  3. Changer l'interface de l'hôte « Zabbix server »

    Data collection → Hosts → Zabbix server, interface Agent : IP vide, DNS name zabbix-agent, Connect to : DNS, port 10050. Pas 127.0.0.1 : dans un conteneur, c'est le conteneur lui-même ; l'IP d'un conteneur change à chaque recréation, son nom non.

    Pas à pas.
    1. Zabbix → Data collection → Hosts → clique sur Zabbix server.
    2. Section Interfaces → Agent : vide le champ IP, renseigne DNS name = zabbix-agent, Connect to = DNS, port 10050.
    3. Update.
    Pourquoi. Dans un conteneur, 127.0.0.1 désigne le conteneur lui-même, pas l'agent. L'IP d'un conteneur change à chaque recréation, son nom Compose non.
    Vérifier. Après une minute, l'icône ZBX de l'hôte passe au vert.

Vérifications

  1. Pile saine
    Ubuntu
    docker compose ps
docker exec zabbix-server zabbix_get -s zabbix-agent -k agent.version

    Quatre conteneurs « Up », réponse 7.4.x.

    Pas à pas.
    1. docker compose ps : quatre conteneurs Up.
    2. docker exec zabbix-server zabbix_get -s zabbix-agent -k agent.version : renvoie la version de l'agent.
    Pourquoi. Prouve que serveur et agent se parlent à l'intérieur du réseau Compose.
    Vérifier. Quatre conteneurs Up et une réponse du type 7.4.x.
  2. L'hôte est disponible

    Monitoring → Hosts : l'icône ZBX de « Zabbix server » est verte. Les agents des autres machines sont ajoutés dans Exploitation.

    Pas à pas.
    1. Zabbix → Monitoring → Hosts.
    2. Repère la ligne « Zabbix server » : l'icône ZBX doit être verte.
    Pourquoi. Un hôte « disponible » reçoit des données : la supervision fonctionne.
    Vérifier. Icône verte et premières valeurs dans « Latest data ».
    Piège. Les agents des autres machines se déclarent dans la page Exploitation.

3Redmine (LON-DOCKER01)

Le helpdesk (tickets) du labo : Redmine et sa base MariaDB, derrière un reverse proxy nginx en HTTPS. Les comptes de l'Active Directory se connectent par LDAP.

Préparation

  1. Variables du .env
    VariableRôleComment la choisir
    MYSQL_DATABASEBase de RedmineLibre, ex. redmine.
    MYSQL_USERCompte applicatif MariaDBLibre, ex. redmine.
    MYSQL_PASSWORDMot de passe de ce compteAlphanumérique, 20+.
    MYSQL_ROOT_PASSWORDMot de passe root MariaDBDifférent du précédent ; pour l'administration, pas pour Redmine.
    REDMINE_SECRET_KEY_BASEClé qui signe les sessionsLongue chaîne aléatoire (64 hex). La changer déconnecte tout le monde.
  2. Nom DNS

    Alias helpdesk (CNAME) vers lon-docker01.eurocorp.lan, ou enregistrement A vers 172.17.30.40.

    Pas à pas.
    1. Sur un contrôleur de domaine : Add-DnsServerResourceRecordA -ZoneName eurocorp.lan -Name <nom> -IPv4Address <IP de la VM> -CreatePtr.
    2. Pour un alias : Add-DnsServerResourceRecordCName vers le nom de la VM.
    3. Teste depuis un poste : Resolve-DnsName <nom>.eurocorp.lan.
    Pourquoi. Les URL du labo utilisent des noms, pas des adresses : navigateurs, agents et certificats les attendent.
    Vérifier. Resolve-DnsName renvoie l'IP de la VM.
  3. Arborescence
    Ubuntu
    mkdir -p ~/redmine/nginx/conf.d ~/redmine/nginx/certs ~/redmine/backup ~/redmine/backups
cd ~/redmine
    Pas à pas.
    1. mkdir -p ~/redmine/nginx/conf.d ~/redmine/nginx/certs ~/redmine/backup ~/redmine/backups.
    2. cd ~/redmine.
    Pourquoi. Une arborescence claire sépare configuration nginx, certificats, scripts de sauvegarde et sauvegardes.
    Vérifier. find ~/redmine -type d liste les sous-dossiers.

Installation

  1. Le compose (Redmine + MariaDB + nginx)

    Trois services sur le réseau redmine-network : db (mariadb:11), redmine (ne publie plus de port) et nginx (80 et 443 de la VM). Volumes nommés pour la base et les pièces jointes : les données survivent à la suppression des conteneurs.

    Fichier du livrable : 05-Docker/redmine/docker-compose.yml.

    Pas à pas.
    1. Copie 05-Docker/redmine/docker-compose.yml dans ~/redmine/.
    2. Lis-le : trois services sur le réseau redmine-network — db (MariaDB), redmine (sans port publié) et nginx (80 et 443).
    3. Vérifie les volumes nommés : base et pièces jointes.
    Pourquoi. nginx est le seul point d'entrée : il termine le HTTPS et protège Redmine. Les volumes nommés gardent les données si les conteneurs sont recréés.
    Vérifier. docker compose config sans erreur.
  2. Certificat auto-signé pour nginx
    Ubuntu
    openssl genrsa -out nginx/certs/redmine.key 4096
openssl req -x509 -new -nodes -key nginx/certs/redmine.key -sha256 -days 365 \
  -out nginx/certs/redmine.crt \
  -subj "/C=BE/O=LAB/OU=IT/CN=helpdesk.eurocorp.lan" \
  -addext "subjectAltName=DNS:helpdesk.eurocorp.lan,IP:172.17.30.40"

    Le navigateur ne fait pas confiance à un certificat auto-signé : l'avertissement est normal. Le nom doit figurer dans le SAN (le seul CN ne suffit plus).

    Pas à pas.
    1. Génère la clé privée : openssl genrsa -out nginx/certs/redmine.key 4096.
    2. Crée le certificat avec le bloc ci-dessous (openssl req -x509 …) : nom helpdesk.eurocorp.lan et IP dans subjectAltName.
    3. Vérifie : openssl x509 -in nginx/certs/redmine.crt -noout -subject -dates.
    Pourquoi. HTTPS exige un certificat ; les navigateurs modernes exigent les noms dans le champ SAN, pas seulement le CN.
    Vérifier. Le certificat est valide un an avec les bons noms.
    Piège. Auto-signé = avertissement du navigateur. Pour l'éviter, signe-le avec l'AC interne (page Services).
  3. Configuration de nginx
    nginx/conf.d/redmine.conf
    server {
    listen 80;
    server_name helpdesk.eurocorp.lan;
    return 301 https://$host$request_uri;          # HTTP -> HTTPS
}
server {
    listen 443 ssl;
    server_name helpdesk.eurocorp.lan;
    ssl_certificate     /etc/nginx/certs/redmine.crt;
    ssl_certificate_key /etc/nginx/certs/redmine.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    client_max_body_size 100M;
    location / {
        proxy_pass http://redmine:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
    }
}
    Pas à pas.
    1. Crée nginx/conf.d/redmine.conf avec le contenu ci-dessous.
    2. Le premier bloc renvoie le HTTP vers HTTPS (301) ; le second écoute en 443, présente le certificat et relaie vers le conteneur Redmine.
    3. client_max_body_size 100M autorise les grosses pièces jointes.
    Pourquoi. nginx sépare l'accès public (HTTPS) de l'application, qui reste cachée dans le réseau Docker.
    Vérifier. docker exec nginx nginx -t : « syntax is ok ».
  4. Démarrer
    Ubuntu
    sudo chmod 600 .env
sudo docker compose config | grep -i password
sudo docker compose up -d
sudo docker ps

    Au premier démarrage, un « Can't connect to server on 'db' » est normal : depends_on attend que MariaDB démarre, pas qu'elle soit prête. Redmine réessaie et se connecte.

    Pas à pas.
    1. sudo chmod 600 .env.
    2. sudo docker compose config | grep -i password : aucune valeur vide.
    3. sudo docker compose up -d puis sudo docker ps.
    Pourquoi. Les mêmes contrôles que pour toute pile : permissions, valeurs, démarrage.
    Vérifier. Trois conteneurs Up.
    Piège. Un « Can't connect to server on 'db' » au premier démarrage est normal : depends_on attend le démarrage de MariaDB, pas qu'elle soit prête ; Redmine réessaie.

Configuration

  1. Première connexion

    https://helpdesk.eurocorp.lan → Sign in avec le compte par défaut de Redmine, qui impose de changer le mot de passe. Administration → Load the default configuration (trackers, rôles, statuts, workflow).

    Pas à pas.

    2. Connecte-toi avec le compte par défaut de l'application (indiqué dans l'étape).
    3. Change tout de suite le mot de passe et note-le dans Infos.md.
    Pourquoi. Les identifiants par défaut sont publics : une application laissée avec eux est ouverte à n'importe qui sur le réseau.
    Vérifier. Tu es connecté avec le nouveau mot de passe, le compte par défaut n'ouvre plus rien.
    Piège. Un certificat auto-signé déclenche un avertissement du navigateur : normal en labo.
  2. Activer l'API

    Administration → Settings → Integration : REST web service (et, si utile, webhooks). La clé API de chaque compte est dans My account.

    Pas à pas.

  3. Connexion à l'Active Directory (LDAP)

    Administration → LDAP authentication → New :

    ChampValeur
    Hostbru-dc01.eurocorp.lan
    Port389 (LDAP) · 636 pour LDAPS, chiffré
    Accountcompte de service du domaine dédié, simple utilisateur (lecture de l'annuaire suffit)
    Base DNDC=eurocorp,DC=lan

    Login / Prénom / Nom / E-mailsAMAccountName · givenName · sN · mail
    Pas à pas.
    1. Crée dans l'AD un compte de service dédié, simple utilisateur (lecture de l'annuaire suffit).
    2. Redmine : Administration → LDAP authentication → New, remplis le tableau ci-dessous (hôte, port 389, compte, Base DN, attributs).
    3. Coche On-the-fly user creation.

    Pourquoi. Les utilisateurs se connectent avec leur compte du domaine : un seul mot de passe, une seule source d'identité.

    Piège. Voir l'étape suivante si le test échoue sur Windows Server 2025.
  4. Si le Test échoue (« Invalid LDAP Account/Password »)

    Sur Windows Server 2025, le contrôleur exige la signature LDAP : il répond « Stronger Auth Needed » et Redmine affiche un message trompeur. Solution de lab : Default Domain Controllers Policy → Security Options → Domain controller: LDAP server signing requirements Enforcement = Disabled, puis gpupdate /force. Les mots de passe passent alors en clair : en production, utiliser LDAPS.

    Pas à pas.
    1. Sur un DC : Group Policy Management → Default Domain Controllers Policy → Edit.
    2. Computer Configuration → Policies → Windows Settings → Security Settings → Local Policies → Security Options → Domain controller: LDAP server signing requirements = None/Disabled.
    3. gpupdate /force sur le DC, puis relance le Test.
    Pourquoi. Windows Server 2025 exige la signature LDAP : le DC répond « Stronger Auth Needed » et Redmine affiche un message trompeur.
    Vérifier. Test réussi.
    Piège. Solution de laboratoire : les mots de passe passent alors en clair. En production, utilise LDAPS (port 636) avec un certificat.
  5. Projet et premier ticket

    Administration → Projects → New project (par exemple « ITSM »), puis Issues → New issue : tracker, sujet, priorité, assigné.

    Pas à pas.
    1. Administration → Projects → New project : nom « ITSM », identifiant itsm. Save.
    2. Dans le projet : Issues → New issue : tracker (Bug/Feature/Support), sujet, priorité, assigné.
    3. Ajoute un commentaire, change le statut : l'historique apparaît.
    Pourquoi. Un premier ticket valide la chaîne : base, application, authentification.
    Vérifier. Le ticket est visible avec son numéro et son historique.

Vérifications

  1. Le site répond en HTTPS

curl -kI http://helpdesk.eurocorp.lan    # doit répondre 301 vers https

  3. Les données survivent
