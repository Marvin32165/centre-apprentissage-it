OPNsense, tunnels et flux

Chaque site a son pare-feu OPNsense. Bruxelles est le centre : les trois autres s'y relient par IPsec. Les quatre étapes de la page : installer le pare-feu, monter les tunnels, faire passer les routes, filtrer.

En bref

Un pare-feu par site (WAN dans la salle, LAN du site), trois tunnels site-à-site vers Bruxelles, un ping réel de LAN à LAN avant de toucher au filtrage, puis seulement les flux de la matrice. Le DHCP passe d'un site à l'autre par relais.

Dans cette page OPNsense · Tunnels IPsec · Routes et DNS · Filtrage

Pourquoi en étoile

Trois tunnels au lieu de six. Paris ↔ Londres passe par Bruxelles ; si Bruxelles tombe, les autres sites ne se voient plus. Les routes et les règles de chaque pare-feu doivent donc connaître tous les LAN.

1Une VM OPNsense par site

OPNsense est un pare-feu logiciel : une VM qui joue le routeur entre le WAN (la salle) et le LAN du site, filtre le trafic et monte les tunnels. Tout se règle dans une interface web.

Préparation

  1. Deux cartes réseau

    Carte 1 sur le commutateur WAN, carte 2 sur LAN-xxx du site. L'ordre compte : la première devient WAN, la deuxième LAN.

    Pas à pas.
    1. Crée la VM (génération 2), puis dans Settings regarde Network Adapter : la carte par défaut.
    2. Branche cette première carte sur le commutateur WAN.
    3. Add Hardware → Network Adapter → Add, et branche cette deuxième carte sur LAN-xxx de ton site.
    4. Pas de VLAN, pas de mémoire dynamique.
    Pourquoi. OPNsense sépare deux mondes : l'extérieur (WAN, la salle) et l'intérieur (LAN, les serveurs du site). Sans deux cartes, il ne peut pas faire de routage entre eux.
    Vérifier. La liste des périphériques montre deux cartes, et leurs adresses MAC sont différentes ; la première est sur WAN, la deuxième sur LAN.
    Piège. FreeBSD numérote les cartes dans l'ordre de création : si tu inverses l'ordre, WAN et LAN sont interchangés à l'assignation des interfaces. Note les adresses MAC (Settings → Network Adapter → Advanced Features) pour les reconnaître.
  2. Dimensionner

    Génération 2 · 2 vCPU · 2 Go de RAM fixe · 20 Go de disque. Désactiver le démarrage sécurisé (Settings → Security) : FreeBSD ne le gère pas avec le modèle par défaut.

    Pas à pas.
    1. Settings → Processor : 2 vCPU.
    2. Memory : 2048 Mo fixes (mémoire dynamique décochée).
    3. Disque de 20 Go (dynamique).
    4. Settings → Security : décoche Enable Secure Boot.
    5. Pas de point de contrôle.
    Pourquoi. OPNsense est léger : 2 Go suffisent pour un pare-feu de labo avec IPsec. Le démarrage sécurisé empêche le noyau FreeBSD de démarrer avec le certificat par défaut.
    Vérifier. La VM démarre sur l'ISO sans message de certificat.
    Piège. Si la VM refuse de démarrer en génération 2, recrée-la en génération 1 : le fonctionnement est le même pour le labo.
  3. Noter les valeurs du site

    WAN de chaque pare-feu : 10.10.28.111 à .114 (Bruxelles à Berlin), passerelle de la salle 10.10.28.254. LAN : 172.17.10.1, 172.17.20.1, 172.17.30.1, 172.17.40.1.

    Pas à pas.
    1. Regarde la page Infrastructure et le tableau « Plan IP » : WAN, LAN, passerelle de ton site.
    2. Recopie : WAN 10.10.28.111 à .114 (BRU, PAR, LON, BER), passerelle de la salle 10.10.28.254, LAN 172.17.x.1/24.
    3. Note aussi les DNS (les deux contrôleurs de domaine) pour l'assistant.
    Pourquoi. À l'installation tu auras besoin de ces valeurs d'un coup : les rassembler d'abord évite les allers-retours.
    Vérifier. Tu as sous les yeux quatre valeurs : IP WAN, passerelle de la salle, IP LAN du pare-feu, DNS.

Installation

  1. Installer depuis l'ISO

    Démarrer sur l'ISO d'OPNsense (image dvd). Se connecter en installer pour lancer l'installation sur le disque, choisir la disposition du clavier, un disque, puis définir le mot de passe de root et redémarrer en retirant l'ISO.

    Pas à pas.
    1. Monte l'ISO OPNsense (image dvd) sur la VM et démarre.
    2. À l'écran de connexion de l'installeur : identifiant installer, mot de passe opnsense.
    3. Choisis le clavier, puis Install (UFS) ou ZFS (UFS suffit pour le labo), sélectionne le disque, confirme l'effacement.
    4. Définis le mot de passe de root à la fin de l'installation (note-le dans Infos.md).
    5. Quand l'installeur le demande, redémarre et retire l'ISO (Settings → DVD Drive → None) pour ne pas recommencer l'installation.
    Pourquoi. L'installeur écrit OPNsense sur le disque : les VM suivantes démarrent ensuite directement depuis le disque.
    Vérifier. Au redémarrage, la console affiche le menu OPNsense (« 0) Logout … 1) Assign interfaces … »).
    Piège. Si la VM redémarre sur l'installeur, c'est que l'ISO est restée montée ou le DVD premier dans l'ordre de démarrage.
  2. Attribuer les interfaces

    À la console : Assign interfaces, confirmer que hn0 est le WAN et hn1 le LAN (les noms d'interface Hyper-V). Set interface IP address : LAN = 172.17.x.1/24, sans DHCP serveur ; WAN = IP fixe du tableau, passerelle de la salle.

    Pas à pas.
    1. Dans le menu de la console, tape 1 (Assign interfaces).
    2. « Do you want to configure LAGGs / VLANs now ? » : n.
    3. WAN : saisis le nom de la première interface (en général hn0) ; LAN : la deuxième (hn1) ; pas d'interface optionnelle (Entrée).
    4. Confirme avec y.
    5. Menu 2 (Set interface IP address) : choisis le LAN, « Configure IPv4 via DHCP ? » n, adresse 172.17.x.1, masque 24, pas de passerelle, pas d'IPv6, pas de serveur DHCP.
    6. Refais le menu 2 pour le WAN : IPv4 manuel, adresse du tableau (10.10.28.11x), masque 24, passerelle 10.10.28.254.
    Pourquoi. C'est ici que le pare-feu reçoit son identité réseau. Une erreur de carte ou d'adresse est la cause de la plupart des pannes de départ.
    Vérifier. La console affiche les deux interfaces avec leurs IP : LAN (hn1) → v4: 172.17.x.1/24, WAN (hn0) → v4: 10.10.28.11x/24.
    Piège. Pour savoir quelle carte est laquelle, compare les adresses MAC affichées avec celles de Hyper-V (Settings → Network Adapter). Si tu as inversé, relance le menu 1.

Configuration

  1. Premier accès web

    Depuis une VM du LAN : https://172.17.x.1 (certificat auto-signé : avertissement normal). Assistant System → Wizard : nom d'hôte (BRU-FW01…), domaine eurocorp.lan, DNS = les deux contrôleurs, fuseau horaire.

    Pas à pas.
    1. Depuis une VM du LAN (IP fixe dans le sous-réseau, passerelle = le pare-feu), ouvre https://172.17.x.1.
    2. Accepte l'avertissement de certificat (certificat auto-signé).
    3. Connecte-toi : root et le mot de passe choisi à l'installation.
    4. System → Wizard : nom d'hôte (BRU-FW01), domaine eurocorp.lan, DNS = les deux contrôleurs de domaine, fuseau horaire Europe/Brussels. Décoche « Block RFC1918 Private Networks » sur le WAN dans l'assistant.
    5. Valide jusqu'à « Reload ».
    Pourquoi. L'assistant pose les réglages de base et évite d'aller les chercher dans dix menus.
    Vérifier. Le tableau de bord s'affiche et indique les deux interfaces avec leurs adresses.
    Piège. Ne règle pas le DNS sur le pare-feu lui-même s'il n'est pas encore joignable : mets une adresse qui répond, tu la corrigeras après.
  2. Laisser entrer le réseau de la salle

    Interfaces → WAN : décocher « Block private networks ». La salle est en 10.10.28.0/24, une adresse privée : avec la case cochée, OPNsense jetterait le trafic des autres pare-feu — les tunnels ne monteraient pas. Laisser « Block bogon networks » coché.

    Pas à pas.
    1. Menu Interfaces → WAN.
    2. Descends à « Generic configuration ».
    3. Décoche Block private networks. Laisse Block bogon networks coché.
    4. Save, puis Apply changes.
    Pourquoi. La salle est en 10.10.28.0/24, plage privée. OPNsense bloque par défaut les adresses privées côté WAN : sans cette modification, les paquets des autres pare-feu sont jetés et les tunnels ne montent jamais.
    Vérifier. Depuis le LAN, un ping vers le WAN d'un autre site répond ; dans Firewall → Log Files → Live View, aucune ligne « block » avec la règle « Block private networks ».
    Piège. Les deux cases sont voisines : ne décoche pas « bogon » par erreur, il bloque des plages réservées qui ne devraient jamais arriver depuis l'extérieur.
  3. Règle temporaire sur le LAN

    Firewall → Rules → LAN : « Autoriser tout » le temps de monter et tester les tunnels. On la remplace par la matrice de flux à la section 4.

    Pas à pas.
    1. Firewall → Rules → LAN.
    2. Ajoute une règle : Action = Pass, Interface = LAN, Protocol = any, Source = any, Destination = any.
    3. Description : « TEMPORAIRE tout autorisé ». Save, Apply changes.
    Pourquoi. En montage, une règle trop stricte masque les vraies erreurs de tunnel. Autoriser tout le temps des tests permet d'isoler le problème (clé, réseau) avant de filtrer.
    Vérifier. Un ping depuis une VM du LAN vers le WAN de la salle répond.
    Piège. À supprimer en dernier : marque-la clairement (description) pour ne pas l'oublier. Un pare-feu laissé en « tout autorisé » n'est pas un pare-feu.
  4. Greffon Hyper-V

    System → Firmware → Plugins : installer os-hyperv pour que la VM s'arrête et redémarre proprement depuis Hyper-V.

    Pas à pas.
    1. System → Firmware → Plugins.
    2. Cherche os-hyperv et clique sur « + » (Install).
    3. Redémarre si l'interface le demande.
    Pourquoi. Le greffon installe les services d'intégration Hyper-V : l'arrêt propre depuis Hyper-V Manager, l'heure, le battement de cœur (heartbeat).
    Vérifier. Dans Hyper-V Manager, l'état d'intégration affiche « OK » et la VM s'éteint proprement avec « Shut Down ».
    Piège. Il faut un accès Internet depuis le pare-feu pour télécharger le greffon : vérifie le WAN et la passerelle.
  5. Changer le mot de passe par défaut

    Utilisateur root. Le noter dans Infos.md, jamais dans une fiche.

    Pas à pas.
    1. System → Access → Users → ouvre l'utilisateur root.
    2. Saisis un nouveau mot de passe fort, Save.
    3. Note-le dans Infos.md.
    Pourquoi. Un mot de passe par défaut connu de tout le monde sur un équipement qui garde les clés du VPN est inacceptable, même en labo.
    Vérifier. Tu te déconnectes puis te reconnectes avec le nouveau mot de passe.

Vérifications

  1. Le pare-feu atteint la salle

    Interfaces → Diagnostics → Ping vers 10.10.28.254 doit répondre.

    Pas à pas.
    1. Interfaces → Diagnostics → Ping (ou menu console 7).
    2. Hôte : 10.10.28.254, source WAN. Ping.
    Pourquoi. Si le pare-feu n'atteint pas la salle, aucun tunnel ne montera.
    Vérifier. 3 réponses, aucune perte.
    Piège. Pas de réponse : mauvaise carte assignée, mauvaise passerelle, ou règle de salle qui bloque.
  2. Un client du LAN atteint le pare-feu

    Depuis une VM du site : ping 172.17.x.1, puis ouvrir l'interface web. C'est le test que tu as déjà fait à Paris.

    Pas à pas.
    1. Depuis une VM du site (IP fixe sur le LAN), lance ping 172.17.x.1.
    2. Ouvre l'interface web https://172.17.x.1.
    Pourquoi. Prouve que le LAN est correctement raccordé : commutateur privé, carte, adresse.
    Vérifier. Le ping répond et l'interface web s'ouvre.

2Les tunnels IPsec

Bruxelles est le centre (hub), Paris, Londres et Berlin sont des extrémités (spokes). Trois tunnels site-à-site, chacun sur un petit réseau de transit :

Préparation

  1. Les tunnels et leurs adresses
    Pas à pas.
    1. Regarde le tableau des tunnels ci-dessus : un /30 par tunnel dans 172.17.255.0/24.
    2. Sur Bruxelles (hub), les trois tunnels : BRU-PAR (172.17.255.0/30), BRU-LON (172.17.255.4/30), BRU-BER (172.17.255.8/30).
    3. Chaque /30 a deux adresses utiles : celle du hub (.1, .5, .9) et celle du spoke (.2, .6, .10).
    Pourquoi. Un /30 par lien point à point évite de mélanger les tunnels et rend les routes lisibles.
    Vérifier. Tu sais, pour chaque tunnel, quelle adresse porte chaque côté.
  2. Décider ce qui sera commun

    Une clé partagée (PSK) différente par tunnel, longue et aléatoire, notée dans Infos.md. Mêmes algorithmes des deux côtés (par exemple AES-256 / SHA-256 / groupe DH 14 ou plus). Identifiants : l'IP WAN de chaque pare-feu.

    Pas à pas.
    1. Génère une clé partagée par tunnel : au moins 32 caractères aléatoires (lettres, chiffres, symboles).
    2. Note-les dans Infos.md : tunnel, clé.
    3. Choisis les algorithmes : IKEv2, AES-256, SHA-256, groupe DH 14 (ou supérieur). Utilise exactement les mêmes des deux côtés.
    4. Identifiants : l'adresse IP WAN de chaque pare-feu.
    Pourquoi. Une négociation IPsec n'aboutit que si les deux pare-feu proposent au moins un jeu d'algorithmes en commun, et la même clé.
    Vérifier. Les deux côtés ont la même liste de paramètres écrite devant toi.
    Piège. Ne réutilise pas la même clé pour les trois tunnels : si l'une fuit, les deux autres restent sûrs.
  3. Rappeler la logique en deux phases

    Phase 1 : les deux pare-feu s'identifient et s'accordent sur le chiffrement. Phase 2 : on dit quels réseaux passent dans le tunnel (LAN local ↔ LAN distant). Une erreur de réseau local/distant inversé est la panne la plus fréquente.

    Pas à pas.
    1. Phase 1 (IKE) : les deux pare-feu se reconnaissent (clé) et créent un canal sécurisé.
    2. Phase 2 (CHILD SA) : sur ce canal, ils négocient quels réseaux passent (LAN local ↔ LAN distant) et avec quelle clé de chiffrement du trafic.
    Pourquoi. Savoir à quelle phase on échoue dit immédiatement où chercher : phase 1 = identité et clés, phase 2 = réseaux.
    Vérifier. Tu peux dire pour chaque erreur du journal si elle vient de la phase 1 ou de la phase 2.
    Piège. Le réseau local d'un côté est le réseau distant de l'autre : l'inverser est la panne la plus fréquente.

Installation

  1. Tunnel Bruxelles ↔ Paris d'abord

    Sur BRU-FW01 : VPN → IPsec → Connections → nouvelle connexion. Adresse locale = WAN de Bruxelles (10.10.28.111), adresse distante = WAN de Paris (10.10.28.112), authentification par clé pré-partagée (saisie dans Pre-Shared Keys), IKEv2.

    Pas à pas.
    1. Sur BRU-FW01 : VPN → IPsec → Connections → Add.
    2. Version IKEv2, Local addresses = 10.10.28.111, Remote addresses = 10.10.28.112, proposals AES-256 / SHA-256 / DH 14.
    3. Local Authentication : Pre-Shared Key, identifiant = IP locale. Remote Authentication : idem, identifiant = IP distante.
    4. Dans VPN → IPsec → Pre-Shared Keys, ajoute la clé : Local Identifier et Remote Identifier = les deux IP, la clé.
    5. Active la connexion, Apply.
    Pourquoi. Un seul tunnel d'abord : on le valide de bout en bout avant de dupliquer, pour ne pas multiplier les erreurs.
    Vérifier. VPN → IPsec → Status Overview : la connexion apparaît, la phase 1 est établie dès que l'autre côté est configuré.
    Piège. Les menus d'OPNsense dépendent de la version : si tu ne vois pas « Connections » mais « Tunnel Settings », tu es sur l'ancienne interface, avec les mêmes paramètres sous d'autres noms.
  2. Ajouter l'enfant (phase 2)

    Dans la connexion : Children → mode tunnel, réseau local 172.17.10.0/24, réseau distant 172.17.20.0/24. Cocher l'activation puis Apply.

    Pas à pas.
    1. Dans la connexion, onglet Children → Add.
    2. Mode Tunnel, Local network = 172.17.10.0/24, Remote network = 172.17.20.0/24 (pour Paris).
    3. Proposals de chiffrement identiques à l'autre côté. Save, puis Apply.
    Pourquoi. L'enfant dit quels réseaux passent dans le tunnel. Sans lui, la phase 1 est établie mais aucun paquet n'est transporté.
    Vérifier. Dans Status Overview, la ligne du tunnel affiche l'enfant avec ses octets échangés dès qu'un ping passe.
    Piège. Réseau local et réseau distant sont inversés sur l'autre pare-feu : vérifie-les à voix haute en comparant les deux écrans.
  3. Faire la même chose sur PAR-FW01, à l'envers

    Local = Paris (10.10.28.112, 172.17.20.0/24), distant = Bruxelles. Même clé, mêmes algorithmes.

    Pas à pas.
    1. Sur PAR-FW01 : même procédure, mais Local = 10.10.28.112 et réseau local 172.17.20.0/24 ; Remote = 10.10.28.111 et réseau distant 172.17.10.0/24.
    2. Même clé, mêmes algorithmes, mêmes identifiants (inversés).
    3. Active et applique.
    Pourquoi. La symétrie est la condition du tunnel : chaque côté décrit la même liaison vue de son extrémité.
    Vérifier. Dès que les deux côtés sont appliqués, Status Overview passe à « Established » des deux côtés.
  4. Tunnel Bruxelles ↔ Londres puis ↔ Berlin

    Seulement quand le premier est validé. Londres : 172.17.30.0/24 ; Berlin : 172.17.40.0/24. Sur le hub, chaque tunnel est une connexion distincte.

    Pas à pas.
    1. Une fois le premier tunnel validé par un ping de LAN à LAN, reprends exactement la même procédure pour Londres (10.10.28.113, 172.17.30.0/24), puis Berlin (10.10.28.114, 172.17.40.0/24).
    2. Sur BRU-FW01, chaque spoke est une connexion séparée avec son propre enfant et sa propre clé.
    3. Teste chaque tunnel avant de passer au suivant.
    Pourquoi. Le hub centralise les liaisons : une panne sur un spoke ne touche pas les autres.
    Vérifier. Trois connexions « Established » sur BRU-FW01, une sur chaque spoke.

Configuration

  1. Autoriser le trafic dans le tunnel

    Firewall → Rules → IPsec : règle d'autorisation, d'abord large pour les tests. Sans elle, le tunnel est « établi » mais ne laisse rien passer.

    Pas à pas.
    1. Firewall → Rules → IPsec (onglet qui apparaît quand IPsec est activé).
    2. Ajoute une règle Pass, protocole any, source any, destination any (large pour les tests).
    3. Save, Apply.
    Pourquoi. Le tunnel est une interface à part avec ses propres règles. Si aucune règle n'autorise, tout est refusé même si le tunnel est « établi ».
    Vérifier. Un ping de LAN à LAN passe.
    Piège. À remplacer par la matrice de flux (section 4), puis supprimer.
  2. Autoriser le tunnel lui-même sur le WAN

    Firewall → Rules → WAN : UDP 500, UDP 4500 et le protocole ESP, de l'IP du pare-feu distant (flux F01 de la matrice).

    Pas à pas.
    1. Firewall → Rules → WAN → Add.
    2. Règle Pass, protocole UDP, source = l'IP WAN du pare-feu distant, destination = « WAN address », port 500, puis une 2e règle pour le port 4500.
    3. Ajoute une règle protocole ESP pour la même source.
    Pourquoi. IKE négocie sur UDP 500 (et 4500 si NAT), le trafic chiffré passe en ESP. Si le WAN bloque ces paquets, la négociation échoue.
    Vérifier. Dans Live View, les paquets UDP 500 de l'autre pare-feu sont « pass » et non « block ».
    Piège. Sans ESP, la phase 1 peut se monter mais aucune donnée ne circule.
  3. Passage par le hub

    Paris ↔ Londres passe par Bruxelles : sur chaque spoke, le réseau distant du tunnel doit inclure les autres LAN (par exemple 172.17.0.0/16 côté spoke), et le hub doit relayer entre ses tunnels.

    Pas à pas.
    1. Sur chaque spoke, dans l'enfant du tunnel vers Bruxelles, mets comme réseau distant le bloc 172.17.0.0/16 (ou les trois LAN des autres sites séparément).
    2. Sur le hub, ajoute des enfants supplémentaires pour que le trafic Paris ↔ Londres soit accepté entre ses tunnels : réseau local = LAN du premier spoke, réseau distant = LAN du second.
    3. Vérifie que la règle de l'interface IPsec autorise ce trafic en transit.
    Pourquoi. Il n'y a pas de tunnel direct Paris ↔ Londres : le hub doit relayer. Sans ces réseaux dans les enfants, le trafic inter-sites est jeté.
    Vérifier. Depuis une VM de Paris, ping 172.17.30.10 (Londres) répond ; tracert passe par le pare-feu de Bruxelles.
    Piège. C'est le point de configuration le plus délicat du labo : fais les enfants un par un et teste après chaque ajout.

Vérifications

  1. Voir l'état

    VPN → IPsec → Status Overview : le tunnel doit être Established (phases 1 et 2).

    Pas à pas.
    1. VPN → IPsec → Status Overview.
    2. Repère la connexion : état « Established » pour la phase 1 et pour l'enfant.
    3. Clique sur les détails pour voir les octets échangés.
    Pourquoi. C'est le premier coup d'œil de diagnostic.
    Vérifier. Établie ne suffit pas : il faut aussi un ping réel (étape suivante).
  2. Un ping réel de LAN à LAN

    Un tunnel « établi » ne prouve rien : depuis une VM de Bruxelles, ping 172.17.20.10 (Paris) doit répondre. Puis dans l'autre sens.

    Windows
    Test-NetConnection 172.17.20.10
Test-NetConnection 172.17.30.10
    Pas à pas.
    1. Depuis une VM de Bruxelles : Test-NetConnection 172.17.20.10 (Paris), puis 172.17.30.10 (Londres), 172.17.40.40 (Berlin).
    2. Reviens à Paris et teste Bruxelles.
    3. Vérifie les octets de l'enfant dans Status Overview : ils augmentent.
    Pourquoi. Un tunnel « établi » ne prouve rien tant qu'aucun paquet n'a traversé.
    Vérifier. Les trois tests renvoient PingSucceeded : True.
    Piège. La cible peut bloquer le ping (pare-feu Windows) : teste un autre port (-Port 3389) pour distinguer.
  3. En cas d'échec

    VPN → IPsec → Log File. Phase 1 qui échoue : clé, identifiants, adresse distante. Phase 2 qui échoue : réseaux local et distant inversés ou différents entre les deux côtés. Rien ne passe malgré « Established » : règle manquante sur l'interface IPsec.

    Pas à pas.
    1. VPN → IPsec → Log File : lis les dernières lignes au moment de la tentative.
    2. Phase 1 qui échoue : clé, identifiants, adresse distante, algorithmes.
    3. Phase 2 qui échoue : réseaux local et distant inversés ou différents entre les deux côtés.
    4. Établi mais rien ne passe : règle manquante sur l'interface IPsec, ou sur le WAN (ESP).
    Pourquoi. Un message d'erreur lu en vrai vaut dix hypothèses.
    Vérifier. L'erreur correspond à une des quatre pistes ci-dessus.

3Les routes et le DNS à travers les tunnels

Un tunnel monté ne suffit pas : chaque VM doit savoir qu'elle passe par son pare-feu pour joindre les autres sites.

Préparation

  1. Même passerelle partout

    Chaque VM d'un site a pour passerelle le LAN d'OPNsense (172.17.x.1). Les plages et leur usage :

    Pas à pas.
    1. Sur chaque VM d'un site, la passerelle par défaut est 172.17.x.1.
    2. Pour Windows : Get-NetIPConfiguration pour vérifier ; pour Linux : ip route.
    Pourquoi. Une seule passerelle par LAN : OPNsense. Tout trafic vers un autre site ou Internet passe par elle.
    Vérifier. La passerelle indiquée est celle du plan.

Installation

  1. Vérifier les routes d'un serveur
    Windows
    Get-NetRoute -DestinationPrefix 0.0.0.0/0
route print
    Pas à pas.
    1. Get-NetRoute -DestinationPrefix 0.0.0.0/0 : une seule route par défaut, avec la passerelle du site.
    2. route print : aucune route vers un sous-réseau inconnu.
    Pourquoi. Une deuxième route par défaut (par exemple d'une autre carte) fait partir le trafic au hasard.
    Vérifier. Une route 0.0.0.0/0 unique, métrique cohérente.
  2. Résolution des noms entre sites

    Les clients de chaque site utilisent le contrôleur de domaine comme DNS. Enregistrements à créer ensuite (page Identité) :

    Pas à pas.
    1. Chaque client a pour DNS les contrôleurs de domaine : 172.17.10.10 et 172.17.20.10.
    2. Les enregistrements des serveurs sont créés sur les DC (page Identité).

4Le filtrage : remplacer « tout autorisé »

Une fois les tunnels testés, on supprime la règle « tout » et on ne laisse que les flux utiles. Une règle dit : sur cette interface, pour ce protocole, de cette source vers cette destination, on autorise ou on bloque. Elles se lisent de haut en bas, la première qui correspond gagne ; sans règle d'autorisation, une interface bloque tout.

Préparation

  1. Lire la matrice de flux

    Chaque ligne ci-dessous est un flux à autoriser, avec la raison. Rien d'autre n'est nécessaire.

    Pas à pas.
    1. Ouvre le tableau des 28 flux : chaque ligne indique la source, la destination, le protocole et la raison.
    2. Repère les flux qui concernent ton site.
    Pourquoi. Une règle sans raison est une faille potentielle : la matrice documente chaque ouverture.
    Vérifier. Tu peux expliquer chaque règle que tu vas écrire.
  2. Créer des alias

    Firewall → Aliases : un alias par groupe (DC, LAN_ALL, DOCKER) évite de réécrire les IP dans chaque règle.

    Pas à pas.
    1. Firewall → Aliases → Add.
    2. Nom DC, type Host(s), contenu 172.17.10.10, 172.17.20.10.
    3. Nom LAN_ALL, type Network(s), contenu les quatre LAN.
    4. Nom DOCKER, type Host(s), les hôtes Docker.
    Pourquoi. Un alias rend les règles lisibles (« vers DC ») et évite de mettre à jour dix règles quand une IP change.
    Vérifier. Les alias apparaissent dans la liste et sont utilisables dans les règles.

Installation

  1. Écrire les règles flux par flux

    Firewall → Rules → IPsec (trafic venant des autres sites) et → LAN (trafic sortant). Pour chaque ligne de la matrice : protocole et ports, source, destination, cocher « Log » le temps des tests.

    Pas à pas.
    1. Firewall → Rules → IPsec pour le trafic venant des autres sites, LAN pour le trafic sortant.
    2. Pour chaque ligne de la matrice : Pass, protocole, source (alias), destination (alias), port.
    3. Coche Log pendant les tests.
    4. Save, puis Apply à la fin.
    Pourquoi. Une règle par flux et une raison par règle : c'est la matrice appliquée.
    Vérifier. Le flux testé fonctionne ; dans Live View la ligne correspondante est « pass » avec la bonne règle.
    Piège. L'ordre compte : la première règle qui correspond gagne.
  2. Supprimer la règle « tout »

    Seulement quand les règles utiles sont en place et testées une par une.

    Pas à pas.
    1. Une fois les règles testées une par une, retourne dans Firewall → Rules.
    2. Supprime la règle « TEMPORAIRE tout autorisé ».
    3. Apply puis relance tous les tests.
    Pourquoi. Tant que la règle « tout » existe, la matrice ne protège rien.
    Vérifier. Les flux de la matrice passent, un flux hors matrice est bloqué.
    Piège. Fais-le en dernier, quand tout fonctionne, pour pouvoir te rattraper.

Configuration

  1. Relais DHCP

    Un site sans serveur DHCP local utilise le relais d'OPNsense : Services → DHCP Relay, interface LAN, destination = 172.17.10.10 et 172.17.20.10. Désactiver le serveur DHCP d'OPNsense sur ce LAN. Les clients envoient leur DISCOVER en diffusion, le relais le transmet en unicast à travers le tunnel (flux F07).

    Pas à pas.
    1. Services → DHCP Relay : active, interface LAN.
    2. Ajoute un serveur de destination : 172.17.10.10, puis 172.17.20.10.
    3. Désactive le serveur DHCP natif d'OPNsense sur le LAN (Services → DHCPv4).
    Pourquoi. Le DISCOVER d'un client est une diffusion qui ne traverse pas un routeur : le relais le transforme en unicast vers les serveurs.
    Vérifier. Un client DHCP du site obtient une adresse de la plage .100–.199.
    Piège. Deux serveurs DHCP sur le même LAN donnent des adresses contradictoires : désactive celui d'OPNsense.
  2. Ouvrir le port du failover DHCP

    Entre les deux serveurs DHCP, le failover utilise le TCP 647 (flux F08).

    Pas à pas.
    1. Règle sur l'interface IPsec : TCP 647 entre 172.17.10.10 et 172.17.20.10 (dans les deux sens).
    Pourquoi. Le failover DHCP synchronise les baux entre les deux serveurs sur TCP 647.
    Vérifier. Dans la console DHCP, l'état du failover affiche « Normal ».
