OPNsense, tunnels et flux

Chaque site a son pare-feu OPNsense. Bruxelles est le centre : les trois autres s'y relient par IPsec. Les quatre étapes de la page : installer le pare-feu, monter les tunnels, faire passer les routes, filtrer.

En bref

Un pare-feu par site (WAN dans la salle, LAN du site), trois tunnels site-à-site vers Bruxelles, un ping réel de LAN à LAN avant de toucher au filtrage, puis seulement les flux de la matrice. Le DHCP passe d'un site à l'autre par relais.

Dans cette page OPNsense · Tunnels IPsec · Routes et DNS · Filtrage

Pourquoi en étoile

Trois tunnels au lieu de six. Paris ↔ Londres passe par Bruxelles ; si Bruxelles tombe, les autres sites ne se voient plus. Les routes et les règles de chaque pare-feu doivent donc connaître tous les LAN.

1Une VM OPNsense par site

OPNsense est un pare-feu logiciel : une VM qui joue le routeur entre le WAN (la salle) et le LAN du site, filtre le trafic et monte les tunnels. Tout se règle dans une interface web.

Préparation

  1. Deux cartes réseau

    Carte 1 sur le commutateur WAN, carte 2 sur LAN-xxx du site. L'ordre compte : la première devient WAN, la deuxième LAN.

  2. Dimensionner

    Génération 2 · 2 vCPU · 2 Go de RAM fixe · 20 Go de disque. Désactiver le démarrage sécurisé (Settings → Security) : FreeBSD ne le gère pas avec le modèle par défaut.

  3. Noter les valeurs du site

    WAN de chaque pare-feu : 10.10.28.111 à .114 (Bruxelles à Berlin), passerelle de la salle 10.10.28.254. LAN : 172.17.10.1, 172.17.20.1, 172.17.30.1, 172.17.40.1.

Installation

  1. Installer depuis l'ISO

    Démarrer sur l'ISO d'OPNsense (image dvd). Se connecter en installer pour lancer l'installation sur le disque, choisir la disposition du clavier, un disque, puis définir le mot de passe de root et redémarrer en retirant l'ISO.

  2. Attribuer les interfaces

    À la console : Assign interfaces, confirmer que hn0 est le WAN et hn1 le LAN (les noms d'interface Hyper-V). Set interface IP address : LAN = 172.17.x.1/24, sans DHCP serveur ; WAN = IP fixe du tableau, passerelle de la salle.

Configuration

  1. Premier accès web

    Depuis une VM du LAN : https://172.17.x.1 (certificat auto-signé : avertissement normal). Assistant System → Wizard : nom d'hôte (BRU-FW01…), domaine eurocorp.lan, DNS = les deux contrôleurs, fuseau horaire.

  2. Laisser entrer le réseau de la salle

    Interfaces → WAN : décocher « Block private networks ». La salle est en 10.10.28.0/24, une adresse privée : avec la case cochée, OPNsense jetterait le trafic des autres pare-feu — les tunnels ne monteraient pas. Laisser « Block bogon networks » coché.

  3. Règle temporaire sur le LAN

    Firewall → Rules → LAN : « Autoriser tout » le temps de monter et tester les tunnels. On la remplace par la matrice de flux à la section 4.

  4. Greffon Hyper-V

    System → Firmware → Plugins : installer os-hyperv pour que la VM s'arrête et redémarre proprement depuis Hyper-V.

  5. Changer le mot de passe par défaut

    Utilisateur root. Le noter dans Infos.md, jamais dans une fiche.

Vérifications

  1. Le pare-feu atteint la salle

    Interfaces → Diagnostics → Ping vers 10.10.28.254 doit répondre.

  2. Un client du LAN atteint le pare-feu

    Depuis une VM du site : ping 172.17.x.1, puis ouvrir l'interface web. C'est le test que tu as déjà fait à Paris.

2Les tunnels IPsec

Bruxelles est le centre (hub), Paris, Londres et Berlin sont des extrémités (spokes). Trois tunnels site-à-site, chacun sur un petit réseau de transit :

Préparation

  1. Les tunnels et leurs adresses
  2. Décider ce qui sera commun

    Une clé partagée (PSK) différente par tunnel, longue et aléatoire, notée dans Infos.md. Mêmes algorithmes des deux côtés (par exemple AES-256 / SHA-256 / groupe DH 14 ou plus). Identifiants : l'IP WAN de chaque pare-feu.

  3. Rappeler la logique en deux phases

    Phase 1 : les deux pare-feu s'identifient et s'accordent sur le chiffrement. Phase 2 : on dit quels réseaux passent dans le tunnel (LAN local ↔ LAN distant). Une erreur de réseau local/distant inversé est la panne la plus fréquente.

Installation

  1. Tunnel Bruxelles ↔ Paris d'abord

    Sur BRU-FW01 : VPN → IPsec → Connections → nouvelle connexion. Adresse locale = WAN de Bruxelles (10.10.28.111), adresse distante = WAN de Paris (10.10.28.112), authentification par clé pré-partagée (saisie dans Pre-Shared Keys), IKEv2.

  2. Ajouter l'enfant (phase 2)

    Dans la connexion : Children → mode tunnel, réseau local 172.17.10.0/24, réseau distant 172.17.20.0/24. Cocher l'activation puis Apply.

  3. Faire la même chose sur PAR-FW01, à l'envers

    Local = Paris (10.10.28.112, 172.17.20.0/24), distant = Bruxelles. Même clé, mêmes algorithmes.

  4. Tunnel Bruxelles ↔ Londres puis ↔ Berlin

    Seulement quand le premier est validé. Londres : 172.17.30.0/24 ; Berlin : 172.17.40.0/24. Sur le hub, chaque tunnel est une connexion distincte.

Configuration

  1. Autoriser le trafic dans le tunnel

    Firewall → Rules → IPsec : règle d'autorisation, d'abord large pour les tests. Sans elle, le tunnel est « établi » mais ne laisse rien passer.

  2. Autoriser le tunnel lui-même sur le WAN

    Firewall → Rules → WAN : UDP 500, UDP 4500 et le protocole ESP, de l'IP du pare-feu distant (flux F01 de la matrice).

  3. Passage par le hub

    Paris ↔ Londres passe par Bruxelles : sur chaque spoke, le réseau distant du tunnel doit inclure les autres LAN (par exemple 172.17.0.0/16 côté spoke), et le hub doit relayer entre ses tunnels.

Vérifications

  1. Voir l'état

    VPN → IPsec → Status Overview : le tunnel doit être Established (phases 1 et 2).

  2. Un ping réel de LAN à LAN

    Un tunnel « établi » ne prouve rien : depuis une VM de Bruxelles, ping 172.17.20.10 (Paris) doit répondre. Puis dans l'autre sens.

    Windows
    Test-NetConnection 172.17.20.10
Test-NetConnection 172.17.30.10
  3. En cas d'échec

    VPN → IPsec → Log File. Phase 1 qui échoue : clé, identifiants, adresse distante. Phase 2 qui échoue : réseaux local et distant inversés ou différents entre les deux côtés. Rien ne passe malgré « Established » : règle manquante sur l'interface IPsec.

4Le filtrage : remplacer « tout autorisé »

Une fois les tunnels testés, on supprime la règle « tout » et on ne laisse que les flux utiles. Une règle dit : sur cette interface, pour ce protocole, de cette source vers cette destination, on autorise ou on bloque. Elles se lisent de haut en bas, la première qui correspond gagne ; sans règle d'autorisation, une interface bloque tout.

Préparation

  1. Lire la matrice de flux

    Chaque ligne ci-dessous est un flux à autoriser, avec la raison. Rien d'autre n'est nécessaire.

  2. Créer des alias

    Firewall → Aliases : un alias par groupe (DC, LAN_ALL, DOCKER) évite de réécrire les IP dans chaque règle.

Installation

  1. Écrire les règles flux par flux

    Firewall → Rules → IPsec (trafic venant des autres sites) et → LAN (trafic sortant). Pour chaque ligne de la matrice : protocole et ports, source, destination, cocher « Log » le temps des tests.

  2. Supprimer la règle « tout »

    Seulement quand les règles utiles sont en place et testées une par une.

Configuration

  1. Relais DHCP

    Un site sans serveur DHCP local utilise le relais d'OPNsense : Services → DHCP Relay, interface LAN, destination = 172.17.10.10 et 172.17.20.10. Désactiver le serveur DHCP d'OPNsense sur ce LAN. Les clients envoient leur DISCOVER en diffusion, le relais le transmet en unicast à travers le tunnel (flux F07).

  2. Ouvrir le port du failover DHCP

    Entre les deux serveurs DHCP, le failover utilise le TCP 647 (flux F08).

Vérifications

  1. Tester chaque flux

    L'outil « Tester un flux du pare-feu » donne les commandes Test-NetConnection à lancer depuis le LAN source.

  2. Lire les journaux

    Firewall → Log Files → Live View : un blocage inattendu y apparaît avec la règle responsable.

  3. Un client reçoit une adresse

    Un poste de Londres en DHCP obtient une adresse de 172.17.30.100–199 venant du serveur de Bruxelles ou de Paris.
